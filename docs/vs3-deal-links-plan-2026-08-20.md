# VS-3: «якорь + прикреплённые сделки» — спецификация (2026-08-20)

Запрос владельца: «обычно к номеру/брони привязываются услуги… так же в ресторане.
Получается 1 якорь, но к нему подкручен заказ услуги — велопрокат, трансфер, — и у
них своя вкладка… они должны двигаться по колонкам отдельно».
Решение по объёму: **привязку создаёт владелец в кабинете** (витрина — следующим
шагом). Отмашка: «делаем».

---

## 1. Сценарии, ради которых это делается

| Архетип | Якорь | Спутники |
|---|---|---|
| Отель | бронь номера 101 (`stay`) | велопрокат (`booking`), трансфер (`booking`/`order`), поздний выезд |
| Ресторан | бронь стола (`booking`) | предзаказ торта (`order`), кейтеринг на вынос |
| Кейтеринг | заявка на мероприятие (`job`) | аренда посуды (`order`), доп-персонал (`booking`) |
| Werkstatt | заявка на ремонт (`job`) | запись на приёмку (`booking`) |

Общее во всех: **спутник — самостоятельная сделка** со своей ценой, своим статусом
и своим движением по колонкам. Связь нужна, чтобы на приёмке/в кухне было видно
«это к брони Кляйнов», а не как отдельный безымянный заказ.

## 2. Что есть сегодня (сверено с кодом)

- **Extras** (`apps/core/extras.py`) — доп-услуга хранится СНИМКОМ в JSON самой
  брони: `[{label, price_cents}]`, сумма уже включена в итог брони. У снимка нет
  ни статуса, ни карточки, ни колонки: «велопрокат» невозможно двинуть по доске,
  назначить исполнителя или отменить отдельно.
- **`Job.booking`** (A7d) — единственная настоящая связь сделок, только для пары
  «заявка → выездной Termin».
- **`Order.parent_order`** — шов Stage 3 без логики (цепочка заказов, один kind).
- Generic-ссылки в проекте уже приняты: `reviews.Review(entity_kind, entity_id)`,
  `inbox.Conversation(ref_kind, ref_id)` — тот же приём.
- Все шесть сделок — TENANT-модели с UUID-PK (`core.TimestampedModel`),
  `apps.core` в `TENANT_APPS` → новая таблица едет в схемы тенантов.
- Кросс-kind поиск сделок уже есть: `palette_search._deals` поверх
  `transactions._managed_queryset(kind, q=…)` — пикер якоря переиспользует его.

## 3. Модель данных

Одна TENANT-таблица в `apps/core` вместо полей на шести моделях: одна аддитивная
миграция, симметричные запросы в обе стороны, ноль правок в движках сделок.

```python
class DealLink(TimestampedModel):
    anchor_kind = CharField(max_length=16, choices=KIND_CHOICES)  # stay|booking|order|job|ticket|reservation
    anchor_id   = UUIDField()
    child_kind  = CharField(max_length=16, choices=KIND_CHOICES)
    child_id    = UUIDField()
    note        = CharField(max_length=120, blank=True)   # «Velo, 2 Tage»

    constraints = [UniqueConstraint("child_kind", "child_id", name="deallink_one_anchor_per_child")]
    indexes     = [Index("anchor_kind", "anchor_id"), Index("child_kind", "child_id")]
```

**Почему не FK.** Якорь и спутник — разные модели; FK «на любую из шести»
потребовал бы GenericForeignKey с джойном `contenttypes` на КАЖДОЙ карточке доски.
Целостность: сделки практически не удаляются (DSGVO-стирание анонимизирует
`Customer`, записи остаются), а сироты отсекаются при чтении — как в `reviews`.

**Почему `unique(child_kind, child_id)`.** У спутника ровно ОДИН якорь: «велопрокат
к брони 101» — иначе доска врала бы («+2 услуги» у двух разных броней про один и
тот же прокат). Перепривязка = обновление той же строки (move), не вторая связь.

## 4. Правила (инварианты волны)

1. **Движение независимо.** Перевод якоря НЕ двигает спутника и наоборот. Каскадов
   нет вовсе — иначе пришлось бы описывать правила для 6×6 пар статусов, а FSM
   каждого kind остаётся жёстким полом (принцип с FB-3).
2. **Деньги не сливаются.** У якоря своя сумма, у спутника своя; в отчётах и в
   `finance` ничего не меняется. На детали якоря показывается справочный итог
   «Zusatzleistungen: 85,00 €» — это ПОКАЗ, не запись.
3. **Один уровень.** Спутник спутника не бывает: сделка, у которой уже есть якорь,
   не может стать якорем (проверка при attach) — иначе доска превращается в дерево.
4. **Себя к себе нельзя** (тот же kind+id) и **цикл A→B→A** отбивается.
5. **Extras не трогаем.** Снимок остаётся снимком; исторические брони неизменны.
   Кому нужен «велопрокат как сделка» — заводит сделку и привязывает.
6. **Витрина не трогается**: гость по-прежнему отмечает Extras галочкой.
7. **Отмена/удаление.** Отмена якоря связь НЕ рвёт (история важнее); удаление
   объекта оставляет сироту — читатель её отбрасывает, `detach` доступен всегда.

## 5. Сервис `apps/core/deal_links.py`

```python
attach(anchor_kind, anchor_id, child_kind, child_id, note="") -> DealLink
    # валидирует kind ∈ TRANSACTION_KINDS; обе сделки должны существовать;
    # запрещает self-link, цикл и второй уровень; идемпотентен (та же пара →
    # обновление note); другой якорь → перенос (unique на child)
detach(child_kind, child_id) -> bool
anchor_of(child_kind, child_id) -> DealLink | None
children_of(anchor_kind, anchor_id) -> list[DealLink]
for_cards(kind, ids) -> {uuid: {"children": [tx…], "anchor": tx|None}}
    # BATCH: 2 запроса к DealLink (в обе стороны) + по одному queryset'у на каждый
    # встретившийся kind для подписей. Ни одного запроса на карточку (замок N+1).
```

Подписи связанных сделок берём через существующий `transactions.transaction_for`
(title/сумма/ссылка уже нормализованы) — никакого второго источника правды.

## 6. Что видит владелец

**Карточка доски**
- у якоря: строка «🔗 2 Zusatzleistungen» (в title — их названия);
- у спутника: «🔗 zu Zimmer 101 · Fam. Klein» — ссылка на карточку якоря.

**Деталь сделки** (`stays`/`booking`/`orders`/`jobs` — 4 экрана v1): блок
«Verknüpfte Leistungen»:
- список спутников: название · сумма · статус · «✂️ Lösen»;
- справочный итог по спутникам;
- у спутника — строка «Gehört zu: <якорь>» с той же кнопкой отвязки;
- кнопка «🔗 Verknüpfen».

**Экран привязки** `/dashboard/verknuepfen/<kind>/<pk>/`
- поиск по коду/имени/e-mail среди сделок ДРУГИХ направлений (гейт
  `sales_page.visible_kinds`, поиск — `_managed_queryset(q=…)`, т.е. новых
  способов читать данные не вводим);
- две роли: «прикрепить ЭТУ сделку к выбранной» (текущая = спутник) и
  «прикрепить выбранную К ЭТОЙ» (текущая = якорь) — параметр `role`;
- из списка исключены: сама сделка, уже привязанные к другому якорю (с пометкой
  «bereits verknüpft»), и сделки, у которых уже есть спутники (правило §4.3).

## 7. Безопасность и производительность

- Все вьюхи — кабинетные: `@login_required` + `Membership` (`has_cabinet_access`
  fail-closed, урок M22b), мутации POST-only с CSRF, `next=` только внутренний
  путь (правило после ревью «Кабинет-X»).
- Изоляция — схемой тенанта (таблица TENANT), чужой pk → 404.
- Доска: +2 запроса на секцию, независимо от числа карточек. Замок: рендер
  секции с 1 и с 20 связями даёт одинаковое число запросов.

## 8. Демо и i18n

- Кит `hotel`: к брони номера привязан «Fahrradverleih» (booking) — на стенде
  видно обе стороны связи.
- Новые msgid (≈10): «Verknüpfte Leistungen», «Gehört zu», «Verknüpfen»,
  «Lösen», «Zusatzleistungen», «bereits verknüpft», … — сразу в 5 каталогов.

## 9. Замки (пишутся ДО правок соответствующего слоя)

1. `attach` создаёт связь; повтор той же пары идемпотентен.
2. Второй якорь для того же спутника — ПЕРЕНОС, не дубль (unique держит).
3. Self-link → ValueError.
4. Цикл A→B→A → ValueError.
5. Второй уровень (у спутника есть свой спутник) → ValueError.
6. `for_cards` — батч: N связей не увеличивают число запросов.
7. Сирота (объект удалён) не ломает рендер доски.
8. Карточка якоря показывает счётчик, карточка спутника — ссылку на якорь.
9. Деталь: список спутников + справочный итог; «Lösen» рвёт связь.
10. Пикер исключает саму сделку и показывает «bereits verknüpft».
11. Аноним/без Membership → 403/302 (не 200).
12. Отмена якоря связь не рвёт (движение независимо).

## 11. Чего НЕ делаем в v1 (осознанно)

Витрина (гость создаёт спутника сам) · каскады статусов · слияние денег и
отчётов · миграция Extras в сделки · несколько якорей у спутника · вложенность
глубже одного уровня · автоподбор «похоже, это к той брони».
