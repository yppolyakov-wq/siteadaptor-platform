# VS-3: «якорь + прикреплённые сделки» (план, 2026-08-20)

Запрос владельца: «обычно к номеру/брони привязываются услуги… так же в
ресторане. Получается 1 якорь, но к нему подкручен заказ услуги — велопрокат,
трансфер, — и у них своя вкладка… они должны двигаться по колонкам отдельно».
Решение по объёму: **сначала кабинет** (гость на витрине — следующим шагом).

## 1. Чего сегодня нет (сверено с кодом)

- **Extras** (`apps/core/extras.py`) — доп-услуга к брони хранится СНИМКОМ в JSON
  самой брони: `[{label, price_cents}]`. У неё нет ни статуса, ни карточки, ни
  колонки: «велопрокат» невозможно двигать по доске и невозможно посчитать
  отдельно. Сумма Extras уже входит в итог брони.
- **`Job.booking`** (A7d) — единственная настоящая связь сделок, и только для
  пары «заявка → выездной Termin».
- **`Order.parent_order`** — шов Stage 3 без логики (цепочка заказов, не
  кросс-kind).

## 2. Модель связи

Одна TENANT-таблица в `apps/core` вместо полей на шести моделях: одна аддитивная
миграция, симметричные запросы, ноль правок в движках сделок. Прецедент
generic-ссылки в проекте уже есть — `reviews.Review(entity_kind, entity_id)` и
`inbox.Conversation(ref_kind, ref_id)`.

```
DealLink
  anchor_kind  CharField(choices=TRANSACTION_KINDS)   # stay | booking | order | …
  anchor_id    UUIDField
  child_kind   CharField(choices=TRANSACTION_KINDS)
  child_id     UUIDField
  note         CharField(blank=True)                  # «Velo, 2 Tage»
  constraints: unique(child_kind, child_id)           # у спутника ОДИН якорь
               index(anchor_kind, anchor_id)
```

Почему не FK: якорь и спутник — разные модели (StayBooking/Booking/Order/Job),
FK на «любую из шести» невозможен без GenericForeignKey (лишний contenttypes-
джойн на каждую карточку доски). Целостность: удаление сделки — редкость
(DSGVO-стирание анонимизирует, не удаляет), сироты отсекаются фильтром при
чтении, как в reviews.

## 3. Что видит владелец

- **Карточка якоря** на доске: строка «＋ 2 Zusatzleistungen: Velo, Transfer»
  (клик — на карточку спутника). ОДИН запрос на секцию по id видимых карточек
  (паттерн LS-6 «⚠️ Problem»), не per-card.
- **Карточка спутника**: «zu Zimmer 101 · Fam. Klein» со ссылкой на якорь.
- **Вкладки раздельные, движение независимое** — прямое требование владельца:
  велопрокат живёт в своей вкладке и двигается по своим колонкам.
- **Привязка** (v1, кабинет): на карточке/детали сделки — «🔗 Verknüpfen» →
  поиск по коду/клиенту среди сделок ДРУГИХ направлений → выбор якоря.
  Отвязка — там же.

## 4. Границы v1 (осознанно НЕ делаем)

- Деньги НЕ объединяются: у якоря своя сумма, у спутника своя. «Итог по гостю»
  — отдельный вопрос (там же решается судьба Extras).
- Extras не мигрируем в сделки: снимок остаётся снимком (исторические брони
  неизменны). Владелец, которому нужен велопрокат «как сделка», заводит её
  сделкой и привязывает.
- Витрина не трогается: гость по-прежнему отмечает Extras галочкой.
- Каскадов статусов нет: перевод якоря НЕ двигает спутника (иначе пришлось бы
  описывать правила для 6×6 пар).

## 5. Инкременты

1. **VS-3a** модель + миграция + сервис `links.attach/detach/for_anchors` (замки:
   один якорь на спутника, идемпотентность, сироты).
2. **VS-3b** показ на доске: строка на карточке якоря и на карточке спутника
   (один запрос на секцию — замок N+1).
3. **VS-3c** кабинетная привязка: экран/попап поиска сделки + отвязка.
4. **VS-3d** демо: у отеля — бронь номера с прикреплённым велопрокатом
   (наглядно на стенде).
