# План: виды отображения вариантов и опций (2026-08-01)

Решения владельца по вопросу «что у нас по учёту опций»:

1. **Варианты** — «возможность использования в[ыбора]: варианты, цвет, фото,
   список, чекбокс; если есть ещё что-то — добавь». То есть вид выбирает
   ВЛАДЕЛЕЦ из реестра, как `CBLOCK_VARIANTS`/`SECTION_STYLES` в редакторе.
2. **Модификаторы блюда** — «да, с фото и чекбоксами-плитками».

## 1. Что есть сегодня (разведка)

| Механизм | Учёт | Фото | Вид на витрине |
|---|---|---|---|
| `catalog.ProductVariant` | цена, ОСТАТОК (леджер), SKU/EAN, Grundpreis, EK/Meldebestand; оси `size`/`color` рядом с `label` | поле `images` **есть** | один `<select name="variant">`; при выборе подменяется главное фото |
| `catalog.ModifierGroup`/`ModifierOption` | надбавка `price_delta`, снимок в позицию заказа; `min/max_select` | **нет** | `<select>` при max=1, чекбоксы при max≠1 |
| `core.Extra` (доп-услуги брони) | цена разовая / за ночь | есть (`image`) | чекбокс + миниатюра 32×32 |
| `catalog.Combo*` | опция = товар + надбавка | нет своего | список |

**Найденный дефект:** `ProductVariant.images` завели в M4-A, витрина честно
подменяет главное фото по `data-image`, но **заполнить поле из кабинета нечем** —
в форме варианта полей загрузки нет, CSV-импорт их не пишет; единственный писатель
— демо-кит `mode`. Функция мёртвая у реального владельца. Чиним первым шагом,
иначе фото-виды не на чем показывать.

## 2. Жёсткое ограничение

Замок `test_cart_form_variants_and_modifiers_fields` пинит ТОЧНЫЙ набор полей
формы корзины: `{csrfmiddlewaretoken, product, variant, mod, qty}`, причём
`field_names` — это regex по `name="…"` во всём HTML формы. Значит:

* новых имён полей вводить нельзя — свотчи управляют СУЩЕСТВУЮЩИМ
  `select name="variant"`;
* кнопки свотчей — `<button type="button">` **без** `name=` (иначе имя попадёт в
  набор и замок упадёт).

Отсюда архитектура: `<select>` остаётся в DOM всегда; при включённом виде рядом
рендерится разметка свотчей, а скрипт прячет select и связывает их. Нет JS —
работает ровно как сегодня (progressive enhancement, как во всём проекте).

## 3. Реестр видов

Новый `apps/catalog/option_styles.py` — единый источник для витрины и кабинета.

**Варианты (`VARIANT_STYLES`):**

| ключ | вид | когда уместен |
|---|---|---|
| `""` | выпадающий список (как сегодня, дефолт) | много фасовок, узкая колонка |
| `buttons` | пилюли-кнопки | размеры, объёмы |
| `color` | цветные кружки + подпись | одежда с цветом |
| `photo` | фото-плитки | когда у вариантов есть фото |
| `list` | строки: миниатюра + подпись + цена + остаток | наборы, боксы |
| `axes` | ДВЕ оси: цвет кружками, размер кнопками | одежда цвет×размер |

`axes` показываем в реестре только когда у товара заполнены обе оси — иначе он
выродится в один ряд и запутает.

**Модификаторы (`MODIFIER_STYLES`):** `""` (как сегодня), `tiles` (плитки с фото),
`list` (строка с миниатюрой, как Extras), `chips` (компактные пилюли).

Цвет кружка: `color` варианта → HEX через словарь немецких названий
(`Blau`/`Rot`/`Schwarz`/`Weiß`/`Anthrazit`/`Navy`/`Bordeaux`/`Beige`…). Нет в
словаре → показываем фото варианта, нет и его → первую букву. Никаких «угадаем
цвет по строке» — только явный словарь, иначе «Sonnengelb» станет чёрным.

## 4. Хранение выбора

* `Product.variant_style` — CharField(choices, blank) — **миграция catalog**.
  Пусто = глобальный дефолт.
* `ModifierGroup.display_style` — CharField(choices, blank) — **та же миграция**.
  Per-группа, потому что «Größe» и «Beilage» просят разного вида.
* `ModifierOption.image` — JSONField(default=dict) — **та же миграция** (FileRef,
  как `Extra.image`).
* Глобальный дефтолт магазина — `site_config["site_defaults"]["variant_style"]`
  (presence-minimal, как `card_style` из ST-7c): golden normalize не меняется,
  ключ появляется только когда владелец его выбрал.

Пустой стиль везде = байт-в-байт текущая разметка (паритет-замки пишем ДО правок).

## 5. Кабинет

* Форма варианта: поле загрузки фото + миниатюра + «удалить» (закрывает дефект §1).
* Форма товара: селект «Вид выбора вариантов» (реестр + «как в настройках сайта»).
* Блок модификаторов: на группе — селект вида; на опции — загрузка фото.
* Билдер/тема: глобальный дефолт «Вид выбора вариантов» рядом с «Kartenform».

## 6. Порядок работ

1. **O-1** фото варианта в кабинете (без миграции) + замок.
2. **O-2** реестр `option_styles.py` + миграция (`variant_style`,
   `display_style`, `ModifierOption.image`) + глобальный дефолт в normalize.
3. **O-3** рендер вариантов: партиал `_variant_picker.html` со всеми видами +
   один делегированный скрипт; паритет-замок «пустой стиль = прежняя разметка»
   и «набор имён полей неизменен» — ДО правок.
4. **O-4** рендер модификаторов: плитки/список/чипы + фото.
5. **O-5** кабинет (селекты видов, загрузка фото опции) + билдер.
6. **O-6** демо (`mode` — `axes`, `restaurant`/`cafe` — `tiles`), i18n, доки.

## 7. Вне объёма

* Матрица «недоступные комбинации» при `axes` считается из активных вариантов и
  их остатка (гасим кнопку), но БЕЗ подгрузки с сервера — данные уже в DOM.
* `ComboOption` фото — v2 (там опция = товар, фото берётся у товара; отдельный
  разговор).
* Учёт остатка у модификаторов не заводим: это надбавка к позиции, а не складская
  единица (иначе поедет леджер).
