# Verkäufe v2 — главная рабочая страница кабинета (план, 2026-08-20)

Владелец: «это главная страница админки, наряду с каталогом, должна быть хорошо
продумана — при условии что это ОДИН тип, не комплекс как pranasy (его тоже нужно
будет продумать)». Решения по 4 развилкам приняты (см. §2). Всё ниже — по коду,
не по памяти.

## 1. Что есть сегодня (сверено с кодом)

| Слой | Как сейчас | Файл |

- **1 направление (13):** bakery · butcher · grocery · clothing · retail ·
  online_shop · restaurant · cafe · friseur · tour_operator · events ·
  handwerker · **catering**
- **2 направления (2):** hotel (Übernachtungen + Termine) · werkstatt
  (Termine + Aufträge)

## 2. Решения владельца (2026-08-20)

1. **Одно направление → ряда вкладок нет**, заголовок страницы = имя направления.
2. **Колонка = СТАТУС**, но колонки визуально сгруппированы по стадии, к которой
   относятся.
3. **На карточку:** дата события + гости · сортировка по дате события · сумма в
   шапке колонки · срок сметы / просрочка.
4. **Мульти-направление:** «к номеру/брони привязываются услуги… они должны
   двигаться по колонкам отдельно… т.е. получается 1 якорь, но к нему прикручен
   заказ услуги (велопрокат, трансфер), и у них своя вкладка».

## 3. Волна VS-2 (без миграций) — п.1-3

### VS-2a. Заголовок вместо одинокой вкладки
`sales_page.tab_descriptors` уже знает состав; шаблон рисует ряд только при
`len(tabs) > 1`, иначе `<h1>` = `KIND_LABEL[kind]`. У двух+ — вкладки СО
СЧЁТЧИКОМ активных сделок (один агрегат на вкладку, как честные счётчики колонок
из волны V4).

### VS-2b. Колонки = статусы, сгруппированные по стадиям
- Источник колонок: `status_registry.all_descriptors(kind, tenant)` (встроенные ∪
  свои, SM-3) → колонка на статус, `descriptor.stage` = группа.
- Над колонками — полоса групп (NEU · IN BEARBEITUNG · FERTIG · ABGESCHLOSSEN),
  каждая накрывает свои колонки; группа = существующая стадия, поэтому FSM,
  эффекты статусов и роли НЕ трогаются.
- Drag становится ОДНОЗНАЧНЫМ: сейчас `_board_body.js` ищет «первый допустимый
  переход в эту стадию» — с колонкой-статусом целевой статус задан явно.
  Недопустимый переход → прежний snap-back + тост (правила FSM = жёсткий пол).
- Терминальные колонки скрыты тумблером «Abgeschlossene anzeigen» (как сейчас).
- Настройка колонок на «Abläufe» переезжает на уровень статусов: переименование
  уже есть (FB-4a «Status-Namen»), скрытие/порядок — те же механики, но ключ
  `board` начинает хранить статусы. **Осторожно:** `normalize_board` и его
  golden-паритет — presence-minimal; старые значения стадий читаем как «группу».

### VS-2c. Карточка отвечает «что горит и где деньги»
- В контракт `Transaction` добавляется `when` (дата/время события) + `when_label`:
  job → `event_date` (+ `guest_count` строкой «80 Gäste»), order → `pickup_slot`,
  stay → `arrival`, booking → `start`, ticket → дата события.
- Сортировка доски по `when` (по возрастанию — ближайшее сверху), фолбэк
  `-created_at` там, где даты нет. `_EVENT_ORDER` расширяется на job/order/ticket.
- Шапка колонки: `count` + СУММА (один агрегат на колонку по БД, не по
  загруженным карточкам — иначе врёт при лимите).
- Бейдж срока: `Job.valid_until` → «Angebot läuft in 3 Tagen ab» / «abgelaufen».

## 4. Волна VS-3 (миграция) — п.4 «якорь + прикреплённые сделки»

Что просит владелец: у брони номера (или стола) есть прикреплённые сделки —
велопрокат, трансфер, услуга. Каждая двигается по СВОИМ колонкам и живёт в СВОЕЙ
вкладке, но на якоре видно, что к нему прикручено.

Чего сегодня нет: Extras — снимок JSON внутри брони (не сделка, не двигается);
`Job.booking` — единственная настоящая связь и только для пары job→booking.

Предложение (фундамент на все шесть kind, одна аддитивная миграция):
пара полей `anchor_kind` + `anchor_id` на сделке-спутнике (или отдельная
таблица связей — решается на этапе плана VS-3). UI:
- на карточке якоря — строка «＋ 2 Zusatzleistungen: Velo, Transfer»;
- на карточке спутника — «zu Zimmer 101 · Fam. Klein» со ссылкой на якорь;
- вкладки остаются раздельными (движение по колонкам независимое — требование
  владельца).

**Открытый вопрос (нужно решение до плана VS-3):** кто создаёт привязку —
(а) гость на витрине (выбирает велопрокат при бронировании номера → появляется
ОТДЕЛЬНАЯ сделка со своим статусом), (б) владелец в кабинете (прикрепляет
существующую сделку к брони), (в) оба. От ответа зависит объём: (а) — правки
витринных воронок всех архетипов, (б) — только кабинет.
