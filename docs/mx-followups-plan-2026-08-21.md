# MX follow-ups — план исполнения (отмашка владельца «Делай», 2026-08-21)

Четыре объявленных хвоста программы MX v1 (`mx-execution-plan-2026-08-21.md`),
порядок: **2e → 3b → 6c → кит Stadtführer**. Цикл прежний: локальные гейты →
пуш → зелёный CI → мерж в main.

## 2e — enforcement трекеров опций (БЕЗ миграций)
Новый `apps/core/option_trackers.py`:
- **pool**: продажа опции с `tracker=pool` проверяет занятость пула в окне
  ИСПОЛНЕНИЯ сделки (stay: ночи; ticket: дни события; booking: день слота) под
  `select_for_update` строки Extra (сериализация продаж опции); переполнение →
  `PoolFull` → честный отказ формы. Занятость = скан активных сделок трёх kind
  со строкой этой опции в снимке (SME-объёмы; отменённые — через реестр статусов).
- **stock**: продажа списывает Вещь (`Extra.product`) — движение
  `source="option", source_ref="<kind>:<deal>:<extra>"` СНАЧАЛА (идемпотентность
  (source, source_ref, kind) даром), счётчик — только если движение создано;
  нехватка → `OptionOutOfStock` → отказ (общий anti-oversell платформы). Отмена
  сделки возвращает: restore-движение + инкремент; двойной вызов (builtin-хук +
  зеркало кастом-статусов) идемпотентен. Партии FEFO в v1 НЕ трогаем — только
  счётчик+леджер (Вариант A: счётчик = истина, реконсиляция переживает).
- Врезки: `book_stay`/`book_ticket`/`booking.book` (в их atomic, после create);
  отмена — SM-хуки трёх kind + `status_effects.restore_stock_for`; правки MX-3
  (stays `extras_present`, booking `action=extras`) — diff-синк
  `sync_options(old, new)`; qty stock-опции v1 = 1 за сделку (per_night не
  умножает списание — объявленное упрощение).

## 3b — правка допов БИЛЕТА (БЕЗ миграций)
Зеркало MX-3: ветка `action="extras"` в `events.views.ticket_action` +

## 6c — серия/тур ОДНОЙ карточкой в листинге и агрегаторе (БЕЗ миграций)
- Листинг `/veranstaltungen/`: события одной группы (tour_id | series_id)
  сворачиваются в одну карточку (ближайший будущий заезд, бейдж «+N Termine»)
  — характеризационные замки индекса обновляются ОСОЗНАННО; фасеты/поиск целы
  (свод после фильтров, до пагинации).
- Агрегатор: `sync_event_listing` события группы обновляет ОДНУ запись
  (source_ref = группа, payload = ближайший будущий заезд); прошёл заезд →
  роллинг на следующий (существующий beat-механизм протухания).
