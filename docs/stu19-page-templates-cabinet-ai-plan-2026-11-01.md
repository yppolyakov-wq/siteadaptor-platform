# STU-19 — шаблоны страниц в кабинете + ИИ-помощник «что создать и как»

**Дата:** 2026-11-01. **Статус:** план на согласование, кода нет.
**Запрос владельца:** «в Студии оставить порядок, переименования, тексты и добавление новых;
в кабинете у каждого типа — вкладка „Шаблон страницы“ с шаблонами, сетками и т.д.» +
«сразу думай, как внедрить ИИ: пользователь пишет „создай товар/категорию“, ИИ показывает,

Независимое ревью — агент `architect` (ECC), выводы вплетены ниже.

## 2. Целевая раскладка

### 2.1 Какая настройка куда

| Ось | Куда | Примеры |
|---|---|---|
| Композиция (шаблон страницы) | Кабинет | `catalog_page_style`, `category_page_style`, `promo_page_style`, `*_page_style` листингов, `*_detail_layout`, `promo_detail_style`, `home_hero` |
| Сетка | Кабинет | `catalog_layout`, `promo_index_layout`, `service_layout`, `stay_layout`, `product_related` … |
| Карточка | Кабинет | `product_card_form`, `promo_card_form` |
| Содержимое: вывод | Кабинет | сортировка, фильтры, подкатегории, цены/маркировка меню, группировка акций, upsell корзины, ширина текста |
| Содержимое: порядок блоков | **Студия** | `home_sections`, `*_detail_sections` (порядок/видимость секций деталей) |

Карточка `home_hero` — граничный случай: это вид первого экрана главной, а не блок. Остаётся
в кабинете на экране «Seitenvorlagen → Startseite»; в Студии — сводка.

### 2.3 Вкладка «Seitenvorlage» (макет на согласование — артефакт «Seitenvorlage»)

Слева — настройки типа карточками по осям («Vorlage der Seite» · «Ausgabe» · «Kartenform» ·
«Inhalt»), плитки-мини-макеты из реестра; недоступные шаблоны видны серыми с причиной («Braucht
Unterkategorien»). Справа — **живое превью** страницы этого типа в окне без сохранения
(`?preview=1&tpl=<setting>:<value>`, механизм `?look=`/`?bundle=`), переключатель Desktop/Phone.
Внизу — «Speichern» (точечная запись) и «In der Studio ansehen →». Переопределения у отдельных
объектов — список «Eigene Vorlage bei: Kategorie Brot, Aktion Räumung» со ссылками на формы.
Сверху — строка ИИ-помощника (§4).

### 2.4 Студия после переноса

Строка страницы в панели: «Vorlage: Regale · 4 Spalten · Karte: Lookbook — **Ändern →**»
(ссылка на вкладку с якорем типа). Плитки шаблонов, селекты сетки и формы карточки из панели

## 3. Один сервис записи (фундамент)

`apps/core/page_settings.py` (новый, обобщение `studio_scope.write_value`):
- `schema(tenant, types=None)` → для каждого типа: настройки, ось, допустимые значения с
  подписями, текущее значение, источник («Standard» / «Website» / «Kategorie X»), доступность и
  причина, объектный уровень. Строится ТОЛЬКО из `studio_pages` + `compositions` + `card_forms`.
- `write(tenant, setting_code, value, obj=None)` → валидация по тому же `_valid_values`,
  блокировка строки тенанта, точечная запись одного ключа, нормализация, аудит.
- Его зовут: вкладка кабинета, «Nur hier» Студии (пока жив), формы объектов, ИИ-применение.

Замки (до переноса): (а) Save Студии **не пишет** ключи перенесённых настроек; (б) черновик
Студии их не несёт (реестр приёмника STU-18g); (в) `schema()` совпадает с реестром и разметкой
вкладки в обе стороны (образец `test_registry_and_panel_agree`); (г) встречные замки покрытия
осей STU-17 остаются.

## 4. ИИ-помощник «Was möchten Sie anlegen?»

### 4.1 Что видит владелец

Строка ввода в кабинете (на главной, в «Sortiment», на вкладке «Seitenvorlage» и в палитре
Ctrl+K). Владелец пишет: «neue Kategorie Kuchen mit Fotos», «Produkt Sauerteigbrot 4,50 €»,
«Aktionen als Prospekt zeigen». Ответ — карточка-план:

1. **Was angelegt wird** — «Kategorie „Kuchen“» (тип сущности).
2. **Welche Daten nötig sind** — поля из формы: обязательные отмечены, распознанное из фразы уже
   подставлено (название, цена), остальное — «fehlt noch» (фото, описание, категория).
3. **Wo** — кнопка «Formular öffnen» (форма создания, поля заполнены через `?entwurf=`).
4. **Welche Vorlage** — рекомендованный шаблон из ДОСТУПНЫХ сейчас (с причиной: «6 Unterkategorien →
   Regale passt»), мини-превью и «Übernehmen» (пишет через `page_settings.write`).

Ничего не создаётся и не меняется без нажатия. Отказ ИИ / ИИ выключен → тот же экран, план
строится правилами (§4.3), подпись «ohne KI».

### 4.2 Как устроено

- Задача `setup_plan` в реестре ИИ (`tier="fast"`, JSON-схема, без картинок, без PII в промпте).
- **Вход модели:** фраза владельца (как ДАННЫЕ, контракт ai0 §10) + сжатый каталог возможностей
  тенанта: список создаваемых сущностей с полями (из `ModelForm` с учётом модулей и прав) и
  `page_settings.schema()` только доступных значений. Ни данных клиентов, ни заказов.
- **Выход (enum-ы из реестра):** `intent ∈ {create_category, create_product, create_service,
  create_promotion, create_event, change_template, …}`, `fields` (только имена из списка формы,
  значения-строки), `template` (`setting ∈ коды реестра`, `value ∈ допустимые`), `reason` ≤ 140.
- **Постпроверка на сервере:** неизвестное поле/значение отбрасывается, цена парсится нашим
  `core/money.py` из ТЕКСТА владельца (модель цены не придумывает — правило Д1), шаблон
  перепроверяется гейтом доступности. Ответ модели никогда не пишется в БД напрямую.
- **Права:** план строится только из сущностей, которые этот сотрудник может создать
  (`view_perms`/`has_perm`); «Übernehmen» шаблона — только с правом на настройку сайта.
- Синхронный вызов с таймаутом (план короткий); при таймауте — правила.

### 4.3 Без ИИ (правила)

Словарь интентов по ключевым словам (de/en/ru/uk/tr: Kategorie/категория, Produkt/товар,
Aktion/акция …) + число с «€» → цена. Шаблон — первый рекомендованный из `compositions` для
текущих данных (например, есть подкатегории → «Regale»). Это же — запасной путь при ошибке ИИ и
эталон для тестов.

### 4.4 Почему ИИ можно делать сразу, а не «после»

Помощнику нужны ровно `page_settings.schema()` и список полей форм — фундамент шага 1 этого плана.
Поэтому ИИ идёт **вторым инкрементом, параллельно с вкладками**, а не в конце: он не зависит от
того, перенесены ли контролы из Студии (ссылка «Übernehmen» пишет тем же сервисом).

## 5a. STU-19d — как сделано (2026-11-01)

Вместо семи вкладок по разделам — **три экрана** (решение по ходу: в кабинете X4 услуги,
номера, события и туры уже живут в «Sortiment» как сущности, отдельные вкладки дублировали бы
меню):
- **Sortiment → Seitenvorlage** — каталог, категория, товар, наборы, лукбук, Merkzettel,
  Finder, корзина, услуги, номера, события, туры (видны только типы включённых модулей);
- **Marketing → Aktionen → Seitenvorlage** — обзор, группа, одна акция;
- **Website → Seitenvorlagen** — все 30 типов (главная, текстовые страницы, блог и т. д.).

`page_settings` знает все 46 настроек (кроме порядка блоков `*_sections`): шаблоны листингов
в `page_styles`, «необязательные» сетки (Standard = ключ снят), сортировки из провайдеров
фасетов, вид детали четырёх видов, баннер, ширина текста, группировка акций, upsell корзины,
форма карточки акции. Тип страницы показывается только при включённом модуле
(`TYPE_MODULES`). Экран пишет только настройки своих типов. Все витринные вьюхи читают конфиг
через `page_settings.raw_config(request)` — превью `?tpl=` работает на всех страницах (раньше
туры, блог, наборы, Merkzettel, лукбук и отзывы не видели даже черновик Студии).

## 5b. STU-19e — план (замер 2026-11-01, до кода)

Ось «композиция» — 19 настроек: `home_hero`, `catalog_page_style`, `category_page_style`,
`product_detail_layout`, `promo_page_style`, `promo_group_style`, `promo_detail_style`,
девять `*_page_style` листингов, `service/stay/event_detail_layout`.

**Что меняется.** В панели Студии строки этих настроек остаются (замок
`test_registry_and_panel_agree`: реестр знает — панель показывает), но вместо плиток —
**сводка**: «Vorlage: <подпись> — Ändern →» со ссылкой на нужный экран кабинета (`?typ=`).
Пилюли «Nur hier» у трёх настроек уходят вместе с плитками: «только эта категория/акция»
задаётся в форме объекта (поля `Category.page_style`, `Promotion.page_style` уже там),
«только этот тип акций» — на экране «Aktionstypen». `CABINET_OWNED` получает эти 19 кодов:
Save Студии и её черновик берут их значения из БД (`protect_owned` уже подключён).

**Цена — замки.** Сейчас поля этих настроек шлёт и ждёт сохранёнными ~25 тестовых
файлов (`hero_style` — 9, `ed_layout`/`pd_layout` — 6, `*_page_style` — 10, live-draft
STU-18g). Это поведение Студии, которое снимается НАМЕРЕННО: каждый такой ассерт
переписывается на `page_settings.write` (кабинет) + отдельный замок «Save Студии больше
не меняет ключ, даже если поле пришло в POST». Переписывать по одному файлу, без
массовой замены. Сид демо-китов и мастер (`apply_bundle`/`apply_look`) пишут эти ключи
мимо Студии — их не трогаем.

**Риски.** (1) `hero_style` пишется Save'ом безусловно (views.py ~2829) — без
`protect_owned` первый же Save сбросил бы баннер в «plain»; замок обязателен.
(2) Живое превью Студии для этих осей пропадает — проверка вида теперь в превью кабинета.
(3) Стенд: открыть Студию, сохранить блок → шаблоны страниц не изменились.

**Порядок.** 19e-1 ✅ листинги+детали (13 кодов, нет «Nur hier»), 19e-2 ✅ каталог/категория/
акции (с пилюлями), 19e-3 ✅ баннер главной (`home_hero` в `CABINET_OWNED`). Каждый — свой коммит и прогон CI.

## 5c. STU-19f — план (замер 2026-11-01, до кода)

Ось «сетка» — 12 настроек `_LAYOUT_KEYS` (каталог, похожие товары, услуги, номера,
события, обзор/группа акций, наборы, туры, лукбук, отзывы, Merkzettel, блог). Секции
главной (`sections[*].layout`) остаются в Студии — это вид блока, не шаблон страницы.

**Главный риск — потеря возможностей.** В Студии у каждой сетки есть не только пресет
колонок, но и «тип вывода» (`_output_axis.html`): Raster/Slider, ряды, «pro Seite»
(каталог и акции), последняя строка, темп ленты. Кабинет сегодня пишет ТОЛЬКО пресет.
Снять контролы из Студии до того, как кабинет умеет всё это, = отнять у владельца
настройки. Поэтому порядок:

- **19f-1 (кабинет умеет всю сетку).** `page_settings.write(..., output=)` — для
  layout-настроек вторым аргументом приходит тип вывода (mode/rows/page_size/speed/tail),
  разбор — та же функция, что у Студии (`_page_layout_payload` переезжает в
  `page_settings.output_payload`, Студия зовёт её же), клампы — `normalize_layout`.
  Пустое поле = ключ снят (presence-minimal, как в Студии). `SettingState` несёт
  нормализованную раскладку и признак пагинации; экран кабинета рисует под плитками
  блок «Ausgabe» (Raster/Slider · Reihen · Pro Seite · Letzte Reihe · Tempo; ряды и темп
  видны только там, где действуют — то же правило, что в Студии). Стиль — детали `ui-*`.
- **19f-2 (Студия — сводка).** 12 строк сетки в панели → `_stu19_summary.html`
  («Raster: 4 pro Reihe · Slider»); `CABINET_OWNED` += 12 кодов; поля `*_preset` и
  `*_mode/_rows/…` уходят из payload черновика; `retires_legacy_promo_layout` в Save
  Студии больше не срабатывает (поле не приходит) — легаси-лента снимается кабинетом
  (`apply_override` уже делает это). Замки, ждущие запись сетки Студией, переписываются
  осознанно по одному файлу.
- **19f-3 «карточка»** (`product_card_form`, `promo_card_form`) и **19f-4 «содержимое»**
  (сортировки, фильтры/подкатегории каталога, цены/маркировка меню, группировка акций,
  upsell корзины, ширина текста) — той же схемой; у формы карточки есть уровень объекта
  (поле `card_style` у товара/категории/акции) — «только здесь» уходит в формы объектов,
  как у шаблонов в 19e-2.

**Известное ограничение v1.** Живое превью кабинета (`?tpl=`) показывает выбор плитки;
изменения «Ausgabe» видны после «Speichern» (превью перезагружается).

## 6. Риски

1. **Потеря выбора при Save Студии** (W0/W6): удалить поле, но оставить запись ключа → Save
   обнулит выбор из кабинета; оставить hidden-копию → перезапишет устаревшим. Лечится замком (а)+(б)
   и удалением поля вместе с записью.
2. **Разные валидаторы у двух экранов** (прецедент STU-15) → один `page_settings.write`.
3. **Устаревший черновик** перекроет свежее значение в превью → черновик не несёт перенесённые ключи.
4. **Обещание без исполнения** (STU-9/17) → вкладка показывает ось, только если разметка типа её
   читает; встречные замки покрытия.
5. **ИИ придумывает поля/цены/шаблоны** → закрытые enum-ы из реестра + постпроверка + цена только
   из текста владельца; ничего не применяется без клика.
6. **Находимость** (владелец не найдёт, куда уехало) → сводка в Студии со ссылкой, вход в
   Ctrl+K, сценарий владельца на стенде.

## 7. ECC-прогоны

- **До кода:** скиллы `django-patterns`, `django-tdd`, `django-security`, `accessibility`
  (вкладка — новые UI-элементы), `e2e-testing` (превью и канва — JS).
- **После плана:** `architect` — ревью сделано (2026-11-01); `planner` — разбивка STU-19a/b на
  файлы перед кодом.
- **В цикле:** `django-reviewer` — каждый инкремент; `security-reviewer` — 19a (запись настроек,
  права), 19c/19g (ввод владельца → модель, постпроверка); `silent-failure-hunter` — 19c (ошибки
  ИИ и запасной путь); `a11y-architect` — 19b; `e2e-runner`/Playwright — 19b, 19e–19h.
- **До мержа каждого инкремента:** `ruff check` + `ruff format --check .` + pytest затронутых
  модулей + `i18n_quickcheck` + `template_comments` + `npm run build:css` при новых классах.
