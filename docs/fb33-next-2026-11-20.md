- **Деплой: блокировка и чистка (стопка 7), с какого деплоя что действует.** Деплой командой `git pull origin main && ./scripts/deploy.sh single` — ПЕРВЫЙ раз уже новым сценарием: блокировка миграций, flock и чистка образов действуют сразу. Деплой одной командой `./scripts/deploy.sh single` (без предварительного pull) или через ssh-однострочник — ПЕРВЫЙ раз работает старый сценарий (его pull подменяет файл уже под работающим bash): без блокировки, flock и чистки; пересев в этот раз запускать только после конца деплоя. СО ВТОРОГО деплоя — новый сценарий в любом варианте запуска. Рекомендация на первый раз — именно `git pull origin main && ./scripts/deploy.sh single`.
- **Деплой и пересев демо (стопка 7):** шаг миграций ждёт блокировку до 15 мин (`OPS_LOCK_TIMEOUT=900`), затем останавливается с сообщением «Блокировка операций над схемами занята … (seed_demo_tenants)»: схемы не тронуты, сервисы на прежней версии, образ уже собран. Дождаться пересева и запустить деплой снова; дольше ждать — `OPS_LOCK_TIMEOUT=3600 ./scripts/deploy.sh single`. Пересев во время миграций деплоя ждёт до 15 мин, затем код 1 (дольше — `seed_demo_tenants … --lock-timeout 3600`). Второй деплой, пока идёт первый, сразу выходит «Другой деплой уже идёт» (лок-файл `.git/siteadaptor-deploy.lock`, снимается сам). Блокировка покрывает три шага миграций (shared, tenant, повтор по одной схеме); между шагами она отпускается — пересев может вклиниться между «shared» и «tenant», тогда шаг tenant его дождётся.
- **Чистка образов (стопка 7):** первая чистка (со второго деплоя) снимет теги `siteadaptor-app:<sha>` старше пяти последних — освободится заметно места; откат остаётся на 5 последних коммитах (`IMAGE_KEEP=10 ./scripts/deploy.sh single` — оставить больше). Кэш сборки старше 72 ч удаляется: если деплоев не было трое суток, сборка пойдёт без кэша (дольше на минуты). Тома (БД, media) и контейнеры чистка не трогает.

## 4. Как работать (уроки этих сессий — держать)
- **Параллельные срезы — в отдельных git worktree** (Agent `isolation: worktree`), у каждого своя тест-БД:
  `DB_NAME=platform_<срез> uv run pytest … --reuse-db` (после новых миграций в main — `--create-db`).
  Два pytest на одной БД не запускать.
- **`.mo` не в git, gettext нет локально**: в свежем worktree/контейнере компилировать `.po`→`.mo` через
  polib (`uv run --no-project --with polib python -c "…"`), иначе снимки не на de падают ложно. Эталоны
  не на немецком снимать только со свежими `.mo` (pitfalls §4).
- **Стенд окна блока** — `scripts/fb33_m3_window_stand.py` (инструкция в шапке; тенант `ptx` —
  `scripts/text_pages_stand.py --setup`; сервер `--settings=config.settings.stand`, без debug-toolbar;
  Playwright — `uv run --no-project --with playwright`). Перед правкой стенд гонять тоже.
- **Стопка срезов (опыт 2026-11-20):** параллельные срезы от одной базы — общие доки не правят (заметки
  в scratchpad, сводит координатор), новые msgid ставят после своей записи-якоря в `.po` (якоря
  снимаются на верхушке), `app.css` и общие эталоны окна (`golden_fb33m3/page_nojs`, `panel.json`)
  не коммитят — пересборка и пересъёмка один раз на верхушке со сверкой списка изменившихся случаев.
  Стыки срезов (чужой реестр, новая плитка) — отдельным коммитом на верхушке с тестами.
- **Force-push запрещён**: после rebase уже запушенной ветки — пуш под новым именем (`…-2`) и
  переименовать локальную ветку так же (иначе Stop-хук считает коммиты неотправленными).
- **Когда main ушёл вперёд** — сообщить всем работающим срезам: `git fetch && git rebase origin/main`.
- Нестабильные при `-n 4`: `test_migration_state`, `test_async_signup::test_provision_creates_schema_owner_and_emails`
  — отдельно проходят; при падении перепроверить файл отдельно.
- Ревьюер, которому нужен код ветки, — `git show/diff` (не `checkout` в главной папке); если не видит —
  выгрузить дифф и шаблоны в scratchpad файлами.
- Хуки: pre-commit (ruff, format, i18n) блокирует; Stop-хук требует пуша — незаконченную работу
  исполнителя не коммитить за него, а объяснить.
