# План: владелец наполняет богатую карточку услуги (attributes + FAQ)

Закрывает пункт, выявленный при i18n-волне 2026-08-01: поля `Service.attributes`
и `Service.faq` завёл UA4-3, витрина их рисует (секции «Details» и FAQ детали
услуги), но **в кабинете их негде заполнить** — они появляются только у демо-китов.
Реальный владелец услугового архетипа (A3 Friseur, A7 Handwerker, A9 Werkstatt,
спа-услуги отеля) видит на демо богатую карточку и не может повторить её у себя.

## 1. Что есть сегодня

* Форма услуги — **не ModelForm**, а простые POST-формы в `services_view`
  (`action=create|update`, presence-guard'ы на чекбоксах, `_int`-клампы).
* На чтении поля нормализуются: `attributes_list` (≤12 строк по 200 симв.),
  `faq_list` (≤12 пар `{q,a}`; `q` обязателен, `a` до 1000). Мусор молча
  выбрасывается — форма может отдавать что угодно, витрина не сломается.
* Секция витрины видна по базовому списку (`bool(service.attributes_list)`),
  переводы — оверлеями `attributes_i18n`/`faq_i18n` с выравниванием по индексу
  нормализованного базового списка (`apps/core/i18n_seq.py`).

## 2. Ввод

Обе секции — в свёрнутом `<details>` на карточке услуги, чтобы не раздувать
строку списка (форма уже плотная: фото, описание, переводы, длительность, цена).

**Details (`attributes`) — одна textarea, пункт на строку.** Это самый дешёвый
для владельца ввод и он естественно ложится на «список строк». Парсер:
`splitlines` → `strip` → отбросить пустые → тот же нормализатор.

**FAQ (`faq`) — пары полей, а не текст.** Разделитель внутри свободного текста
(`Q | A`, «строка вопрос / строка ответ») ломается на первом же ответе с
переносом или вертикальной чертой. Рендерим N существующих пар + одну пустую;
сбор — по индексам `faq_q_<i>` / `faq_a_<i>`, пара с пустым вопросом
отбрасывается (то есть очистка вопроса = удаление пункта). Слоты дорастают
после Save — тот же приём, что в редакторе Finder (FD-3), без JS.

**Presence-guard (обязателен, инвариант W0/LS-1).** Оба блока пишутся ТОЛЬКО
при сентинелах `attributes_present` / `faq_present`. Иначе любой клиент формы
без этих полей (а `action=update` шлётся и из компактной строки списка) молча
стирал бы наполнение.

## 3. Переводы

* `attributes` — textarea на локаль (`attributes_<loc>`), строки выравниваются
  по индексу базовой textarea. Инвариант уже задокументирован в `i18n_seq`:
  база задаёт длину, пустая строка = фолбэк. В подписи явно сказать «строка к
  строке», иначе владелец не поймёт связь.
* `faq` — пары `faq_q_<i>_<loc>` / `faq_a_<i>_<loc>` под каждой базовой парой,
  внутри общего `<details>🌐 Translations` карточки.
* Тенант с одной локалью не видит ничего нового (`extra_locales` → `[]`).

Сбор — новый хелпер рядом с `apply_i18n_overlay`, чтобы не размазывать
семантику оверлеев по вьюхам: `apply_i18n_seq_overlay(obj, post, tenant, …)`.

## 4. Границы

* Числа пунктов/пар не ограничиваем в форме — режет нормализатор (≤12), но в
  подсказке об этом сказать, иначе 13-й пункт исчезнет молча.
* Аналогичные поля у `StayUnit`/`Event` — **вне объёма**: там богатой карточки
  такого вида нет, добавлять модель ради симметрии не надо.
* Порядок пунктов — как введён; drag-сортировка не нужна (textarea = порядок).
