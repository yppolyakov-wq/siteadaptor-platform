## 2. Правила исполнения
- Базовый msgid — как в файле (в проекте смешаны немецкие и английские msgid;
  НЕ переписываем msgid ради единообразия — это оторвёт существующие переводы).
- Каждая волна: обернуть → добавить msgid во ВСЕ 5 `.po` (en/tr/ru/uk/de; для de
  msgstr = msgid, если msgid немецкий) → локальные гейты → CI → merge.
- `gettext_lazy` в реестрах/choices (импортируются на старте), `gettext` во вьюхах.
- Ловушка: lazy-строка в JSON `site_config` не сериализуется — в реестрах, чьи
  значения ПИШУТСЯ в site_config, оборачивать только UI-метки, не хранимые значения.
- Ловушка: golden-тесты normalize сравнивают строки — проверять после каждой волны.
- `%` в `{% trans %}` НЕ удваивать (Django не делает %-интерполяцию в trans без
  переменных) — иначе на экране `%%`.

### Почему I18N-7 отложен
Это не UI, а ДОКУМЕНТЫ: счета (`finance/pdf.py`), сметы (`jobs/pdf.py`), накладные
(`orders/pdf.py`), билеты (`events/memo.py`), постеры (`promotions/poster.py`).
Развилка, которую нельзя решить за владельца:
1. **Язык документа = язык клиента** (турецкий гость получает счёт по-турецки) —
   удобно, но для DACH счёт/Rechnung обычно оформляется по-немецки, а DATEV-экспорт
   имеет фиксированные немецкие заголовки (их переводить НЕЛЬЗЯ — сломается импорт
   в бухгалтерию).
2. **Язык документа = язык бизнеса** (всегда немецкий) — юридически безопасно,
   но иностранный клиент не понимает счёт.
3. **Гибрид**: маркетинговое (постер, билет, memo) — на языке клиента; финансовое
   (Rechnung, DATEV, Widerrufsbelehrung) — на языке бизнеса.
Рекомендация: вариант 3. Требуется явное «да» владельца до кода.

### Правило для новых строк
Любая новая видимая строка добавляется СРАЗУ во все 5 `.po` (`de` включительно;
для немецкого msgid — `msgstr = msgid`). Локально после правки `.po` обязательно
`msgfmt -o …django.mo …django.po` по всем локалям — иначе переводы в тестах не
активны и класс «замок пинит сырой литерал» всплывёт только на CI.
