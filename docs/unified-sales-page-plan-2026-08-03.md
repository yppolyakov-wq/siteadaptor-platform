# План-док: единая страница продаж (Verkäufe) — секции по типам сущностей (2026-08-03)

Запрос владельца: у отеля три типа продаваемых сущностей — номера, услуги, товары.
Все — на ОДНОЙ странице продаж, раздельными секциями; брони номеров — основное и
видны всегда, услуги/товары — только если по ним есть продажи. Порядок: календарь
броней номеров → календарь броней услуг → заказы магазина. В каждой секции —
переключатель видов: номера и услуги: календарь ∥ канбан ∥ список; товары:
канбан ∥ список. Затем — примерить ту же модель на остальные архетипы, с оглядкой
на популярные рыночные решения. СТАТУС: обсуждение с владельцем, код не начат.

## 1. Рыночные паттерны по архетипам (что считают «нормой» лидеры ниш)

Сводка по классам инструментов, на которые ровняются владельцы малого бизнеса
DACH. Это паттерны взаимодействия (стабильные годами), не свежие фичи конкретных
продуктов.

| Архетип | Референсы рынка | Главный вид продаж | Вторичные виды | Канбан? |
|---|---|---|---|---|
| Отель/Pension (A5, retreat) | TravelLine, Cloudbeds, Little Hotelier, Smoobu, MEWS | **Tape chart / Belegungsplan** (комнаты × даты) — безальтернативный центр | Списки заездов/выездов (стойка), список броней | В PMS канбана нет; ближайшее — housekeeping-доска (dirty→clean) и пайплайн групповых заявок |

| Магазин/бутик/онлайн (A1, mode, online_shop) | Shopify, Lightspeed | **Список заказов** со статусами/фильтрами | Экспорт, поиск | Shopify канбана не даёт; для Click&Reserve («In der Anprobe») канбан полезен |

| Werkstatt (A9) | Werkstattplaner, авто-СТО-софт | **Календарь термИнов приёмки** + доска статусов машин (angenommen→in Arbeit→abholbereit) | Список | Да, доска статусов машин — стандарт (физическая доска оцифрована) |
| События/туры (A6, tours) | Eventbrite, Pretix, Bookingkit, Regiondo | **Календарь дат/выездов** + список участников на дату | Список продаж билетов | Нет |
| Aktionsmarkt (акции+резервы) | — (наш формат) | Список резервов с окнами выдачи | — | Очередь выдачи — как C&C |

Выводы из рынка:
1. **Владелец прав по отелю**: Belegungsplan первым и всегда — это норма PMS;
   услуги и магазин у отелей — «допродажи», их прячут, пока их нет.
2. **Канбан — не универсален**: для booking-архетипов (салон/ресторан) рынок его
   не использует (календарь королевствует), а для jobs (Handwerker) канбан —
   наоборот ГЛАВНЫЙ вид. Значит, дефолтный вид секции обязан зависеть от
   архетипа, а не от kind.
3. **Календарь для ТОВАРОВ — рыночная ниша, которую владелец не заказывал, но
   которая есть в DACH-традиции**: пекарни/кондитерские живут «книгой заказов по
   дням выдачи» (Auftragsbuch). Если у заказа есть время выдачи — календарь по
   дате выдачи полезен. Предлагаю как ОПЦИЮ (вид появляется, только если у
   тенанта есть заказы с датой выдачи), не как дефолт.

### 2.2 Ключевые факты текущего устройства
- «Verkäufe» отеля сегодня — это НЕ страница, а навигация: сайдбар/плитка ведут на
  `stays:calendar` (Belegungsplan), сегмент ST-5b переключает СТРАНИЦЫ
  (`board` ⇄ `stays:calendar` ⇄ `booking:calendar` ⇄ `orders:order-list`), у отеля
  с booking сегмент = «🧮 Board | 📅 Kalender | 📅 Termine | ＋ Buchung».
- Ключ `orders_view` из site_config УДАЛЁН фидбэком 2026-07-28 — сегмент без
  персиста, маппинг фиксирован по архетипу (`siteconfig.py:2203` дропает легаси).
- Канбан умеет все три нужных kind уже сейчас; «Board» у отеля = вкладки
  stay/booking по активным модулям.
- KDS-кухня (`orders/views.py:105-165`) — отдельный полу-канбан, не трогаем (D2).

### 2.3 Чего НЕТ (дельта до требования владельца)
1. **Единой страницы-стека нет** — 4-5 отдельных страниц, связанных сегментом;
   маршрута `/dashboard/verkaeufe/` не существует.
2. **Per-kind переключателя видов нет** — сегмент один на хаб и меняет страницы,
   не вид внутри секции.
3. **«Списка» для номеров и услуг нет** — `feed` умеет только orders; ближайшее:
   `stays:today` (заезды/выезды), поиск `?q=` на календаре, однодневный список
   booking. Отдельной «Liste броней/записей» нет — надо строить (дёшево: тот же
   queryset календаря, плоской таблицей).
4. **Гейтинга «секция при наличии продаж» нет** — `manage_sections_for`
   сознательно показывает пустые вкладки; единственный прецедент exists-гейта —
   `sellable_manage`.
5. **Календаря заказов нет** (только KDS).
6. **Belegungsplan не партиал** — разметка + ~160 строк JS в
   `templates/stays/calendar.html:74-335`, JS завязан на глобальный
   `#belegungsplan` и document-слушатели → для встраивания нужно извлечение в
   партиал (иначе конфликт селекторов при двух календарях на странице).
7. **Booking-«календарь» — на деле список одного дня** (`booking/views.py:72-108`),
   не сетка. Для секции «календарь броней услуг» это уже приемлемый вид дня, но
   надо честно назвать это Tagesplan (недельная сетка — отдельная работа).
8. **classic_ui** — новая страница обязана иметь классический фолбэк (правило ST).

## 3. Предлагаемое решение (на обсуждение)

### 3.1 Страница
`/dashboard/verkaeufe/` — одна страница, СТЕК секций (не вкладки):
каждая секция = заголовок + счётчик + переключатель видов + встроенный вид +
ссылка «Vollansicht» на полную страницу. Секции сворачиваемые (details/summary,
состояние в localStorage), ниже первого экрана — ленивые (`?box=`-фрагменты, как
селектор столов ресторана).

### 3.2 Состав и порядок секций
Порядок = приоритет архетипа (реестр `_PRIORITY`), у отеля: stay → booking →
order. Правило видимости секции:
- kind primary-модуля — ВСЕГДА (пустой — с CTA «настроить/создать»);
- прочие kind — модуль активен И существует хотя бы одна сделка (`exists()`,
  батч-запрос на страницу);
- ручной оверрайд в настройках не делаем в v1 (обсудить).

### 3.3 Виды в секции (переключатель per-kind, запоминается)
| kind | виды | дефолт (по архетипу) |
|---|---|---|
| stay (номера) | Kalender (Belegungsplan) ∥ Board ∥ Liste | Kalender |
| booking (услуги) | Kalender ∥ Board ∥ Liste | Kalender (салон/отель); Board — нет на рынке, но оставляем как опцию |
| order (товары) | Board ∥ Liste (+ Kalender по дате выдачи — опция, см. §1.3) | retail: Liste; гастро-C&C: Board |
| job (заявки) | Board ∥ Liste (+ Kalender термИнов — v2) | Board (рыночная норма Handwerker) |
| ticket (билеты) | Liste ∥ Kalender дат | Kalender |

Хранение: расширить ключ `orders_view` (ST-5b) до `{kind: view}`
(presence-minimal в normalize; плоское старое значение = легаси-маппинг).

### 3.4 Сборка из существующего (без переписывания движков)
- **Канбан секции** = `manage_sections_for` c фильтром по одному kind +
  `_kanban_board.html` (партиал уже двухстраничный — главная кабинета его
  встраивает; DnD-скрипт `_board_body.html` сделать однократным на страницу).
- **Календарь номеров** = извлечь тело Belegungsplan из
  `templates/stays/calendar.html` в партиал `stays/_belegungsplan.html`
  (рендер 1:1, страница `stays:calendar` становится обёрткой — паттерн B1
  `_board_body`); JS скоупить контейнером, не document (готовим к соседству
  двух календарей на странице).
- **Календарь услуг** = текущий однодневный Tagesplan booking партиалом
  (тот же queryset), честно называем «Tagesplan».
- **Списки stay/booking** (новых страниц нет) = плоская таблица по queryset'ам
  календарей: гость/даты/статус/сумма + `status_actions` (тег уже есть) —
  дёшево и закрывает «Liste» из требования.
- **Список заказов** = слим-вариант `orders/order_list.html` партиалом.
- **Гейт «есть продажи»** = батч `exists()` по kind (паттерн
  `sellable_manage`, но без материализации).
- **Ленивая подгрузка** вторичных секций = `?box=`-фрагменты (паттерн
  ресторана/карточки брони).
- **Переключатель вида в секции** = новый лёгкий сегмент per-kind (шаблон
  `_orders_view_switch.html` как образец разметки), выбор — НОВЫЙ ключ
  `sales_views: {kind: view}` в site_config (presence-minimal; НЕ путать с
  удалённым легаси `orders_view` — тот дропается normalize'ом и остаётся
  дропаемым).
- **classic_ui** → прежнее поведение: «Verkäufe» ведёт на отдельные страницы,
  новая страница не подключается (замок).

### 3.5 Другие архетипы — та же страница
Секционная модель универсальна: у салона первой стоит секция booking-календаря,
у Handwerker — job-канбан, у магазина — order-список; «допродажные» kind
подключаются сами при первой продаже. Это закрывает и вопрос находимости
(«где мои продажи?» — всегда один ответ: Verkäufe).
