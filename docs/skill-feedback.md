# Журнал находок: чему учатся проектные скиллы (T-13.7)

Проектные скиллы `.claude/skills/sa-*` сами себя не меняют и прошлых сессий не помнят.
Учатся они через этот журнал: каждая находка ревью, CI, стенда или владельца — одна строка
здесь, в том же коммите, что и правка по находке.

## Правила

1. **Строка на находку**, а не на коммит. Колонка «Когда» — где находку поймали: `план`
   (чеклист или ревью плана, до кода — так и задумано), `дифф` (ревью, CI или стенд после
   кода), `после мержа` (нашёл владелец или прод — самое дорогое). Колонка «Скилл покрывал?» —
   одно из трёх:
   - `нет правила` → дописать строку в скилл (в том же коммите);
   - `правило неверное` → исправить скилл;
   - `было, не сработало` → текст НЕ дописывать: превратить в замок или хук (текст, не
     сработавший один раз, не сработает и во второй). Имя замка — в колонку «Что сделано».
2. **Скилл ≤ 200 строк.** Новое правило вытесняет наименее полезное. У каждой грабли в
   скилле — дата последнего срабатывания (`· посл. 2026-11-21`); два месяца без срабатываний
   → удалить или убедиться, что её держит замок.
3. **Ретро раз в стопку** (шаг скилла `sa-increment`): снимок командой
   `uv run python scripts/dev_stats.py --snapshot "<стопка>" --range origin/main..HEAD --red-ci N`
   — строка в `docs/dev-stats-history.md` (коммиты, доля правок ревью, находки по «Когда»,
   красные CI); в таблицу «Тренд» ниже — какие классы повторились и что поправлено в скиллах.
   **Судить по трём числам вместе** (одну долю можно «улучшить», реже запуская ревью): доля
   правок ревью на шаг (база 30 %, цель устойчиво < 20 %); находок `план` больше, чем `дифф`;
   `после мержа` не растёт. Вывод «работает / нет» — не раньше 3–4 стопок.
4. **Раз в месяц:** шаги, где скилл по теме не был загружен, → править его `description`;
   правила, не сработавшие ни разу за 5 стопок, → удалить.
5. Скилл не был загружен вовсе — в колонке «Скилл» писать `—` (это тоже сигнал: описание
   скилла не привело к загрузке).
