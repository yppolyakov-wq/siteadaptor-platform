# Журнал находок: чему учатся проектные скиллы (T-13.7)

Проектные скиллы `.claude/skills/sa-*` сами себя не меняют и прошлых сессий не помнят.
Учатся они через этот журнал: каждая находка ревью, CI, стенда или владельца — одна строка
здесь, в том же коммите, что и правка по находке.

## Правила

1. **Строка на находку**, а не на коммит. Колонка «Когда» — где находку поймали: `план`
   (чеклист или ревью плана, до кода — так и задумано), `дифф` (ревью, CI или стенд после
   кода), `после мержа` (нашёл владелец или прод — самое дорогое). Колонка «Скилл покрывал?» —
   одно из трёх:
   - `нет правила` → дописать строку в скилл (в том же коммите);
   - `правило неверное` → исправить скилл;
   - `было, не сработало` → текст НЕ дописывать: превратить в замок или хук (текст, не
     сработавший один раз, не сработает и во второй). Имя замка — в колонку «Что сделано».
2. **Скилл ≤ 200 строк.** Новое правило вытесняет наименее полезное. У каждой грабли в
   скилле — дата последнего срабатывания (`· посл. 2026-11-21`); два месяца без срабатываний
   → удалить или убедиться, что её держит замок.
3. **Ретро раз в стопку** (шаг скилла `sa-increment`): снимок командой
   `uv run python scripts/dev_stats.py --snapshot "<стопка>" --range origin/main..HEAD --red-ci N`
   — строка в `docs/dev-stats-history.md` (коммиты, доля правок ревью, находки по «Когда»,
   красные CI); в таблицу «Тренд» ниже — какие классы повторились и что поправлено в скиллах.
   **Судить по трём числам вместе** (одну долю можно «улучшить», реже запуская ревью): доля
   правок ревью ПОСЛЕ кода (база 28 % по пересчёту T-13.8b, цель устойчиво < 20 %; план и его ревью считаются отдельно); находок `план` больше, чем `дифф`;
   `после мержа` не растёт. Вывод «работает / нет» — не раньше 3–4 стопок.
4. **Раз в месяц:** шаги, где скилл по теме не был загружен, → править его `description`;
   правила, не сработавшие ни разу за 5 стопок, → удалить.
5. Скилл не был загружен вовсе — в колонке «Скилл» писать `—` (это тоже сигнал: описание
   скилла не привело к загрузке).

## Расход токенов: куда уходит (T-16, 2026-11-24)

Источник — запись расхода самой сессии (событие `result`: `total_cost_usd`, `modelUsage` по моделям; цены
прайс-листа). Ревьюеры ECC закреплены за моделью Sonnet, поэтому их расход виден отдельной строкой.

| Сессия | Всего, $ | Ревьюеры (Sonnet) | Основная модель: координатор, исполнители, планировщик |
|---|---|---|---|
| Стопка 11 (22 агента: 13 ревьюеров, 5 исполнителей) | 139 | 3,1 — 2 % | 136 — 98 % |
| Стопка 12 | 208 | 2,3 — 1 % | 206 — 99 % |
| Стопка 13 на 13:02 UTC, не закончена (26 агентов: 21 ревьюер, 4 исполнителя, архитектор) | 178 | 8,1 — 4,5 % | 170 — 95,5 % |

Стопка 13 по виду расхода (цены за токен подобраны по двум ходам стопки 11, сумма сходится с фактической в
пределах 1 %; деление «координатор / агенты» — оценка по виду кэша: у координатора часовой, у агентов 5 минут):
запись контекста агентов в кэш 16,9 млн токенов — ≈ $84 (47 %); чтение контекста 322 млн — ≈ $66 (37 %);
написанный текст и код 0,9 млн — ≈ $17 (10 %); контекст координатора — ≈ $4 (2 %).
Итого исполнители и архитектор — ≈ 80 %, координатор — ≈ 11–18 %, ревьюеры — 4,5 %.

Вывод: дорог не ревьюер, а исполнитель с большим контекстом, которого будят после паузы дольше 5 минут
(ожидание тестов, круг правок после ревью). Правила — `sa-increment`, раздел «Расход»; гейт — `preflight.py --slice`.

**Как снять расход своей сессии для снимка:** инструментом `list_events` своей сессии с `kinds: ["result"]`
взять последнюю запись: `total_cost_usd` — сумма; доля агентов ≈ (сумма − расход координатора) / сумма, где
расход координатора оценивается по его модели за вычетом 5-минутных записей кэша. Если не получается оценить —
писать только сумму и расход модели ревьюеров.

**Проверка на стопке 14:** те же числа после правил T-16. Ожидание — доля записи в кэш заметно ниже 47 %;
контроль — находки журнала по диффу не растут (если растут — мягкие правила про свежего исполнителя и малый
контекст откатываем).
