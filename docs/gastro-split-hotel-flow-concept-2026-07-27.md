# Концепт: гастро-сплит главной · переработка брони отеля · Belegungsplan кабинета

Дата: 2026-07-27. Статус: НА ОБСУЖДЕНИИ с владельцем (запрос из чата). Три темы,
каждая опирается на код-разведку (3 Explore-агента) + рыночный анализ
(booking-движки и малоотельные PMS). Развилки — §4. Код НЕ начат.

## 1. Гастро (кафе/ресторан): сплит первого экрана на 2-3 входа

**Как сейчас.** Шаблон `gastro` = hero(accent) → products → promotions → contact;
у hero — ровно ОДИН авто-CTA (primary_item). У кафе/ресторана бронь стола уже
работает в 2 клика (`/termin/` при одном столе-ресурсе сразу редиректит в выбор
времени), «Speisekarte» = каталог `/sortiment/`, «акция дня с остатком» есть в
движке (Promotion.available_quantity = живой остаток, recurrence="daily" =
акция дня; партиал scarcity «Nur noch N übrig» готов).

**Предложение (вариант A, рекомендую): `hero_widget="gastro"`** — по образцу
отеля (date-search в баннере) и friseur (услуги в баннере): в hero — 2-3 большие
плитки-входа:
- 🍽 **Tisch reservieren** → `/termin/` (уже 2 клика до слота);
- 📖 **Speisekarte** → `/sortiment/`;
- 🔥 **Angebot des Tages** → живая карточка акции: название, цена/скидка,
  «Nur noch N übrig» (scarcity) и/или countdown → клик на деталь акции.
  Нет активной акции → плитки две (fail-safe).
Точки врезки готовы: if/elif в `_hero_widget.html`, whitelist
`normalize_site_defaults` (+ Look-preserve кортеж `sitetemplates.py:329` — иначе
смена Look молча сбросит), `site_defaults` у шаблона gastro + демо cafe/restaurant.
Без миграций. Секции ниже hero остаются (продукты/акции) — плитки это НАВИГАЦИЯ,
не замена контента.

Альтернатива (вариант B): полноэкранный сплит-лендинг вместо секционной главной —
радикальнее, ломает архитектуру секций/билдера, не рекомендую в v1.

Выбор «акции дня»: v1 авто (активная с recurrence=daily первой, иначе ближайшая
по ends_at); v2 — явный выбор владельца в кабинете (по спросу).

## 2. Отель: переработка формы наличия и флоу брони (гость)

**Честный диагноз по коду (подтверждён разведкой):**
1. **Тройной ввод дат**: hero → листинг → деталь несут ОДНУ И ТУ ЖЕ форму
   von/bis/erw/kinder; на детали она рендерится даже когда даты уже пришли в URL.
2. **Календарь на детали не ведёт выбор** — клики лишь заполняют date-инпуты и
   сабмитят GET с полной перезагрузкой; нет подсветки диапазона, нет цены.
3. **«Свободно» календаря слабее «доступно» брони** — month_availability не знает
   min_nights/гостей → зелёный диапазон может вернуться янтарным отказом.
4. **Тарифы невидимы до дат**, потом сразу 4 абсолютные суммы; гость видит 3
   разные цифры (база/ночь, «ab total», суммы тарифов) за два клика; молчаливый
   фолбэк на первый тариф при игноре радио.
5. Деталь несёт 4 работы сразу: выбор дат + календарь + тарифы + данные гостя.

**Рынок:** дата-first (Booking/Airbnb/движки для малых отелей: Cloudbeds,
Little Hotelier); range-picker с серыми занятыми днями и min-stay прямо в
календаре (Airbnb «checkout only»); смарт-дефолты; одна липкая CTA; минимум полей
в финале; 61% броней — мобайл; overlay/без перезагрузки.

**Предложение (эволюция, не переписывание):**
- **B1. Даты вводятся один раз и живут в контексте**: липкая «дата-полоса»
  (24.07 → 31.07 · 2 Gäste · [ändern]) на всех stay-страницах; деталь БЕЗ
  дублирующей формы.
- **B2. Календарь = единственный селектор дат на детали** («коридор
  доступности»): диапазон красится между кликами, min_nights видим (дни-нарушители
  гаснут), выезд-в-занятый-день кликабелен (checkout-only), выбор дат подтягивает
  цены/тарифы fetch-свопом буйбокса БЕЗ перезагрузки. Нативные date-поля — мелкий
  фолбэк «вручную» под календарём.
- **B3. Тарифы как компакт-карточки сравнения**: абсолютная сумма за проживание
  (как Booking) + дельта-бейдж к базовому («+84 € Frühstück»), «Bestpreis» на
  дешёвом, чипы отмены/предоплаты как есть; Basistarif предвыбран явно.
- B4. funnel-лейблы приводятся в соответствие (Auswahl→Daten→Bestätigt).
Всё витринный слой, без миграций; паритет-замки ДО правок (у buybox они уже есть).

## 3. Кабинет отеля: календарь = канбан (Belegungsplan / tape chart)

**Как сейчас:** сетка юниты×дни показывает ЧИСЛО свободных (брони на сетке не
видны вообще); брони — плоским списком ниже; перенос дат — два date-инпута в
строке списка; редактирования полей нет (нет ни одной формы StayBooking), удаления
нет (только FSM отмена), переноса в другой номер нет (move_stay не умеет unit),
walk-in форма внизу страницы без префила, блокировки — только со страницы Units,
окно 30 дней, JS на календаре ноль. Drag-примитив в кодовой базе есть (доска UD2).

**Рынок:** tape chart — стандарт малоотельных PMS (Little Hotelier, Smoobu,
Cloudbeds): номера×дни, брони горизонтальными плашками с именем гостя, цвет =
статус, клик → карточка, drag = перенос.

**Предложение по фазам:**
- **C1 (ядро): плашки на сетке.** Новый билдер сетки, возвращающий СЕГМЕНТЫ броней
  per-unit (sub-lanes при quantity>1), плашка = «Имя · S-XXXXXX», цвет по статусу
  (pending янтарь / confirmed зелёный / fulfilled серый / блок тёмный), клик →
  карточка FB-11; блокировки тоже плашками; свободные клетки — счётчик как сейчас;
  окно — месяц с листанием.
- **C2 (мутации с календаря):** клик по свободной клетке → walk-in форма с
  префилом (юнит+дата); создание блока выделением; drag плашки по горизонтали →
  move_stay (fetch + 409 snap-back — паттерн доски); drag по вертикали → перенос в
  другой номер (нужно расширение move_stay(unit=…): проверка наличия на целевом +
  вопрос перецены — см. развилку).
- **C3 (карточка FB-11 = полноценное редактирование):** правка дат/юнита/гостей/
  заметки; «удаление» — см. развилку (GoBD: отменённые брони с деньгами должны
  оставаться; рекомендую отмена+архив, hard-delete только для ручных без оплаты).

## 4. Развилки на решение владельца

- **A-1**: гастро-плитки в hero (вариант A) — ок? Состав: Reservieren + Speisekarte
  + Angebot des Tages (авто-выбор акции v1)?
- **B-1**: на детали номера календарь = единственный ввод дат (фолбэк «вручную»
  мелкой ссылкой) — ок, или сохранить видимые date-поля рядом?
- **B-2**: тарифы — абсолютные суммы + дельта-бейдж (рекомендую) или только дельты?
- **C-1**: v1 без drag (плашки+клик+префил создания), drag в v2 — ок, или drag
  сразу обязателен?
- **C-2**: «удалять брони» = достаточно отмены (плашка исчезает, запись остаётся,
  GoBD) или нужен настоящий hard-delete (предлагаю только для manual-броней без
  оплаты)?
- **C-3**: при переносе брони в другой номер цену СОХРАНЯТЬ (гость согласился,
  показать подсказку) или ПЕРЕСЧИТЫВАТЬ по целевому номеру? (PMS-стандарт —
  сохранять с предупреждением.)
- **Порядок**: предлагаю A (быстрая победа, виден в демо) → C1 (ежедневный
  инструмент владельца) → B (крупнейшая, гостевая конверсия) → C2 → C3.

Эффорт: A≈S/M (без миграций) · B≈M (без миграций, паритет-замки) · C1≈M ·
C2≈M (+сервисное расширение) · C3≈S/M.
