# MX v2 — Продаваемые сущности: якорь, варианты, слот, бронь

**Дата:** 2026-08-20 · **Статус:** проверка по коду (кода нет, продолжение обсуждения)
**Предыдущий документ:** `mx-multi-sale-analysis-2026-08-20.md` (инвентаризация и 8 дефектов)

Отвечает на три сообщения владельца: (1) якорь = тур, даты = группировка, опции при
оформлении и редактировании, закупка от опций; (2) «у нас только 5 продаваемых сущностей —
поправь, если не прав»; (3) модель Tripster `Guide → Experience → Slot → Booking`.

Метод: 18 агентов разведки по коду, каждое измерение перепроверено скептиком, ключевые
утверждения проверены мной лично. Один дефект доказан прогоном теста. Там, где скептик
опроверг разведчика, в тексте стоит проверенная формулировка.


> **⚠️ Продолжение — `mx-anchor-strategy-2026-08-21.md` (v3, СТРАТЕГИЯ).** Владелец поправил принцип переписи: якорь — только то, за чем клиент пришёл; сертификат — цифровой товар, акция — слой, бронь стола/мастера — поддержка продажи основного якоря. Десять сущностей этого документа свёрнуты в 4 якоря + роли; ключевой сдвиг — способ продажи становится свойством карточки.

## §1. Список продаваемых сущностей — поправка

Список владельца («товар, номер, билет, Termin, заявка-смета») **смешивает две разные оси**
и пропускает семь позиций.

### Ось каталога — что владелец заводит и продаёт: десять сущностей

| # | Сущность | Замечание |
|---|---|---|
| 1 | Товар / блюдо (`catalog.Product`) | |
| 2 | Набор (`catalog.Combo`) | Отдельный вид: своя витрина `/kombi/`, свой конфигуратор, свой вид отзывов |
| 3 | Услуга (`booking.Service`) | |
| 4 | Номер (`stays.StayUnit`) | |
| 5 | Событие / заезд (`events.Event`) | |
| 6 | **Абонемент** (`booking.PassPlan` → `Pass`) | ЗАБЫТО. Страница `/karten/`, свой Stripe-Checkout `kind="pass_purchase"` |
| 7 | **Подарочный сертификат** (`loyalty.GiftVoucher`) | ЗАБЫТО. Своя модель, свой `payment_state`, свой Checkout `kind="gift_voucher"` |
| 8 | **Платная доп-услуга** (`core.Extra`) | ЗАБЫТО. Своя цена, свой экран `/dashboard/extras/` — но существует только как снимок внутри чужой брони |
| 9 | **«Свободная» акция без цели** | ЗАБЫТО. `Promotion.target_kind == ''` продаётся сама строкой `custom_lines` через `/p/<uuid>/kaufen/` |
| 10 | **Бронь ресурса без услуги** | ЗАБЫТО. У `Resource` свой `deposit_cents`, `Booking.service` — nullable: стол/зал/мастер берёт депозит |

### Ось транзакций — чем оформляется продажа: семь, а не пять

`order` · `booking` · `stay` · `ticket` · `job` · `reservation` (легаси — витрина в него больше
не пишет, `storefront-reserve` не встречается ни в одном шаблоне) **плюс `orders.Offer`** —
**вторая, отдельная от `jobs.Job` смета** («Sofort-Angebot» из чата: свой токен, свои статусы
`open/accepted/declined/cancelled`, своя публичная страница `/o/<token>/` с выбором способа
оплаты). `Offer` нет ни на доске «Verkäufe», ни в поиске Ctrl+K — он виден только внутри
переписки.

### Независимая проверка счётом чекаутов

Клиентских Stripe-чекаутов **семь**, и ровно два из них — абонемент и сертификат — не
соответствуют ни одной сущности из списка владельца. Журнал выручки знает **пять** источников
(`order/booking/stay/ticket/reservation`), поэтому **деньги за абонемент и сертификат в
«Finanzen» не попадают вообще**.

### «Тур» — не товар

`Tour` не продаётся: собственной цены у него нет (`events/models.py:28-120`; `from_price_cents`
— это минимум по ближайшим заездам). Продаётся билет на заезд. В контракте `sellable` и в
обзоре «Sortiment» тура нет; в навигации он есть — подпункт «Reisen» в ящике «Erweitert»
(`nav_registry.py:483-490`).

Отдельно и не смешивая: **платформа продаёт бизнесу** подписку, платное продвижение листинга
и Nutzungsgebühr. Это другая схема и к задаче отношения не имеет, но живёт в тех же экранах.

## §2. Модель Tripster: `Guide → Experience → Slot → Booking`

Цепочка реализована **частично и по-разному в двух движках**. Вывод, к которому пришла
разведка и который я перепроверил: **ближе `events` — он покрывает 4 звена из 5.**

| Звено Tripster | `events` (Ticket) | `booking` (Termin) |
|---|---|---|
| **Guide** | ✅ `Teacher`: публичная страница `/lehrer/<pk>/` со списком его событий **и туров** (`public_views.py:254,256`), фасет `?teacher=` (`:133-139`) | ⚠️ `Resource` есть (`title`, `bio`, `photo`), выбирается `?resource=` — **но публичной страницы нет** |
| **Experience** (карточка) | ✅ `Tour`: контент, галерея, маршрут, страна, гиды | ⚠️ `Service`: страница есть, **вариантов нет** |
| **Slot** | ✅ `Event.tour` — заезд с датой, вместимостью и деньгами | ⚠️ только **недельное** правило `AvailabilityRule.weekday`; разовых слотов на конкретную дату нет |
| **Booking** | ✅ `Ticket.quantity` — бронь на N мест | ✅ `Booking` |
| **Цена за человека** | ✅ `price_cents × quantity` (`events/models.py:683`), поле формы подписано «Preis je Platz» | ❌ |
| **Цена за группу** | ❌ | ✅ (так и работает) |
| **Вариант** инд./групповая | ⚠️ тиры — одна ось, свободный текст | ❌ нет |

### Три находки, которые меняют картину

**1. У услуги нет связи с исполнителем вообще.** Пул исполнителей услуги — это **все активные
ресурсы**: `pool = list(Resource.objects.filter(is_active=True))`
(`booking/availability.py:96`). FK `Service → Resource` в моделях отсутствует. То есть
«эту экскурсию водит только Татьяна» (и «окрашивание делает только Мария») **невыразимо**.

**2. «Сколько человек» и «цена» — в двух взаимоисключающих ветках одного движка.** В форме
брони услуги поля `party_size` **нет вовсе**; `party_size` принимает только ветка брони
*ресурса* (`public_views.py:1005`), которая вызывает `services.book(...)` **без `price_cents`**
(`:996-1007`). А там, где цена есть, множитель — это `units`, то есть **длительность**
(`?dauer=N`, `_parse_units`, `:64-72,807`), а не люди.

**3. Демо это уже обходит текстом.** Ограничение на число людей записано в описание строкой:
«Bis zu 4 Personen — der Preis gilt pro Buchung» (`demo_kits.py:2259`).

### Что это значит

Одну и ту же экскурсию **нельзя продать в двух вариантах** (индивидуальная за группу /
групповая за человека) — придётся завести её дважды в двух разных разделах кабинета, и клиент
увидит два несвязанных предложения.

Пробелы `events` до полной модели владельца: нет режима «цена за группу», у `Teacher` нет
занятости и проверки пересечений (это чистый M2M-тег, а не ресурс с расписанием), и `Tour`
не входит в контракт продаваемых сущностей.

Уточнение: «за человека» не совсем отсутствует в `stays` — курортный сбор считается как
`adults × ночи × ставка` (`stays/pricing.py:215-223`). Но это надбавка, а не режим цены.

## §3. Опции: что проверено

### Опция записывается ровно один раз — при создании сделки

Все шесть мест записи `extras=` в коде — аргументы конструктора. Присваивания
`booking.extras = …` после создания в проекте **нет ни одного**. Набор выбранных модификаторов
входит в **ключ позиции корзины** (`pid:vid:o1,o2`), а корзина умеет только «✕ удалить» —
поэтому опцию нельзя сменить даже **до** оформления.

| Вид сделки | Можно ли изменить состав после продажи |
|---|---|
| Заказ | ✕ Полностью иммутабелен: `order_action` знает `mark_paid` и переходы статуса. Единственное поле, дописываемое постфактум, — `tracking_code` |
| Проживание | ✕ Форма «Buchung bearbeiten» правит даты, номер, гостей, заметку, комнату — **Extras в ней нет** |
| Запись (Termin) | ✕ `booking_action` знает только `move` и статусы; `services.move` пишет ровно `start`/`end` |
| Билет | ✕ |
| Смета (`Job`) | ✅ **единственное исключение**: `set_lines` удаляет все строки и пересоздаёт с пересчётом net/VAT/gross |

Механизма «изменили состав → доплата или возврат» нет вообще. Более того, `RevenueEntry`
пишется через `get_or_create` и при изменившейся сумме **не обновляется**; частичного возврата
нет.

### Два денежных дефекта в единственной работающей ветке пересчёта

Пересчёт при правке брони (`move_stay(reprice=True)`) существует и работает — но умеет только
даты. В нём две ошибки.

**(а) Доп-услуга «за ночь» не пересчитывается.** `snapshot()` умножает её на число ночей
**один раз, при бронировании** (`core/extras.py:29-31`); `move_stay` складывает готовую сумму
замороженного снимка (`stays/services.py:359-360`). **Проверено тестом** — продление брони
с 2 до 5 ночей:

```
номер:          500,00 €
итог по коду:   530,00 €   (завтрак остался за 2 ночи)
честный итог:   575,00 €   (завтрак за 5 ночей)
недосчёт:        45,00 €
```

**(б) Пересчёт молча стирает скидку.** `book_stay` вызывает
`auto_discount(room_cents, nights, arrival, unit=unit, departure=departure, extra=[промо])`
(`services.py:264-266`), а `move_stay` — ту же функцию **без этих трёх аргументов**
(`:356-358`). Значит любая правка с галочкой «Preis neu berechnen» теряет Lücken-Deal и
скидку по акции, при том что FK `StayBooking.promotion` остаётся стоять: итог брони и причина
скидки расходятся.

Плюс: `deposit_cents` фиксируется один раз при создании и не пересчитывается никогда — даже
там, где итог пересчитан, сумма к оплате остаётся старой.

### Снимок опции теряет её идентификатор — и это блокирует ERP

- доп-услуга → `{"label", "price_cents"}` (`core/extras.py:30-31`);
- модификатор → `{"label", "delta"[, "sku"]}` (`orders/services.py:252`).

**Ни в одном нет id опции.** Вопрос «сколько гостей выбрали аренду мотоцикла на заезде X»
решается только сравнением немецких строк, а переименование опции молча рвёт историю.

### Механизм опций уже есть — но только у товара

`ModifierGroup`/`ModifierOption` — это в точности то, что описал владелец:
`min_select=1, max_select=1` → **радио, обязательный выбор** («Тип размещения: двухместное /
одноместное +250 €»); `max_select=0` → **чекбоксы** («Аренда Enfield 500 +400 €, трансфер
+80 €»); `price_delta` меняет итог. Движок валидации (`catalog/modifiers.py`) почти
сущность-независим — обращается только к `product.modifier_groups_active`.

**Не нужно изобретать «оси вариаций»** (как я предлагал в первом документе). Владелец прав:
это опции. Нужно расшить уже работающий движок на услугу, номер, событие и тур — по образцу
generic-отзывов (`reviews.Review` с `entity_kind` + `entity_id`).

Чего движку не хватает под ERP: у `ModifierOption` **нет остатка**, у `Extra` — **ни
количества, ни поставщика, ни привязки к конкретной сущности** (`active_for(scope)` отдаёт все
активные опции этого scope).

## §4. Закупка от опций — «своеобразная ERP»

Нужная модель **уже написана** — просто заперта в турах.

`events.SupplierBooking` (`logistics.py:27-84`) имеет ровно то, что назвал владелец: вид
закупки (отель / транспорт / пермит / гид), **поставщик FK на общий справочник**
`inventory.Lieferant`, день маршрута, дату, **точку `stop`** («Jispa», «Leh» — те самые «разные
точки»), количество, закупочную цену с валютой оригинала, статусы
`to_book → requested → confirmed → paid`, номер брони у поставщика, документ-ваучер.

Не хватает двух вещей:

1. **`event` — обязательный FK** → закупка существует только у туров;
2. **`qty` вбивается руками.** Связи «продали 8 опций аренды → нужно 8 мотоциклов» нет и быть
   не может, пока снимок опции не хранит id (§3).

Параллельно живёт вторая закупка — складская: `BestellPosition.product` — **обязательный FK
на товар**. «8 прокатных мотоциклов» или «4 номера в Джиспе» через неё не заказать. Повод
закупки там ровно один — Meldebestand (`reorder_suggestions` → `draft_from_suggestions`).

Итого: **две закупки, общий справочник поставщиков, ни одна не покрывает услуги.**

Швы под кросс-тенантные закупки (`Order.parent_order`, `supplier_tenant_schema`) объявлены
с комментарием «ПАССИВНЫЕ, логики наследования пока нет» и вне модели встречаются только
в тесте.

## §5. Группировка

Владелец: «товары / услуги / туры проще выводить сгруппированными», «комбо — это один из
видов группировки или комплект».

**Комбо как группировка — код подтверждает:** `Combo` имеет `Category` FK и собственную
страницу, то есть ведёт себя как раздел с фиксированным составом.

Но группировать умеют **не все**:

| Сущность | Иерархия | Своя страница раздела | Чем группируется |
|---|---|---|---|
| Товар | ✅ `Category`, глубина не ограничена | ✅ `/sortiment/<slug>/` + 4 шаблона `page_style` | Category + Collection |
| Набор | ✅ `Category` | ✅ `/kombi/<pk>/` | Category |
| **Услуга** | ✕ | ✕ | только `Collection` M2M. В шаблоне прайса прямо написано: «Группировки нет: услуги живут без категорий» |
| **Номер** | ✕ | ✕ | только `Collection` M2M |
| **Событие** | ✕ | ✕ | `category` — **закрытый пресет из 9 тем** (`events/taxonomy.py:12-22`: yoga, meditation, ayurveda…). Свою категорию владелец завести не может |
| **Тур** | ✕ | ✕ | `country` — свободный текст |

*Поправка к первому документу: я написал, что `Event.category` — свободный текст. Это неверно:
поле заполняется из `ChoiceField` по закрытому wellness-списку. Для тур-оператора или
организатора мастер-классов это хуже, чем свободный текст.*

Группировка уже реализована **трижды и каждый раз отдельно**: акции по `Promotion.group`
(порог — от 2 акций, остальное в «прочее»), туры по стране (от 2 стран), события по месяцам
на отдельной странице. В общем каркасе листинга слота под группы нет.

### Поле для группировки дат уже есть и простаивает

`Event.series_id` заполняется при клонировании повторяющихся событий
(`services.py:399-416`) и **не читается нигде** — ни витриной, ни кабинетом (проверено grep'ом
по всему репозиторию). Курс из 12 занятий даёт 12 отдельных карточек в листинге.

## §6. Деньги и расходы по опциям

### Выручка

**Счёт не создаёт выручку.** `issue_invoice` присваивает номер и меняет статус — ни хука, ни
сигнала. В `RevenueEntry.SOURCES` нет `job`, а реестр статусов прямо помечает: `"done"` →
«commit_stock, но не record_revenue (invoice-флоу)» (`status_registry.py:120`).
**Следствие:** у Handwerker и кейтеринга (где заявка — главный товар) журнал выручки пуст,
пока владелец не вобьёт суммы руками. Абонемент и сертификат туда не попадают вовсе (§1).

**НДС нигде не привязан к сущности.** Ни у товара, ни у варианта, ни у услуги, ни у номера,
ни у события, ни у набора, ни у позиции заказа **нет поля ставки НДС** — ставка живёт только
на документе. Поэтому выезд гостя пишет всю сумму брони по 7 % (`stays/state_machine.py:52-66`),
хотя туда входят завтрак (в DE 19 %) и курортный сбор (вне НДС). Комментарий в коде это
признаёт: «завтрак/доп — вне v1».

Это прямой ответ на «считаем на основе продаваемых сущностей и их опций»: **сегодня опция
в расчёте налога не участвует вовсе** — у неё нет ни своей ставки, ни своей строки в журнале.

### Расходы

`ExpenseEntry.event` — FK только на заезд; пишется из одного места; `SOURCE_PURCHASE` объявлен
и не используется; ни одного шаблона с расходами; маржа видна на единственном экране —
логистике заезда.

Разведка добавила: `ExpenseEntry.vat_rate` объявлен, но **в `defaults` не попадает** → всегда
`0.00` и нигде не читается (**вычета НДС нет**); `original_currency`/`original_amount` пишутся
и не читаются нигде; `related_name="expense_entries"` не вызывается ни разу.

**Себестоимости опции нет ни у кого.** Нельзя сказать «за аренду мотоцикла заплатили
мотопрокату 200 €, продали за 400 € — маржа 200 €».

## §7. Архетипы × продаваемые сущности

Матрица собирается из **четырёх несвязанных реестров**: типы бизнеса (16), `recommended_for`
модулей (пресет нового клиента), `_PRIORITY` (якорь) и `enable_modules` демо-китов. Связь
односторонняя: **тип бизнеса влияет только на пресет, а якорь дальше определяется фиксированным
порядком модулей без единого упоминания `business_type`.**

Отсюда системные расхождения:

- **Пресет ↔ демо расходятся у 9 типов из 14.** Демо включает модули сверх пресета (гастро
  добавляет `orders`/`events`/`jobs`, friseur и werkstatt — `orders`, tour_operator — `events`,
  retreat — сразу 5). Новый клиент получает **одну** вкладку продаж там, где демо показывает
  две-пять.
- **Три расхождения меняют сам якорь.** `handwerker` в демо съезжает с `jobs` на `booking`
  (booking выше в `_PRIORITY`); `pranasy` при типе «restaurant» уезжает на `events`, потому что
  явный патч `primary_module` получил только кит RESTAURANT.
- **Максимальное смешение — retreat**: 5 вкладок продаж (`ticket`, `stay`, `booking`, `job`,
  `order`). Затем restaurant / pranasy — по 4. Минимум — тип «other», ноль вкладок.
- **`promotions` недостижим как якорь по построению**: core-каталог всегда перехватывает
  фолбэк раньше.
- **Каталог есть у всех 16 типов**, но кнопка покупки требует `orders` или фолбэк-заявку
  `jobs`, которых нет в пресете у семи типов. Единственный механизм спрятать лишнее
  (`hide_archetypes`) действует лишь на одну секцию главной и **уже разъехался с данными**:
  у hotel, moto и catering он мёртв.

Уточнение (скептик поправил разведчика): **UI для смены якоря есть** — селект «Start page»
(`storefront_root`) на странице сайта; он читается с приоритетом выше `_PRIORITY`.

## §8. Что из этого следует

Модель владельца ложится на код лучше, чем моя первая версия. Четыре поправки к первому
документу:

1. **Не «оси вариаций», а опции.** Движок опций уже есть и работает (`ModifierGroup`) —
   его надо не изобрести, а расшить.
2. **Не «новая модель закупки», а расшивка существующей.** `SupplierBooking` уже нужной формы.
3. **Комбо — действительно группировка**, отдельным видом товара считать не надо.
4. **Про Tripster: ближе `events`, а не `booking`** (4 звена из 5). Я ошибся, пока не увидел,
   что у услуги нет связи с исполнителем вообще, а «люди» и «цена» живут в разных ветках.

Порядок, который из этого получается:

| ID | Шаг | Почему в этом месте |
|---|---|---|
| **MX-0** | Опция хранит id в снимке; `move_stay` пересчитывает доп-услуги и не теряет скидку; `deposit_cents` следует за итогом | Мелкий класс правок, но без него ERP невозможен; чинит два доказанных денежных дефекта |
| **MX-1** | Расходы → раздел ERP (снять FK на заезд, экран, закупка пишет расход, живой `vat_rate`) | Не зависит от остального, закрывает прямой запрос |
| **MX-2** | Опции для услуги / номера / события / тура (расшить `ModifierGroup`); опция получает остаток и поставщика | Даёт «тип размещения» и «аренду мотоцикла» как опции |
| **MX-3** | Редактирование состава сделки после продажи + доплата/возврат | «И далее при редактировании» |
| **MX-4** | Закупка от опций: `SupplierBooking` вне туров, `qty` из проданного | «Своеобразная ERP» |
| **MX-5** | Experience: режим цены (за группу / за человека), связь `Service ↔ Resource`, страница исполнителя | Модель Tripster целиком |
| **MX-6** | Группировка: раздел у услуг / номеров / событий, живой `series_id`, свои категории событий | «Одинаковые, разные даты — одной карточкой» |
| **MX-7** | Абонемент, сертификат и `Offer` — в общий слой (Sortiment, доска, выручка, способы оплаты) | Забытые сущности перестают быть теневыми |

Открытые вопросы к владельцу — прежние шесть из первого документа плюс два новых:
про режим цены (нужны ли оба — за группу и за человека — на одной сущности) и про то,
должен ли `Teacher` стать настоящим ресурсом с занятостью.
