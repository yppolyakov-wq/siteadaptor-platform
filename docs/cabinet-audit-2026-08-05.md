## Диагноз: 7 системных причин «каши» (все подтверждены кодом)

### 1. Навигация описана в ЧЕТЫРЁХ несинхронизированных реестрах (+ пятый слой карточек)
`REGISTRY.nav_items` (рендерится только в classic), `NAV_TASK_LABELS` (37 меток, к
новому UI не применяются), `HUB_TABS` (свои подписи, свои дубли), `hub_tiles` главной
(игнорирует гейты вопреки собственному докстрингу) + карточки лендингов
marketing_home/integrations_home. Один экран получает до 4 входов под 3 именами
(`notifications-settings`: «Benachrichtigungen» / «Care-Zyklus» / «Erinnerungen &
Care-Zyklus» / «Benachrichtigungen & Telegram»). «Сайдбар говорит одно, хаб — другое»
при такой архитектуре структурно неизбежно.

### 2. Три поколения поверхности продаж живут одновременно
Легаси (board + order_list + календари + hub_tabs["board"], который в новом UI выродился
в огрызок из Tickets/Aufträge без активного таба) · ST-5b (`orders_view`, «персист
удалён») · V4 (`/dashboard/verkaeufe/`, персист есть). Два движка дефолтов с
расходящимися результатами, три словаря действий (целевой статус / глаголы / вшитый
whitelist), «Alte Ansicht»-метка стоит даже на самой новой странице. Действия внутри
встроенных календарей Verkäufe выбрасывают на легаси-страницы (redirect'ы per-app вьюх).

### 3. Простой режим НЕ работает в новом (дефолтном) интерфейсе
`sidebar_nav` не вызывает `simple_hidden_modules` (требование плана ST-4b §
docs/st4b-sidebar-plan-2026-07-19.md:46 потеряно при реализации); HUB_TABS не читают
ui_mode; ящик «Erweitert» — независимая четвёртая ось скрытия; тултип тумблера обещает
скрытие, которого не происходит; тесты режима охраняют мёртвый в дефолте classic-путь;
комбинация simple×classic не покрыта ни одним тестом. Реально режим влияет только на:
виджеты главной, classic-сайдбар, 2 аккордеона settings.html, табы формы товара.

### 4. classic_ui — не «оформление», а вторая информационная архитектура
Два НЕПОЛНЫХ кабинета: классический пользователь никогда не увидит
marketing_home/integrations_home/verkaeufe (якорей нет), новый — не достигнет
board/events:list/jobs:list (у части архетипов вообще ни одного входа). «Marketing» в
сайдбаре открывает разные страницы в зависимости от флага. ~21 точка ветвления.

### 5. Ориентация потеряна: подсветка работает на 7 из 44 nav-значений
Компакт-сайдбар подсвечивает строго `nav == nav_key` при 7 якорях; вьюхи отдают 44
разных значения → на ~37 экранах (включая вкладки собственного хаба Einstellungen) не
подсвечено ничего. Хабы молча подменяются при переходе (Marketing → Kunden/Settings
без пути назад в таб-баре); nav_key «care» не производится никем — таб не подсвечивается
никогда. Поиск по меню в компакт-режиме СЛОМАН: JS ищет `.nav-group`, которых в
компакт-ветке нет → всегда «Nothing found.» поверх полного списка. «Website» — один
ярлык, две разных цели (site-лендинг vs Studio); back-ссылка Studio подписана
«Dashboard», ведёт на site.

### 6. Настройки: дубли писателей, опасные save-пути, недостижимые панели
- **HIGH (потеря данных):** `siteconfig.normalize()` не знает ключей `notify` /
  `low_stock_threshold` / `lots_enabled` → сохранение ЛЮБОГО экрана
  Website/SEO/Finder/мастера (~20 мест записи) молча стирает матрицу уведомлений,
  привязку Telegram владельца и настройки склада. Замков нет.
- **HIGH:** notifications_settings при Save затирает каналы временно выключенных
  модулей (узел customer заменяется целиком).
- **HIGH:** `settings_view` делает голый `tenant.save()` без update_fields — гонка со
  всеми параллельными писателями (черновик билдера, Telegram-вебхук, Stripe-callback).
- Мёртвые POST-ветки `orders:order-settings` (delivery/vorkasse/prepay) и живой
  недостижимый эндпоинт `billing-payments-methods` способны обнулить поля пустым POST.
- Правовые тексты — два экрана (settings плоские поля vs /recht/ LegalDoc), победитель
  молчаливый; часы работы — два поля, мастер пишет только текстовое.
- Настройки процессов (колонки доски, имена статусов, переходы) недостижимы с
  Verkäufe — точки входа; у stays панели вычисляются, но не рендерятся (мёртвый код).
- Тема/шрифт/SEO живут только в билдере, из Einstellungen входов нет; «языки» — 5
  понятий, 3 подписаны 🌐 без объяснений.
- REFUTED: «Zahlarten редактируются с двух экранов» — вторая форма уже убрана (W4-3),
  остался только мёртвый эндпоинт.

### 7. Экраны-сироты и мёртвый код
Недостижимы из нового UI: **/dashboard/billing/ (подписка!)**, Blog & News (включён
всем архетипам), /promotions/newsletter/ (0 входов во всём репо), Finanzen (в Простом —
вообще), Auswertungen (2 входа, оба ведут в 404 из-за гейта модуля analytics),
events:list/jobs:list/board у части архетипов, Kollektionen. Мёртвое: `dashboard_tiles`
(75 строк + 3 теста «для истории»), NAV_GROUPS-ветка наполовину пуста,
`grouped_active_modules` считается на каждом рендере впустую, 6 блоков контекста
site_view не используются шаблоном.

### Бонус: расхождения ПОВЕДЕНИЯ (не только навигации) между поверхностями продаж
- «Versendet» с доски шлёт письмо клиенту БЕЗ трек-номера и не пишет shipped_at
  (карточка заказа — пишет); у доставочного заказа доска предлагает «Abgeholt».
- Резерв с доски теряет confirmed_at/fulfilled_at/cancelled_at и select_for_update
  (сервисы promotions их ставят, FSM-путь доски — нет).
- Акцию на услугу/номер/комби НЕЛЬЗЯ создать из UI (движок PL готов, в PromotionForm
  только product).
- Вкладка «Bestellungen» на Verkäufe открывается при выключенном модуле orders
  (primary-kind без гейта), а «Alte Ansicht» из неё ведёт в 404.
- Кастомные статусы применимы с доски, но не с карточки заказа (вшитый whitelist).
- Три поверхности доски (главная/board/Verkäufe) дают три разных ответа «сколько у
  меня заказов» (limit 20/50/200 при счётчиках по БД).

## Ключевые уроки конкурентов (полные отчёты в папке)

**Канон верхнего уровня (Shopify/Wix/Squarespace/Shopware совпадают):** объекты бизнеса
(Заказы→Товары→Клиенты) → инструменты роста (Маркетинг/Контент/Аналитика) → опциональные
расширения (каналы/приложения — появляются в меню только при установке) → **единый
Settings-хаб внизу** (15–30 разделов, всё «настроил и забыл»). Наш 7-якорный сайдбар
ST-4b уже соответствует канону — чинить надо наполнение, подсветку и Settings.

**Битрикс (антипаттерн-эталон):** «показать всё и дать скрывать» — проигрышная
стратегия; выигрышная — «показывать мало по архетипу и дать включить». Дубли входов в
одну сущность = пользователь не знает, какой вход «настоящий». Настройка должна жить
там, где её эффект. Режим должен менять ВИДИМОСТЬ, а не семантику данных (наш W0).
Язык задач вместо терминов. Навигационные страховки (поиск/избранное) компенсируют, но
не лечат структуру.

**TravelLine:** операционка выше настроек, календарь-шахматка = главный рабочий стол,
все действия из карточки брони без ухода в разделы; вкладки «Основные / Дополнительные
настройки» на карточке сущности; чек-лист «обязательное vs дополнительное». Их болезнь =
наша: три куста настроек с неочевидными границами; меню из бренд-названий продуктов.

**CS-Cart:** Settings одним пунктом внизу сайдбара, внутри «раздел → вкладки»
(структура закреплена платформенно, аддоны обязаны встраиваться); Settings Wizard;
отсутствие поиска по настройкам — главная боль мерчантов.

**Сквозные паттерны к перенятию:** (1) единый Settings-хаб с табами по типам;
(2) поиск-палитра по разделам И настройкам (Ctrl+K); (3) правило «параметр, который
меняют реже раза в неделю, живёт в Settings»; (4) лендинг-прихожая оправдана ТОЛЬКО
если показывает состояние, которого нет в меню; (5) при переезде навигации — маппинг
«старое→новое» (редиректы/подсказки), иначе «Where did everything go»; (6) plan-гейты
вместо полного скрытия; (7) Home отвечает на «что сегодня», а не дублирует отчёты.
