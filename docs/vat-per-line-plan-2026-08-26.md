# Волна VAT: ставка НДС в каждой позиции + перестановка блоков карточки (2026-08-26)

Запрос владельца после деплоя: «Сделай отображение налога прямо в каждой позиции и в итоге
рассчитывай налог в зависимости от указанного налога во всех архетипах для всех товаров в заказе.
Если у товара нет настройки налога — нужно добавить в настройках товара или услуги и выводить
именно тот параметр, который там указан. Поле Gültig bis и Angebot schicken перенеси в поле
Dokumente. Nachrichten перенеси в правую колонку под кнопку написать клиенту.»

Разведка — 12 агентов (6 тем × разведка + скептик), все находки проверены по коду.

## 0. Что выяснилось (главное)

**Действующий дефект, а не будущий риск.** Счёт из заказа со смешанными ставками считается по
ОДНОЙ ставке: 11,90 € @19 % + 10,70 € @7 % → счёт 23,80 € при фактическом итоге заказа 22,60 €.
Ошибка 5 % в пользу бизнеса; при обратном составе — в пользу клиента. Это же ломает сопоставление
платежа в ERP-2 (сравнение по равной сумме) и Mahnung (требование на сумму, которой клиент
не покупал). Демо-кит `cafe` со смешанным чеком 7/19 % воспроизводит это на живых данных.

**Слой показа уже многоставочный, слой документа и учёта — нет.** `OrderItem.vat_rate`,
`deal_components`, снимки допов и `deal_lines` умеют ставку на позицию; `Invoice`, `RevenueEntry`,
DATEV, PDF сметы и публичная страница сметы знают одну ставку на документ.

## 1. Где ставка сегодня теряется

| Место | Что происходит | Чинится |
|---|---|---|
| `JobLine` (смета) | поля ставки нет вовсе; в строке печатается `job.vat_rate` — общая | миграция `jobs` |
| `Combo` (набор) | ставки нет в модели → позиция заказа всегда 19 % | миграция `catalog` |
| `Extra` (доп) | поле есть (`core.Extra.vat_rate`), но нет в форме → у 100 % допов NULL | без миграции |
| свободные строки | `pool_lines` MEN-4, свободная промо-акция, услуга из пикера → 19 % | без миграции |
| `Invoice` | одна ставка на документ; строки без ставки | без миграции (JSON) |
| `RevenueEntry` | одна ставка на сделку → DATEV/UStVA получают не тот счёт | отдельный шаг, гард |

Отдельно: у отеля завтрак и парковка облагаются по 7 % вместо 19 % (Aufteilungsgebot) — ровно
случай, ради которого `Extra.vat_rate` и заводился, но ввести ставку владелец не может.

## 2. Решения (принимаю по умолчаниям разведки)

1. **`JobLine.vat_rate` — nullable.** NULL = ставка документа (`Job.vat_rate`). Тогда бэкфилл
   не нужен и все существующие сметы считаются байт-в-байт как раньше; замки на 19 % остаются
   зелёными. Ставка появляется у строки, только когда её задали или подтянули из каталога.
2. **`Combo.vat_rate` — default 19 % + подсказка в форме** «Speisen meist 7 %». Ставить 7 %
   автоматически по типу бизнеса не будем: правило проекта — не угадывать за владельца.
3. **`Extra.vat_rate` — опция «wie die Buchung» (пусто) в форме.** Пустое значение сохраняет
   нынешнюю семантику «ставка сделки», поэтому ничего не ломается у существующих допов.
4. **Округление — по ГРУППЕ ставки, не по строке.** Построчное округление с последующим
   суммированием даёт ±копейку против нынешних замков.
5. **Одна точка истины на документ.** Все четыре поверхности сметы (карточка, PDF,
   публичная страница принятия, счёт) зовут одну функцию — иначе клиент примет один итог,
   а получит другой. Тот же приём, что спас заказы в волне SH.
6. **Снимки не пересчитываем.** Правка ставки действует только вперёд; выставленный счёт
   и записи журнала не трогаем. Data-миграций нет.

## 3. Батчи

**A. Смета (главное по запросу).**
- `JobLine.vat_rate` (миграция `jobs/0017`, nullable) + `effective_vat_rate` = ставка строки или ставка документа.
- `apps/jobs/totals.py::quote_totals(lines, small_business)` → `{rows: [{rate, net, vat, gross}], net, vat, gross}`; группировка по ставке, округление по группе.
- `set_lines` пишет ставку строки (из формы; при привязке к товару — из `Product.vat_rate`), считает через `quote_totals`.
- Форма сметы: селект ставки в строке; общий селект документа остаётся дефолтом новых строк.
- `core/vat.py` ветка `job` отдаёт rows из `quote_totals` → карточка показывает разбивку.
- PDF сметы + публичная страница + счёт из сметы — через ту же функцию.

**B. Снимки и формы.**
- `Combo.vat_rate` (миграция `catalog/0031`) + `{% vat_select %}` в форме комбо + снимок в `create_order`.
- `Extra.vat_rate` в форму «Zusatzleistungen» + `parse_rate_optional` + чтение во вьюхе.
- Проброс ставки в свободные строки: 7-й элемент `custom_lines`, параметр `vat_rate=` у `editing.add_item`; потребители — `pool_lines`, свободная промо-акция, услуга из пикера (там ставка берётся из `Service.vat_rate`).
- Демо: ставки у комбо и допов гастро/отеля.

**C. Документы (чинит дефект прода).**
- `Invoice.lines[i]["vat_rate"]` (JSON, без миграции) + фолбэк на `Invoice.vat_rate` для легаси.
- `compute_totals` — построчная форма (старая сигнатура сохраняется байт-в-байт: её зовёт и смета).
- `invoice_from_order` берёт готовые `order_totals(...)["rows"]`; `invoice_from_stay`/`invoice_from_booking` — из `deal_components`. Инвариант: `invoice.gross == сумма сделки` (замок).
- PDF счёта печатает строки «USt X %» по группам; старый счёт рисуется по старому снимку.
- `RevenueEntry` по ставкам — ТОЛЬКО для новых записей, с гардом «если есть запись с голым `<id>` — не дробить» (иначе оборот удвоится). DATEV за закрытые периоды не должен поехать.

**D. Перестановки карточки.**
- «Gültig bis» и действие «Angebot senden» (FSM `new → quoted`) — в блок `deal_documents` карточки заявки.
- «Nachrichten» — в рейл под карточку клиента. Решение: переносим на ВСЕХ карточках сделок (скелет общий, правило владельца «меняется один — меняются все»).

## 4. Риски и замки

- GoBD: нельзя переписывать снимки и выставленные счета — правки только вперёд; тест на неизменяемость issued-счёта.
- Двойной учёт выручки при смене `source_ref` — гард обязателен, замок на отсутствие дублей.
- Публичная смета и PDF обязаны совпадать с карточкой — замок сравнивает итоги трёх поверхностей.
- Округление по группам — замок на смешанной смете (7 % + 19 %), сверка с суммой строк.
- `test_set_lines_computes_totals_19` и соседние замки сметы должны остаться зелёными без правок
  (это доказывает, что nullable-ставка не изменила поведение).
