## §0. Запрос владельца (2026-08-04, дословно по смыслу)

Мото/квадро-архетип для туров по Индии/Непалу:
1. полноценная бронь + ведение клиента;
2. богатое описание тура;
3. блог + комментарии; «подключать туда клиентов», обмен файлами «как в соцсети» —
   замена нынешней практике «отдельная Telegram-группа на каждый тур»;
4. у каждого участника — личный кабинет, где в **зашифрованном** виде хранятся его
   данные и документы;
5. инструмент организатора: брони отелей в точках маршрута, экскурсии, построение
   маршрута, ведение расходов, учёт времени/задач/работ;
6. функционал переиспользовать на остальных архетипах.

## §3. Предлагаемая архитектура

Принцип тот же, что во всей платформе: **не новая вертикаль, а слой поверх
существующих движков.** Тур = `Event`; всё новое — переиспользуемые модули.

### 3.1 Тур-ядро: маршрут (без миграции)
`Event.details._SCHEMA` += `itinerary`: записи
`{day, title, text, km, overnight, lat, lng}` (построчный ввод «Tag 3 | Manali →
Jispa | 140 км | …», как остальные records-поля details). Рендер: секция «Route» в
`detail_sections` (events уже orderable) — таймлайн по дням + карта Leaflet с
маркерами точек и простой polyline по порядку (настоящий роутинг не нужен и
невозможен без внешнего API — прямые сегменты честнее). Пресеты анкеты
`registration.py` += мото-набор (категория прав, стаж, рост, своя техника/аренда).
Тиры покрывают «своя техника / аренда Enfield / пассажир / одноместный номер» без
новых моделей.

### 3.2 Досье участника: `SecureDocument` (новый app `apps/documents`, миграция)
Generic-модель: `owner_customer`, опц. `ref_kind/ref_id` (билет/бронь/заявка —
паттерн inbox), `kind` (passport/license/insurance/visa/other), `path/mime/size`,
метаданные (номер документа и т.п.) — `EncryptedTextField`. **Содержимое файла
шифруется Fernet перед записью в storage; выдача ТОЛЬКО через proxy-вьюху** с
проверкой magic-link-сессии участника или Membership организатора (закрывает
сегодняшнюю дыру «публичный URL у всего»). PDF+изображения (новый валидатор рядом
с `validate_image`). Retention по эталону Meldeschein: purge через N дней после
`Event.ends_at` (настраиваемо), beat через `schema_context`. В ЛК — раздел
«Dokumente», у организатора — матрица «участник × документ» (кто что сдал) на
странице тура. Согласие на хранение — чекбокс при загрузке (паттерн
`marketing_opt_in_at`).

### 3.3 Тур-спейс «Reise-Feed» (новый app `apps/community`, миграция)
Замена Telegram-группы = **лента, а не realtime-чат** (WebSocket в проекте нет,
поллинг inbox — предел; лента покрывает реальные сценарии группы: объявления
организатора, фото дня, файлы, вопросы-ответы):
- `FeedSpace` — generic `ref_kind/ref_id` (v1: event), `is_open` (открыт до/после
  тура), настройки («участники могут постить» вкл/выкл).
- `FeedPost` — автор = организатор (`author_user`) ИЛИ участник
  (`author_customer`), text, attachments (список FileRef + SecureDocument-механика
  выдачи для приватных файлов; фото — обычный FileRef).
- `FeedComment` — плоские комментарии (+ ответ организатора выделен, как CM-6).
- **Доступ**: гейт `has_ticket` (готов) + magic-link-сессия ЛК; приглашение
  «сопровождающего» без билета — подписанный invite-токен (паттерн cancel_token).
- Уведомления: домен `community` в `notifications/prefs.py` (email + **Telegram**
  через готовый `send_to_customer` — участник получает пуш «новый пост» со ссылкой;
  сам контент живёт у нас, Telegram остаётся каналом доставки).
- Модерация: организатор скрывает пост/комментарий (паттерн `review_toggle`).
- Блог остаётся публичным маркетингом (SEO-лица туров, автопостинг publishing);
  Reise-Feed — приватное пространство группы. Пост из ленты можно «поднять в блог»
  (кнопка-копирование) — обратной связи не нужно.

### 3.4 Логистика организатора: `SupplierBooking` (в `apps/events` или новый `apps/logistics`, миграция)
По рекомендации разведки — новая лёгкая модель, а не изгиб dropshipping-швов:
`event` (тур), `day`/`date`, `stop` (текст точки, опц. ссылка на itinerary-день),
`supplier` (FK **`inventory.Lieferant`** — реюз справочника как есть), `kind`
(hotel/excursion/transport/permit/guide/other), `qty` (комнаты/места), `cost_cents`
+ `currency` + `cost_eur_cents` (см. развилку §5.6), `status`
(to_book→requested→confirmed→paid / cancelled — маленький FSM), `confirmation_ref`,
`note`, ваучер-вложение (SecureDocument). UI: вкладка «Logistik» на туре — таблица
по дням маршрута со статус-чипами; свод «что не подтверждено за X дней до старта»
на хоум-виджет. Реальные API отелей/OTA — external-gated (как G11c–e), v1 —
учётная книга + вложения подтверждений.

### 3.5 Расходы: `finance.ExpenseEntry` (миграция) — кусок давно запланированного M13
Зеркало `RevenueEntry`: `source` (supplier_booking/manual/…), `source_ref`
(идемпотентность), `amount`, `vat_rate`, `date`, `category`, `note`, опц.
`event`-привязка. Авто-запись при `SupplierBooking→paid`. Отчёт «маржа тура»:
Σ выручка билетов (RevenueEntry по event уже пишется `TicketSM`) − Σ расходы.
**Это сразу общеплатформенная фича** (пекарня/отель/мастер получают учёт расходов).

### 3.6 Задачи: чек-лист тура `TourTask` (миграция, маленькая)
`event`, `title`, `due_date`, `assignee` (Membership-user), `done_at`, `sort`.
Плоский чек-лист на странице тура (пермиты Inner Line, границы, ТО техники,
брифинг) + просрочка на хоум-виджет. НЕ новый kind Kanban-доски (доска —
транзакции с FSM; чек-лист проще и понятнее). «Учёт времени» — см. развилку §5.7:
в коде его нет вовсе, объём зависит от того, что владелец имеет в виду.

## §5. Развилки владельца (нужны решения ДО кода)

1. **Тип бизнеса.** (а) остаёмся на `tour_operator` + мото-демо-кит; **(б,
   рекомендация)** + отдельный `moto_tours` в BUSINESS_TYPES (choices-only
   миграция, дёшево: своя карточка регистрации, язык задач, пресеты, Branchen-
   страница «Motorrad- & Quad-Touren»).
2. **Формат тур-спейса.** **(а, рекомендация)** лента с комментариями (соцсеть-
   лайт, надёжно на текущем стеке, покрывает функции TG-группы); (б) realtime-чат
   (требует WebSocket/Channels — новый инфраструктурный слой, дорого).
3. **Типы файлов в ленте/досье.** Рекомендация: фото + PDF + GPX (трек маршрута —
   родной формат мото-сообщества), лимит размера ~10 МБ.
4. **Глубина шифрования.** **(а, рекомендация)** шифровать содержимое файлов
   Fernet + proxy-выдача + EncryptedTextField на метаданных; (б) только
   приватная выдача без шифрования blob'ов. Retention: рекомендация 90 дней после
   окончания тура (настраиваемо). Бонус-пункт: перевести
   `GuestRegistration.doc_number` (Meldeschein отеля) на EncryptedTextField —
   лежит открыто.
5. **«Тур-продукт с N датами» (гэп T6).** **(а, рекомендация)** v1: заезд =
   Event + кнопка «Дублировать тур» (контент копируется), T6 отдельной волной по
   спросу; (б) строить TourProduct сразу (заметно дороже, трогает листинги/SEO).
6. **Валюта расходов.** Индия/Непал = INR/NPR. **(а, рекомендация)** сумма в EUR
   обязательна (курс вводится руками при записи), оригинал `currency+amount`
   опционально хранится рядом; (б) полноценная мультивалюта с курсами — не
   строим v1.
7. **«Учёт времени» — уточнить, что имеется в виду:** (а) часы гидов/работников по
   туру (→ таймшит-модель), (б) план-график подготовки (→ покрывается TourTask с
   дедлайнами), (в) хронометраж дней тура (→ покрывается itinerary). От ответа
   зависит, есть ли тут вообще отдельная работа.
8. **Telegram-мост.** **(а, рекомендация)** v1: пуш-уведомления о постах ленты со
   ссылкой (готовый канал) + Mini App открывает ЛК; (б) двусторонний мост
   (сообщения из TG-группы в ленту) — отложить, помечу в
   `external-integrations-backlog`.

## §7. Риски / право

- **Паспорта/права участников** — чувствительные PII: шифрование at-rest (§3.2),
  retention, согласие при загрузке, DSGVO-export/erase расширить на документы.
  Явно НЕ храним больше, чем нужно организатору (принцип минимизации).
- **Waiver для мото** — уже есть (`TicketWaiver`), но у него нет purge-задачи
  (в отличие от Meldeschein) — добавить в MT-2 ретеншн и ему.
- **UWG/DOI** не трогаем: лента — транзакционное общение с купившими участниками,
  не маркетинговая рассылка; но кнопки «пригласить в рассылку» в ленте не делаем.
- **Индия/Непал ≠ DACH**: Kurtaxe/DATEV не мешают (не активируются), i18n
  ru/en/tr/uk уже есть, Stripe продаёт в EUR. Из нового — только валюта расходов
  (§5.6).
- Реальные API бронирования отелей/OTA — external-gated (партнёрства), как G11c–e.
