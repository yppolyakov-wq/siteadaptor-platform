**Статус: РЕШЕНИЯ ВЛАДЕЛЬЦА ПРИНЯТЫ (§0b, 2026-08-04), сводное ТЗ на финальной
проверке владельца. Один открытый вопрос — формат чата (§5).** Код не начат.

## §0. Запрос владельца (2026-08-04)

Мото/квадро-архетип для туров по Индии/Непалу: полноценная бронь + ведение
клиента; богатое описание тура; блог/лента с комментариями и «подключением»
клиентов, обмен файлами «как в соцсети» — замена практике «Telegram-группа на
каждый тур»; ЛК участника с **зашифрованным** хранением данных/документов;
инструмент организатора (брони отелей в точках, экскурсии, построение маршрута,
расходы, хронометраж/задачи); переиспользование на других архетипах.

**Уточнение владельца (вторым сообщением): маршрут — интеллектуальная
собственность гида.** Не всегда тур раскрывается по этапам: публично могут
светиться только ключевые места, а полный маршрут остаётся закрытой разработкой.
То же с привязкой отелей и транспортных билетов — открытость для участников
на усмотрение гида. Гид в любом случае строит маршрут «для себя», а публикует ли
его в группе или на сайте — выбирает настройкой. → Модель видимости в §3.1b.

## §0b. Решения владельца (2026-08-04)

1. **Тип бизнеса:** отдельный business_type НЕ делаем — демо-кит на существующем
   `tour_operator` (subdomain `moto`).
2. **Формат тур-спейса:** владелец спросил цену realtime-чата → оценка в §5;
   рекомендация — v1 чат на быстром поллинге, WebSocket отдельной волной.
   ⏳ ждёт подтверждения.
3. **Файлы:** до **50 МБ** (фото + PDF + GPX + короткие видео MP4).
4. **Шифрование:** да — шифруем содержимое файлов + proxy-выдача; retention
   90 дней после тура (настраиваемо).
5. **Тур-продукт с N датами:** строим **сразу** (закрываем гэп T6).
6. **Валюта расходов:** EUR обязателен, оригинал в местной валюте — опционально
   рядом.
7. **«Учёт времени» = хронометраж тура** → закрывается временами в итинерарии,
   отдельный таймшит НЕ строим.
8. **Telegram-мост:** двусторонний — **делаем сразу** (MT-3b).

## §3. Архитектура (с учётом решений §0b)

Принцип: **не новая вертикаль, а слой поверх существующих движков.**

### 3.1 Тур-продукт + заезды (закрываем T6; миграция)
Новая модель **`Tour`** (контент): название, описание, галерея, детали
(includes/price_includes/bring/faq/hosts — по образцу `Event.details`), гиды M2M,
итинерарий (3.1a), slug. **`Event` получает FK `tour` (nullable)** и играет роль
«заезда»: даты, цены/тиры, capacity, депозит/рассрочка — весь движок продаж
(билеты, анти-оверселл, письма, QR, waiver) НЕ трогается. Страница тура на
витрине = контент + блок «Даты и цены» со списком заездов (свободно/мест
осталось/sold out → waitlist); выбор заезда → штатный флоу покупки билета.
Обычные события без FK живут как раньше (обратная совместимость, листинги
показывают туры и одиночные события вместе).

### 3.1a Итинерарий с хронометражем (внутри Tour)
Элементы: `{day, time_from, time_to, title, text, km, overnight, lat, lng,
visibility}` — построчный ввод в кабинете (как records-поля details) + карта
Leaflet с маркерами и polyline по порядку точек (настоящий роутинг через внешние
API не делаем — прямые сегменты). Времена точек = **хронометраж тура** (решение
§0b.7): день раскрывается таймлайном «09:00 выезд → 13:00 перевал → 17:00
ночёвка», сумма км по дню считается автоматически.

### 3.1b Модель видимости (уточнение владельца — сквозная для MT)
Три уровня: **`private`** (только кабинет гида) · **`participants`** (участники
тура: ЛК + Reise-Feed) · **`public`** (страница тура на сайте).
- **Каждый элемент итинерария** несёт `visibility`, **дефолт `private`**: гид
  строит полный маршрут для себя, затем точечно открывает «ключевые места» в
  public (витрина покажет только их — «Highlights der Route»), а участникам —
  сколько сочтёт нужным. Плюс переключатель на туре «открыть весь маршрут
  участникам/публично» одним действием (массовая смена, не отдельное хранение).
- **Каждая запись логистики** (отель/транспортный билет/экскурсия, §3.4) несёт
  флаг `visible_to_participants` (дефолт выкл). Включён → участник видит в ЛК
  карточку «Ночь 3: Hotel X, подтверждено» **без закупочных цен** (цены закупки
  не отдаются наружу ни при каком флаге — это отдельные поля, не попадающие в
  участник-сериализацию). Публичного уровня у логистики нет.
- Реализация: фильтрация на сервере в точках выдачи (витрина/ЛК/фид), не CSS;
  тесты-замки «private не утекает» обязательны в каждой волне.

### 3.2 Досье участника: `SecureDocument` (новый app `apps/documents`; миграция)
Generic-модель: `owner_customer`, опц. `ref_kind/ref_id` (билет/бронь/заявка —
паттерн inbox), `kind` (passport/license/insurance/visa/other), `path/mime/size`,
метаданные — `EncryptedTextField`. **Содержимое файла шифруется Fernet перед
записью в storage; выдача ТОЛЬКО через proxy-вьюху** с проверкой magic-link-сессии
владельца документа или Membership организатора (закрывает дыру «публичный URL у
всего»). Типы: изображения + PDF + GPX + MP4, лимит **50 МБ** (решение §0b.3);
новый валидатор рядом с `validate_image`. Retention по эталону Meldeschein: purge
через 90 дней после `Event.ends_at` заезда (настраиваемо), beat через
`schema_context`. В ЛК — раздел «Документы»; у гида — матрица «участник ×
документ» на заезде (кто что сдал: паспорт ✓, права ✗). Согласие при загрузке
(паттерн `marketing_opt_in_at`). Бонус тем же инкрементом:
`GuestRegistration.doc_number` → `EncryptedTextField`; ретеншн для `TicketWaiver`.

### 3.3 Тур-спейс «Reise-Feed» + чат (новый app `apps/community`; миграция)
- `FeedSpace` — generic `ref_kind/ref_id` (v1: заезд-Event), `is_open`
  (до/после тура), настройка «участники могут постить» (вкл/выкл).
- `FeedPost` — автор = гид (`author_user`) ИЛИ участник (`author_customer`),
  text, вложения (фото — FileRef; файлы — через SecureDocument-механику выдачи).
- `FeedComment` — плоские комментарии, ответ гида выделен (как CM-6).
- **Чат** — та же пара моделей в режиме «сообщения» (отдельная вкладка спейса,
  posts без заголовка): v1 на быстром поллинге (3 с, паттерн inbox `thread_poll`
  + typing-флаги Redis уже есть). WebSocket — см. §5.
- **Доступ**: гейт `has_ticket` (готов) + magic-link-сессия ЛК; invite-токен для
  сопровождающих без билета (паттерн cancel_token). «Подключить клиента» = он
  купил билет ИЛИ получил invite-ссылку.
- Уведомления: домен `community` в `notifications/prefs.py` (email + Telegram
  `send_to_customer`).
- Модерация: гид скрывает пост/комментарий (паттерн `review_toggle`).
- Блог остаётся публичным маркетингом; связь: кнопка «поднять пост в блог».

### 3.3b Telegram-мост (двусторонний; решение §0b.8)
Расширение `apps/telegram`: гид добавляет бота тенанта в TG-группу тура и
привязывает её командой `/link <код>` (код показан в кабинете спейса) →
`FeedSpace.tg_chat_id`. Дальше:
- **исходящее**: пост/сообщение из Reise-Feed → бот публикует в группу
  (идемпотентно, dedupe-ключ);
- **входящее**: webhook начинает принимать `message` из привязанных групп →
  сохраняет в фид/чат; автор матчится по `TelegramLink.chat_id` (если участник
  привязывал бота), иначе — имя из Telegram; фото/документы ботом скачиваются
  через `getFile` (лимит Bot API на скачивание — 20 МБ; больше — сохраняем
  ссылку-заглушку);
- эхо-петля гасится маркировкой источника (`source=telegram` не пересылается
  обратно). DSGVO-примечание (Telegram — не-EU) — в доке кабинета, как уже
  зафиксировано в docstring `apps/telegram/models.py`.

### 3.4 Логистика гида: `SupplierBooking` (миграция)
`tour`/`event` (заезд), `day`/`date`, `stop` (точка, опц. привязка к
itinerary-дню), `supplier` (FK `inventory.Lieferant` — реюз как есть), `kind`
(hotel/transport_ticket/excursion/permit/guide/other), `qty`, `cost_cents` +
`currency`+`amount_original` (§0b.6: EUR обязателен, оригинал опционально),
`status` (to_book→requested→confirmed→paid / cancelled — маленький FSM),
`confirmation_ref`, `note`, ваучер-вложение (SecureDocument),
**`visible_to_participants`** (§3.1b). UI: вкладка «Logistik» на туре — таблица по
дням со статус-чипами; свод «не подтверждено за X дней до старта» на хоум-виджет.
Реальные API отелей/OTA — external-gated (как G11c–e), v1 — учётная книга.

### 3.5 Расходы: `finance.ExpenseEntry` (миграция) — кусок M13
Зеркало `RevenueEntry`: `source` (supplier_booking/manual/…), `source_ref`
(идемпотентность), `amount` (EUR), `currency`+`amount_original` (опц.),
`vat_rate`, `date`, `category`, `note`, опц. привязка к туру/заезду. Авто-запись
при `SupplierBooking→paid`. Отчёт «маржа тура»: Σ выручка билетов (уже пишется
`TicketSM` в RevenueEntry) − Σ расходы. Общеплатформенная фича — расходы получают
все архетипы.

### 3.6 Чек-лист тура: `TourTask` (маленькая миграция)
`tour`/`event`, `title`, `due_date`, `assignee` (Membership-user), `done_at`,
`sort`. Плоский чек-лист на туре (пермиты Inner Line, границы, ТО техники,
брифинг) + просрочка на хоум-виджет. НЕ новый kind Kanban-доски. Таймшит не
строим (§0b.7).

## §4b. MT-2 — детализация до кода (пишется после MT-1)

Новый TENANT-апп `apps/documents` (в `TENANT_APPS`; тест-настройки подхватят как SHARED).

**Модель `SecureDocument`:** `owner_customer` FK(`promotions.Customer`, CASCADE) ·
`ref_kind`/`ref_id` (мягкая привязка к билету/заезду — паттерн inbox, переживает
удаление) · `kind` (passport/license/insurance/visa/other) · `path` (ключ в
storage), `original_name`, `mime`, `size` · `meta` — `EncryptedTextField`
(номер документа и т.п.) · `uploaded_by` (customer|staff) · `consent_at` ·
`expires_at` (проставляется при загрузке: конец заезда + N дней, дефолт 90).

**Шифрование содержимого:** байты файла проходят Fernet ПЕРЕД записью в storage
(`apps/secrets/crypto.py`), в хранилище лежит шифротекст. Отдача — только через
proxy-вьюху `/konto/dokument/<uuid>/`: сессия ЛК владельца документа ИЛИ
`has_cabinet_access`; иначе 404 (не 403 — не подтверждаем существование).
Прямой `default_storage.url()` для документов не используется НИКОГДА.

**Валидатор** рядом с `catalog/images.py::validate_image`: изображения + PDF +
GPX + MP4, лимит 50 МБ, проверка по сигнатуре файла (не по расширению).

**Retention:** beat-задача по образцу `stays/tasks.py::purge_due_registrations`
(чистая функция на схему + обёртка `schema_context`), удаляет и запись, и blob.
Тем же инкрементом: перевод `stays.GuestRegistration.doc_number` на
`EncryptedTextField` (ленивая миграция поля терпит плейнтекст; фильтрация по нему
нигде не используется — проверено grep'ом: только запись во вьюхе чек-ина и
вывод в списке заездов). `TicketWaiver` НЕ трогаем — см. §7.

**UI:** раздел «Dokumente» в ЛК (загрузка + список + удаление) и матрица
«участник × документ» на заезде в кабинете (кто что сдал).

**Замки:** посторонний не скачивает чужой документ; истёкший срок удаляет и blob;
не-разрешённый тип и файл >50 МБ отбиваются; в storage лежит НЕ исходный байт-поток
(шифротекст).

## §5. Открытый вопрос: realtime-чат (оценка по запросу владельца)

**Вариант A — чат на быстром поллинге (рекомендация для v1):** переиспользуем
готовый паттерн inbox (`thread_poll` + typing-флаг в Redis, M22b). Сообщение
доходит за 1–3 с; для группы тура 10–30 человек этого достаточно, визуально
неотличимо от «настоящего» чата. Стоимость — входит в MT-3 без надбавки,
инфраструктура не меняется.

**Вариант B — настоящий WebSocket:** требует django-channels + ASGI-сервер
(daphne/uvicorn) + Redis channel-layer + новый процесс в docker-compose + проксирование
WebSocket в Caddy + аутентификация magic-link-сессии в consumer'е + учёт
мультитенантности (роутинг по схеме). Это отдельная волна размером примерно с
весь MT-3 и **постоянная операционная сложность** (ещё один сервис в проде,
мониторинг, рестарты при деплое рвут соединения).

**Рекомендация:** v1 на поллинге; модель данных одинаковая, апгрейд до WebSocket
позже прозрачен (меняется транспорт, не хранение). Решение владельца: ⏳.

## §7. Риски / право

- **Паспорта/права участников** — чувствительные PII: шифрование at-rest,
  retention, согласие при загрузке, расширение DSGVO-export/erase на документы,
  минимизация (не храним больше, чем нужно).
- **Waiver для мото** — есть (`TicketWaiver`). ⚠️ Правка к первой редакции плана:
  отсутствие purge у waiver — НЕ пробел, а осознанное решение (докстринг модели:
  «не авто-чистится — срок исковой давности, в отличие от BMG-Meldeschein»).
  Ретеншн ему не добавляем: удалять подписанный отказ от ответственности раньше
  срока исковой давности значит лишать организатора юридической защиты.
- **Закупочные цены** (SupplierBooking) — никогда не сериализуются в
  участник/публичные ответы; тест-замок в MT-4.
- **UWG/DOI** не трогаем: фид — транзакционное общение с купившими; маркетинговых
  кнопок в фиде нет.
- **Индия/Непал ≠ DACH**: Kurtaxe/DATEV не активируются, i18n ru/en/tr/uk есть,
  Stripe продаёт в EUR; валюта расходов — §0b.6.
- **Telegram** — не-EU процессор: мост включается гидом осознанно (примечание в
  кабинете), контент-копия остаётся у нас.
- Реальные API бронирования отелей/OTA — external-gated (партнёрства), как G11c–e.
