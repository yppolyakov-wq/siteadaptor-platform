### 1.2. `PromoGroupPage`
- Поля: `id` UUID, `key = CharField(max_length=50, unique=True)` (как `Promotion.group`, `apps/promotions/models.py:387`), `structure` JSON null, `created_at/updated_at` (`TimestampedModel`). Таблица новая и пустая — индекс `unique` на ней бесплатен.
- Ключ — точная строка `Promotion.group` **без обрезки** (то же правило, что `siteconfig.promo_group_host`, `siteconfig.py:1447-1455`: «Sale» и «Sale » — разные группы).
- Строка создаётся только писателем при первой правке страницы группы (A2) или переносом; пустых строк нет.
- **Переименование группы.** Действия «переименовать группу» в коде нет (grep `rename|umbenenn|update(group=` по `apps/promotions` — пусто); группа меняется по одной акции в её форме. Правило: после сохранения формы акции со сменой `group` старый→новый `object_structure.follow_group_rename(old, new)` в той же транзакции: если у `old` не осталось акций, у `new` нет своей страницы, а у `old` есть — `key` переезжает на `new`; иначе ничего (страница старого ключа остаётся и видна в отчёте команды как «ohne Aktionen»). Массовое переименование, если появится в «Aktionstypen», зовёт ту же функцию.

### 1.3. Формат копии (версия 1)
```
{
  "v": 1,                         # версия формата; незнакомая → читаем как «наследует» + warning в лог
  "origin": "edit" | "migrate" | "seed",
  "sig": "<sha1 rows+layout>",    # только origin=migrate: --undo снимает лишь нетронутые копии
  "layout": "standard|tabs|breit",# только LAYOUT_KINDS (object_structure.py:37)
  "rows": [                       # ПОЛНАЯ копия строк общего хоста на момент копии, в его формате
    {"key": "<раздел>", "enabled": true|false, ...},        # якорь раздела (detail_parts.anchors)
    {"id": "<12 hex>", "key": "<вид блока>", "enabled": .., "data": {...}, "width": ..}  # блок
  ],
  "i18n": {"<язык>": {"<id блока>": {"data": {"<поле>": "<текст>"}}}}   # переводы по id, не по позиции
}
```
- Формат строк — тот, что `site_schema.load_items` отдаёт для общего хоста детали (`site_schema.py:3367-3370`, `detail_parts.edit_rows`); у категории — строки хоста `catalog`; у группы — строки `promo_group`/`promos`. Точный вид якоря (флаг видимости — `enabled` или иной) — предпосылка, проверить в M6a по `detail_parts.lift` (`detail_parts.py:527`).
- Переводы внутри копии — **по id блока** (вопрос чеклиста 12, 37): перестановка и удаление блоков их не сдвигают. Для показа копия превращается в позиционный оверлей одного хоста и идёт в прежний `siteconfig.localize` (`siteconfig.py:4785`) — витрина не меняется.
- Потолки копии (именованные константы `object_structure.MAX_ROWS = 60`, `MAX_BYTES = 32 * 1024`): превышение — `SchemaError("too_big")` до записи, без обрезки (сегодня `siteconfig._page_block_hosts`, `siteconfig.py:1982-2004`, режет молча). Предпосылка: проверить на самых длинных хостах демо-китов, что 60/32 КБ с запасом.
- Блоки проходят ту же нормализацию, что `page_blocks` (`siteconfig.normalize_page_blocks`) — список допустимых видов на хосте не дублируется.

### 1.5. Миграции (аддитивные)
- Каждая — `AddField(null=True)` без `default`/`db_default`, без индексов на больших таблицах (поиск «у кого своя» — `structure__isnull=False` по таблице одного бизнеса; индекс не нужен: таблицы схемы — сотни–тысячи строк). Если `database-reviewer` потребует индекс — отдельной миграцией `AddIndexConcurrently` с `atomic = False`.
- Первая операция каждой миграции — `RunSQL("SET LOCAL lock_timeout = '5s'", reverse_sql=migrations.RunSQL.noop)`: `ALTER TABLE … ADD COLUMN` берёт `ACCESS EXCLUSIVE` на миллисекунды, но ждёт длинные чтения витрины и держит очередь за собой; таймаут даёт честный отказ шага вместо зависшего сайта. Предпосылка: проверить, что `migrate_schemas --tenant --executor=multiprocessing` (`scripts/deploy.sh:206`) выполняет миграцию одной транзакцией на схему (тогда `SET LOCAL` действует до конца миграции).
- Обратимость: `RemoveField`/`DeleteModel` — штатный откат Django (данные копий при этом теряются, старые ключи целы — §5.3). Без согласия владельца откаты `zero`/`--fake` не делаем (`.claude/rules/project-overrides.md`).
- Время: 136 схем × 5 миграций стопки 18 (+ CreateModel) — ожидание порядка минут на `--executor=multiprocessing`; предпосылка — замер на копии стенда (`migration_state` до/после).
- `CLAUDE.md` §3 «Миграции к деплою» дописывает координатор на верхушке стопки 18.

## 3. Копия с отвязкой вместо наложения

### 3.1. Вариант A2 (утверждён)
- Объект без поля открыт в «Seitenaufbau»: показ A (строки общей, плашка «Gemeinsame Struktur „…“ · gilt für …», подсказка «Sobald Sie hier etwas ändern, …»), ⚙ строк ведёт в окно блока общей структуры с пометкой «gilt für N …».
- Первая операция черновика этой страницы (`add`, `add_row`, `move`, `update`, `hide`/`show`, ★ «Seite») — `aufbau_draft.op` кладёт в черновик `copy_from_shared(...)` и помечает `draft["own"] = True`; дальше правка идёт по копии. Сайт до «Speichern» не меняется (черновик в сессии, `aufbau_draft.py:31`). «Verwerfen» — копии нет.
- Категория сегодня работает так же (`site_schema.category_items` `adopt/reset`, `site_schema.py:971-1000`; подсказка `templates/tenant/site_schema.html:119`) — M6c1 сводит её на тот же путь: `adopt` = A2, `reset` = сброс, хранение — `Category.structure`. Текст «Diese Kategorie zeigt die Blöcke des Katalogs. Sobald Sie hier einen Block hinzufügen, gilt für sie ein eigener Aufbau.» заменяется общими строками артборда (выравнивание «eigener Aufbau» → «Eigene Struktur»; msgid снимает координатор).

### 3.2. «Zur gemeinsamen Struktur zurück»
- Кнопка плашки → операция черновика `reset_shared`: черновик получает строки общей (только чтение) и `draft["own"] = False`; статус «Gemeinsame Struktur übernommen. Mit „Speichern“ wird es wirksam.» в живой области (§7.3). «Speichern» → `object_structure.reset` + `drop_losses`.
- До сброса — список потерь (`losses`): свои блоки поимённо (заголовок блока или вид), отличия разделов («„Bewertungen“ ausgeblendet») и видов («„Ähnliche Produkte“ als Slider»).
- Переводы удалённых блоков уходят вместе с копией (они внутри неё). Старый позиционный оверлей хоста в `site_config` после сброса **не должен оживать**: NULL в поле означает «наследует общий хост», а не «читай старый ключ». Поэтому чтение старых ключей включено только в схеме, которую перенос ещё не прошёл (флаг схемы `site_config["_m6_migrated"]`, §4, §5.1); после переноса запасное чтение в этой схеме выключено целиком.
- Сброс в окне между деплоем и переносом (флага ещё нет): `reset` дополнительно снимает старый ключ этого объекта (`page_override` и хост) через тот же `object_structure` — единственный случай, когда M6 трогает старый ключ; замок `test_fb33_m6c1_draft.py::test_reset_before_transfer_does_not_revive_old_host`.
- Места баннеров: §2.1 `drop_losses`.

### 3.3. Закреплённый порядок разделов (🔒)
`put` для модулей из `detail_parts.FIXED_ORDER_MODULES` (`detail_parts.py:79`; товар, номер) сверяет относительный порядок якорей копии с общей: иначе `SchemaError("fixed_order")`. Свои блоки и скрытие разделов — можно. У услуги, события, тура (и в стопке 19 — Kombi, блог, учитель, Textseite) разделы двигаются.

### 3.4. Конфликт черновика
`aufbau_draft._saved_state` (`aufbau_draft.py:40-62`) у объекта добавляет `state["structure"] = obj.structure` рядом с `override`. Открытый до деплоя черновик объекта, которого коснулся перенос, получит честный `DraftConflict` (вопрос 11) — один раз, без молчаливой перезаписи. Проверка отпечатка уже повторяется под блокировкой Tenant (`aufbau_draft.py:1422-1433`); объект блокируется после (`_lock_object`), и `put` перечитывает `structure` под блокировкой объекта (вопрос 9).

## 4. Команда переноса `migrate_object_structures` (M6b)
- Файлы: `+apps/core/management/commands/migrate_object_structures.py` (разбор аргументов, вывод), `+apps/core/object_structure_migrate.py` (логика; пишет только через `object_structure.put`).
- Шаг `scripts/deploy.sh` сразу после `materialize_page_axes --residue` (`deploy.sh:271-275`), тем же образцом `warn_step` + «Re-run: python manage.py migrate_object_structures»; под `ops_lock` (как шаги выше).
- Аргументы: `--dry-run` (ничего не пишет, тот же отчёт), `--schema <имя>` (повторить одну), `--batch 200`, `--undo` (снимает только копии `origin=migrate` с неизменной `sig`; правленные после переноса — в отчёт, не трогает).
- По схемам (`tenant_context`), в каждой: короткая транзакция с `Tenant.select_for_update()` (тот же замок, что `aufbau_draft.commit`, — черновик и перенос не пересекаются), объекты батчами по 200 с `select_for_update()` и повторной проверкой «поле пусто» под блокировкой (вопрос 9); `bulk_update` нельзя — запись идёт через `put` (один писатель); потолок времени на схему не нужен (объектов с отличиями — единицы, §inventory 11).
- Склейка: `materialize` (поле → `page_override` + `page_blocks["<kind>:<hex>"]` + `i18n.*.page_blocks[host]` → общий хост). Объект без отличий (`object_structure.clean(page_override) == {}`, хоста нет или в нём только якоря в порядке общей) — поле не пишется (наследует).
- Категории: `catalog:<slug>` → `Category.structure` по слагу; хост без категории — призрак. Группы: `promo_group:<md5>` → `PromoGroupPage` по md5 от `distinct Promotion.group` и ключей `promo_groups`; не найдено — призрак. Акции `promo:<hex>` — как объекты. `seite:<slug>` — в стопке 19 (M6g).
- Призраки (хост без объекта, в т. ч. объекта нет и в корзине) — строка отчёта, не удаляются (уборка — стопка 20; при нехватке места до тех пор работает прежний `purge_ghost_hosts`).
- Старые ключи не удаляются. В конце схемы — флаг `site_config["_m6_migrated"]` (дата; пишет `object_structure`, ключ в `siteconfig.normalize` сохраняется — предпосылка, проверить, что `normalize` не выбрасывает неизвестный служебный ключ, иначе — отдельное поле `Tenant`/`ops`-таблица).
- Отчёт на схему одной строкой: `<schema>: product copied=3 inherit=120 ghost=1 kept=0 errors=0 · category … · group …`; итог; код выхода ≠ 0, если упала хоть одна схема (остальные доигрывают, ошибка — `logger.exception` с именем схемы, вопрос 8).
- Идемпотентность: второй прогон — `copied=0`, поле не трогается, флаг уже стоит.

## 5. Обратная совместимость и откат

### 5.1. Порядок чтения (`effective_rows`)
1. черновик (только превью «Vorschau», как сегодня `DRAFT_KEY`, `object_structure.py:47`, `aufbau_draft.overlay :336-369`);
2. `obj.structure` (знакомая `v`);
3. старые ключи — только если в схеме нет флага `_m6_migrated` (§3.2);
4. общий хост типа.

### 5.2. Порядок выката
1. стопка 18 одним деплоем (рекомендация; вопрос §12 №4): `migrate_schemas` (поля) → новый код (читает поле, затем старые ключи; пишет только поле) → шаг `migrate_object_structures`. Окно между миграциями и шагом безопасно: правка в черновике делает `materialize` из старых ключей, команда объект с полем пропускает.
2. стопка 19 — тем же порядком для Combo/BlogPost/ContentPage/Teacher.
3. стопка 20 (M7) — снятие старых ключей, `page_override`, потолков и запасного чтения.

### 5.3. Откат кода после переноса
Данные в старых ключах целы — старый код покажет структуру на момент переноса. Потеряются правки, сделанные после деплоя (они только в поле). Перед откатом — `migrate_object_structures --undo` (снимет нетронутые копии; правленные — список в отчёте владельцу). Откат миграций — только с согласия владельца.

### 5.4. Демо
`SEEDER_VERSION` 24 → 25 (M6b): пересев `seed_demo_tenants --group all --changed --jobs 3` после деплоя прогоняет перенос в демо-схемах. Новых своих структур в китах нет (киты не кладут свои блоки объектам — inventory §11; категории: pranasy, aktionsmarkt, clothing, catering).
