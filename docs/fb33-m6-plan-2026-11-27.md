### 1.2. `PromoGroupPage`
- Поля: `id` UUID, `key = CharField(max_length=50, unique=True)` (как `Promotion.group`, `apps/promotions/models.py:387`), `structure` JSON null, `created_at/updated_at` (`TimestampedModel`). Таблица новая и пустая — индекс `unique` на ней бесплатен.
- Ключ — точная строка `Promotion.group` **без обрезки** (то же правило, что `siteconfig.promo_group_host`, `siteconfig.py:1447-1455`: «Sale» и «Sale » — разные группы). **Регистр — как сегодня: «Sale» и «sale» — разные группы** (фильтр витрины — по точному значению, комментарий `promotions/models.py:383-385`; хост — md5 точной строки, `siteconfig.py:1455`) — M6 это не меняет. Неверный ключ — `SchemaError("group_key")`, строка не создаётся.
- Строка создаётся только писателем при первой правке страницы группы (A2) или переносом; пустых строк нет. **Создаётся только для живой группы** (ключ есть в `site_schema.live_promo_groups()`, `site_schema.py:827-847`; ревью №28) — неизвестный ключ из запроса строку не заводит.
- Создание (ревью №15): в транзакции `commit` — `Tenant.select_for_update()` → `PromoGroupPage.objects.select_for_update().get_or_create(key=…)`; `IntegrityError` (вторая вкладка создала строку между чтением и вставкой) — в `transaction.atomic()` вложенной точкой сохранения, затем повторное `select_for_update().get(key=…)`. Порядок блокировок — Tenant → строка группы, как у объектов (`aufbau_draft.py:1422`, `_lock_object :1631`).
- **Переименование группы.** Действия «переименовать группу» в коде нет (grep `rename|umbenenn|update(group=` по `apps/promotions` — пусто); группа меняется по одной акции в её форме. ### 1.3. Формат копии (версия 1)
```
{
  "v": 1,                         # версия формата; незнакомая → витрина читает «наследует» (§1.3.1)
  "origin": "edit" | "migrate" | "seed" | "clone",
  "sig": "<sha1 всей копии>",     # rows+layout+i18n; пересчитывает каждый put; --undo снимает лишь копии с sig от переноса
  "layout": "standard|tabs|breit",# только LAYOUT_KINDS (object_structure.py:37)
  "rows": [                       # ПОЛНАЯ копия строк общего хоста на момент копии, в его формате
    {"key": "<раздел>", "enabled": true|false, ...},        # якорь раздела (detail_parts.anchors)
    {"id": "<12 hex>", "key": "<вид блока>", "enabled": .., "data": {...}, "width": ..}  # блок
  ],
  "i18n": {"<язык>": {"<id блока>": {"data": {"<поле>": "<текст>"}}}}   # переводы по id, не по позиции
}
```
- Формат строк — тот, что `site_schema.load_items` отдаёт для общего хоста детали (`site_schema.py:3367-3370`, `detail_parts.edit_rows`); у категории — строки хоста `catalog`; у группы — строки `promo_group`/`promos`. **У акции — как сегодня** (ревью №4): вида `promo` нет в `detail_parts.OBJECT_SHARED` (`detail_parts.py:138-144`), её строки — только свои блоки хоста `promo:<hex>` (`detail_parts.object_edit_rows`, `site_schema.py:3371-3374`); разделы `promo_detail` («Angebot», `share/card/related` — ключи уровня сайта `promo_show_*`, `detail_parts.py:92-96`) в копию акции НЕ входят и остаются общими. Точный вид якоря (флаг видимости — `enabled` или иной) — предпосылка, проверить в M6a по `detail_parts.lift` (`detail_parts.py:527`).
- **id блоков копии — те же, что у общей** (ревью №7): `materialize` id не перевыпускает (иначе метка «nur hier» — «id нет в общей» — легла бы на все блоки, а переводы общего хоста не нашли бы своих строк). `put` принимает любой id, который принимает `siteconfig.normalize_page_blocks` (12 hex и id китов `pb-kit-N`, `demo_kits.py:25683`); у копии категории, рождённой прежним `adopt` (`site_schema.py:996` выдаёт новые id), «nur hier» считается против общей по id, а для таких копий при переносе id сверяются по `siteconfig._match_items` (`siteconfig.py:4472`) с блоками общего хоста — совпавшие получают id общего.
- Переводы внутри копии — **по id блока** (вопрос чеклиста 12, 37): перестановка и удаление блоков их не сдвигают. Источники при `materialize` (ревью №8): переводы общего хоста `i18n.<язык>.page_blocks[<общий хост>]` (позиция → id через `siteconfig._match_items` по нормализованному списку общего хоста) **и поверх них** позиционные переводы старого хоста объекта `i18n.<язык>.page_blocks[<kind>:<hex>]` (позиция → id по списку старого хоста). Для показа копия превращается в позиционный оверлей одного хоста и идёт в прежний `siteconfig.localize` (`siteconfig.py:4785`) — витрина не меняется.
- **D9 для копии** (ревью №8): «Speichern» черновика на языке перевода пишет в копию только `copy["i18n"][<язык>]`; немецкая база строк (`rows[*].data`) остаётся как была (тот же разбор, что `split_translation` у общих хостов, `sa-i18n` §грабли «Save Студии на языке перевода»).
- Потолки копии (именованные константы `object_structure.MAX_ROWS = 60`, `MAX_BYTES = 32 * 1024`) — **по сериализованной копии целиком, с `i18n`** (`len(json.dumps(copy, ensure_ascii=False).encode())`): превышение — `SchemaError("too_big")` до записи, без обрезки (сегодня `siteconfig._page_block_hosts`, `siteconfig.py:1982-2004`, режет молча). Предпосылка: проверить на самых длинных хостах демо-китов, что 60/32 КБ с запасом.
- Блоки проходят ту же нормализацию, что `page_blocks` (`siteconfig.normalize_page_blocks`) — список допустимых видов на хосте не дублируется.

#### 1.3.1. Проверка ввода `put` (ревью №27, №10)
Копия приходит из черновика сессии, то есть от клиента. `put` перед записью:
- `v`, `origin`, `sig` **ставит сервер** (`v = FORMAT_VERSION`, `origin` — аргумент вызывающего, `sig` — пересчёт); пришедшие в копии значения отбрасываются;
- `i18n`: ключи — только языки бизнеса (`apps/core/i18n_input.py:17` `extra_locales(tenant)`), id — только id из `rows`, поля — только текстовые поля вида блока; HTML полей — `apps/core/richtext.py` (тот же санитайзер и потолок длины поля, что `block_i18n`); лишнее — отказ `SchemaError("i18n")`, не тихое отбрасывание;
- id в `rows` уникальны; `key` блока — из видов, допустимых на общем хосте (`siteconfig.normalize_page_blocks` + реестр видов хоста); вид раздела — из `detail_sections.sections_for(module)`; `layout` — из `LAYOUT_KINDS`; глубина вложенности `data` — не больше `MAX_DEPTH = 6` (константа);
- незнакомая `v` в **уже сохранённом** поле: `put` не перезаписывает её молча — `SchemaError("version")` (копию из более новой версии кода не затираем A2-копией общей); витрина читает такое поле как «наследует» с `logger.warning` **раз на объект на процесс** (множество `(schema, kind, pk)` в модуле), не на каждый рендер; команда переноса такой объект пропускает и пишет в отчёт `unknown_version=N`.
- Пустое `{}` и в `put`, и в `reset` записывается как `None` (ревью №11): поля «пустой словарь» в базе не бывает.

### 1.5. Миграции (аддитивные)
- Каждая — `AddField(null=True)` без `default`/`db_default`, без индексов на больших таблицах (поиск «у кого своя» — `structure__isnull=False` по таблице одного бизнеса; индекс не нужен: таблицы схемы — сотни–тысячи строк). Если `database-reviewer` потребует индекс — отдельной миграцией `AddIndexConcurrently` с `atomic = False`.
- Первая операция каждой миграции — `RunSQL("SET LOCAL lock_timeout = '5s'", reverse_sql=migrations.RunSQL.noop)`: `ALTER TABLE … ADD COLUMN` берёт `ACCESS EXCLUSIVE` на миллисекунды, но ждёт длинные чтения витрины и держит очередь за собой; таймаут даёт честный отказ шага вместо зависшего сайта. **Миграции атомарные** (`atomic = True`, по умолчанию; `SET LOCAL` вне транзакции молча не действует — ревью №17): замок проверяет у каждой миграции M6 `atomic is True` и что `RunSQL` с `lock_timeout` выполняется внутри блока (`connection.in_atomic_block` в `RunPython`-проверке или разбор операций). Предпосылка: проверить, что `migrate_schemas --tenant --executor=multiprocessing` (`scripts/deploy.sh:206`) выполняет миграцию одной транзакцией на схему.
- **Политика деплоя при таймауте** (ревью №17): `lock_timeout` срабатывает → параллельный `migrate_schemas` падает на этой схеме; `deploy.sh:206-214` уже повторяет его один раз по одной схеме и при втором отказе выходит (`exit "$rc"`) до подъёма нового web. Дальше — ручной повтор деплоя 2–3 раза с паузой 30–60 с (`./scripts/deploy.sh single` идемпотентен; применённые схемы пропускаются); старый код с новой nullable-колонкой работает (колонку не читает, `INSERT` без неё даёт NULL = «наследует»). Запись — в `docs/project-memory.md` §2 (ops) координатором.
- **Время и окно** (ревью №18): `ACCESS EXCLUSIVE` ждёт самую долгую открытую транзакцию на таблице (отчёты, выгрузки, Celery) — поэтому до деплоя координатор замеряет `migrate_schemas` на копии стенда (`migration_state` до/после, время по схемам) и деплой стопки 18 идёт вне пиковых часов витрин DACH (не 11–14 и 17–20 ч по Берлину); строка в чеклист деплоя владельцу (§15 №4).
- Обратимость: `RemoveField`/`DeleteModel` — штатный откат Django (данные копий при этом теряются, старые ключи целы — §5.3). Без согласия владельца откаты `zero`/`--fake` не делаем (`.claude/rules/project-overrides.md`).
- Время: 136 схем × 5 миграций стопки 18 (+ CreateModel) + одна public — ожидание порядка минут на `--executor=multiprocessing`; замер — выше.
- N+1 при `defer` (ревью №19): листинги откладывают `structure` (`.defer("structure")`, §11 в31); `structure_of(obj)` на отложенном поле не читает его по одному — вызывающий в цикле обязан взять поле пачкой (`object_structure.structure_map(model, pks)` одним `values_list("pk", "structure")`), `structure_of` при `"structure" in obj.get_deferred_fields()` возвращает `None` только через карту, без запроса; `SoftDeleteManager` (`apps/core/models.py:107-128`) учтён — карта строится по `all_objects`, чтобы корзина не давала ложное «наследует».
- `CLAUDE.md` §3 «Миграции к деплою» дописывает координатор на верхушке стопки 18.

### 1.6. Флаг переноса — поле `Tenant.m6_migrated_at` (ревью №1)
- **Не в `site_config`.** Ключ `_m6_migrated` в `site_config` ненадёжен: `siteconfig.normalize` отбрасывает неизвестные секции (`siteconfig.py:5694-5697`, докстринг «Неизвестные секции отбрасываются»), а ~30 писателей пишут `site_config` целиком из снимка запроса (тот же довод, что у `Tenant.published_at`, `apps/tenants/models.py:72-76`) — флаг стирался бы первым же Save, и витрина в схеме, уже прошедшей перенос, снова читала бы старые ключи (сброс «оживал» бы). Через `site_config` его можно было бы и подделать из клиента.
- Поле: `Tenant.m6_migrated_at = models.DateTimeField(null=True, blank=True, default=None)` (public-схема, миграция `tenants/0044_fb33_m6_migrated_at`, M6a; `AddField` nullable — без переписи таблицы). Ни одна форма, `site_config` и черновик его не пишут; писатель — только `object_structure.mark_migrated(tenant)` / `clear_migrated(tenant)` через `Tenant.objects.filter(pk=…).update(m6_migrated_at=…)` (замок «один писатель» §2.4 включает и это поле).
- Ставится командой переноса в конце схемы **только при `errors=0` и `unknown_version=0`** и **только если у схемы нет остатка FB-31.7** (`apps/core/page_axes_residue.py:105` `tenant_residue(tenant)` пусто). Почему не «`materialize_page_axes` пишет через `put`» (ревью №2): `materialize_page_axes` — чистые функции над словарём `site_config` (`page_axes_objects.migrate_categories/promos/groups`, `page_axes_objects.py:162,266,321`) с откатом всего сайта целиком и сверкой отрисованных страниц (`page_axes_migration.migrate_objects`, `page_axes_migration.py:371-400`); перевод на `put` по объектам ломает эту «целиком или никак» сверку и переписывает недоигранный FB-31.7, прогон которого — за владельцем. Поэтому: остаток ≠ 0 → флаг не ставится, старые ключи в схеме читаются дальше (поле, если есть, всё равно главнее), отчёт `residue=N`; следующий деплой повторяет перенос (для объектов с полем — no-op).
- `materialize_page_axes` в схеме с флагом не пишет ничего (одна проверка в начале схемы, строка отчёта «übersprungen: M6»): код шаблона объекта в такой схеме больше не читается, остатка по построению нет.
- Команда переноса пропускает схемы с флагом (кроме `--force-schema <имя>`); `--undo` снимает флаг первым шагом (§5.3); `reset` объекта снимает старые ключи этого объекта **всегда** (и до, и после флага — повтор переноса после сброса их не оживит; §3.2); `materialize` в схеме с флагом старые ключи не читает.

## 3. Копия с отвязкой вместо наложения

### 3.1. Вариант A2 (утверждён)
- Объект без поля открыт в «Seitenaufbau»: показ A (строки общей, плашка «Gemeinsame Struktur „…“ · gilt für …», подсказка «Sobald Sie hier etwas ändern, …»). **⚙ строки в режиме A открывает окно блока ЭТОЙ страницы и правит КОПИЮ** (ревью №33): первая «Übernehmen» в окне — операция `update`, она и рождает копию по A2; общую структуру окно со страницы объекта не правит никогда. «gilt für N …» и подсказка A2 — в `aria-describedby` кнопки ⚙ (id текста плашки). Общая правится только ссылкой «Gemeinsame Struktur bearbeiten →» (страница общего типа), ссылка — под `leaveOk()` / `data-ps-leave` (несохранённый черновик не теряется молча; «→» — `aria-hidden`; ревью №40).
- Первая операция черновика этой страницы (`add`, `add_row`, `move`, `update`, `hide`/`show`, ★ «Seite») — `aufbau_draft.op` кладёт в черновик `copy_from_shared(...)` и помечает `draft["own"] = True`; дальше правка идёт по копии. Сайт до «Speichern» не меняется (черновик в сессии, `aufbau_draft.py:31`). «Verwerfen» — копии нет.
- Переход A → B озвучивается (ревью №32): в постоянную живую область обёртки схемы (§7.3) — «Diese Seite hat jetzt eine eigene Struktur. Mit „Speichern“ wird es wirksam.» (новый msgid, §7.4); фокус остаётся на элементе, с которого шла правка (окно закрывается на свою кнопку ⚙ строки); плашка B появляется видимой, текст в sr не дублирует.
- Категория сегодня работает так же (`site_schema.category_items` `adopt/reset`, `site_schema.py:971-1000`; подсказка `templates/tenant/site_schema.html:119`) — M6c1 сводит её на тот же путь: `adopt` = A2, `reset` = сброс, хранение — `Category.structure`. Текст «Diese Kategorie zeigt die Blöcke des Katalogs. Sobald Sie hier einen Block hinzufügen, gilt für sie ein eigener Aufbau.» заменяется общими строками артборда (выравнивание «eigener Aufbau» → «Eigene Struktur»; msgid снимает координатор).

### 3.2. «Zur gemeinsamen Struktur zurück»
- Кнопка плашки → операция черновика `reset_shared`: черновик получает строки общей (только чтение) и `draft["own"] = False`; статус «Gemeinsame Struktur übernommen. Mit „Speichern“ wird es wirksam.» в живой области (§7.3). «Speichern» → `object_structure.reset`.
- До сброса — список потерь (`losses`): свои блоки поимённо (заголовок блока или вид), отличия разделов («„Bewertungen“ ausgeblendet») и видов («„Ähnliche Produkte“ als Slider»); блок «Banner» этой страницы — отдельной строкой (§0.3 №8).
- Переводы удалённых блоков уходят вместе с копией (они внутри неё). Старый позиционный оверлей хоста в `site_config` после сброса **не должен оживать**: NULL в поле означает «наследует общий хост», а не «читай старый ключ». Поэтому `reset` **всегда** снимает старые ключи своего объекта (`page_override`, хост, переводы хоста) — и до, и после переноса (ревью №1): повтор команды после сброса их не найдёт; а чтение старых ключей выключено в схеме с `Tenant.m6_migrated_at` (§1.6, §5.1).
- Снятие старых ключей пишет `site_config` — поэтому `reset` идёт внутри транзакции `commit` под уже взятой блокировкой Tenant и правит **перечитанный под блокировкой** `site_config` (ревью №20; тот же приём, что `aufbau_draft.py:1422-1433`), не снимок запроса.
- Баннеры: `Banner.show_on` сброс не трогает — места принадлежат баннеру, а не блоку (§0.3 №8, ревью №26); баннеры этой страницы после сброса встают туда, где их ставит общая структура (блок «Banner» общей или место по умолчанию `auto_place`). Права на баннеры сбросу не нужны.
- Сброс — POST + CSRF (ревью №31): форма в `<dialog>` и страница без JS шлют код объекта; сервер сверяет его с кодом страницы черновика в сессии (`draft["code"]`), иначе 400 без записи; GET страницы потерь `?seite=<код>&zuruecksetzen=1` требует `website.view` **и** право просмотра объекта вида (иначе 403 — список потерь называет блоки и тексты); неизвестный/удалённый код — 404 **без создания черновика**.

### 3.3. Закреплённый порядок разделов (🔒)
`put` там, где `detail_parts.fixed_order(<общий хост>)` (`detail_parts.py:164-166`: `FIXED_ORDER = frozenset(FIRST_SCREEN)` `:122` — `product_detail`, `stay_detail`; ревью №3), сверяет относительный порядок якорей копии с общей: иначе `SchemaError("fixed_order")`. Свои блоки и скрытие разделов — можно. Не `FIXED_ORDER_MODULES` (`:79-81`) — это модули своих страниц и форм, не товар и номер. У услуги, события, тура разделы двигаются. Стопка 19: `fixed_order` истинна и у `combo_detail` (модуль `combo`) и у хоста своей страницы (модуль `page`) — по решению §15 №7 срезы M6d/M6e снимают эти хосты из закреплённого набора (разделы двигаются и в общей, и в копии); блог и учитель — двигаются.

### 3.4. Конфликт черновика
`aufbau_draft._saved_state` (`aufbau_draft.py:40-62`) у объекта добавляет `state["structure"] = obj.structure` рядом с `override`. Открытый до деплоя черновик объекта, которого коснулся перенос, получит честный `DraftConflict` (вопрос 11) — один раз, без молчаливой перезаписи. Проверка отпечатка уже повторяется под блокировкой Tenant (`aufbau_draft.py:1422-1433`); объект блокируется после (`_lock_object`), и `put` перечитывает `structure` под блокировкой объекта (вопрос 9).

**Отпечаток общей в A2** (ревью №9): копия A2 снята с общей в момент первой правки. Если общую структуру типа (другой вкладкой или сотрудником) правят до «Speichern» копии, копия устарела — её запись молча закрепила бы старые строки общей. Поэтому `copy_from_shared` кладёт в черновик `draft["own_base"] = sha1(строки + переводы общего хоста)`; `commit` под блокировкой Tenant пересчитывает отпечаток общей и при расхождении даёт `DraftConflict` с текстом прежнего конфликта (без новой строки интерфейса); после «Verwerfen» и повторной правки копия снимается заново.

## 4. Команда переноса `migrate_object_structures` (M6b)
- Файлы: `+apps/core/management/commands/migrate_object_structures.py` (разбор аргументов, вывод), `+apps/core/object_structure_migrate.py` (логика; пишет только через `object_structure.put`).
- Шаг `scripts/deploy.sh` сразу после `materialize_page_axes --residue` (`deploy.sh:271-275`), тем же образцом `warn_step` + «Re-run: python manage.py migrate_object_structures»; под `ops_lock` (как шаги выше).
- Аргументы: `--dry-run` (ничего не пишет, тот же отчёт), `--schema <имя>` (повторить одну; имя сверяется с реестром `Tenant.objects.filter(schema_name=…)`, не подставляется в `search_path` как есть — неизвестное имя → ошибка и код выхода ≠ 0; ревью №30), `--force-schema <имя>` (пройти схему с флагом заново), `--batch 200`, `--undo` (§5.3).
- **Предвыбор кандидатов** (ревью №16): до любой блокировки — чтение без блокировок: ключи `page_blocks`, совпадающие с `is_structure_host`, + `pk` объектов с непустым `page_override` (`all_objects.exclude(page_override={})` по каждой модели) + ключи переводов старых хостов. `materialize` зовётся **только для кандидатов**, не по всем объектам схемы. Объект вне кандидатов — `inherit` без записи.
- **Короткие транзакции на батч**: на каждый батч кандидатов (по 200) — своя транзакция: `Tenant.select_for_update()` (тот же замок, что `aufbau_draft.commit`, — черновик и перенос не пересекаются; порядок Tenant → объекты, как в `commit`), перечитать `site_config` под блокировкой, объекты батча — `select_for_update()` с повторной проверкой «поле пусто» (вопрос 9), запись через `put(..., origin="migrate", system=True)`; `bulk_update` нельзя (один писатель). Блокировка Tenant держится на один батч, а не на всю схему — витрина и черновики схемы не ждут весь перенос.
- **Корзина** (ревью №22): кандидаты и запись — по `Model.all_objects` (удалённые мягко тоже получают копию: иначе восстановление из корзины вернуло бы объект без своей структуры, а старые ключи после флага уже не читаются); призрак — хост, у которого объекта нет и в `all_objects` (у групп — ключа нет ни у одной акции `Promotion.all_objects`, вкл. неактивные и удалённые).
- Склейка: `materialize` (поле → `page_override` + `page_blocks["<kind>:<hex>"]` + `i18n.*.page_blocks[host]` → общий хост с его переводами; id — от общей, §1.3). Объект без отличий (`object_structure.clean(page_override) == {}`, хоста нет или в нём только якоря в порядке общей) — поле не пишется (наследует).
- Категории: `catalog:<slug>` → `Category.structure` по слагу (`Category.all_objects`); хост без категории — призрак. Группы: `promo_group:<md5>` → `PromoGroupPage` по md5 от `distinct Promotion.all_objects.group` и ключей `promo_groups`; не найдено — призрак. Акции `promo:<hex>` — как объекты. `seite:<slug>` — в стопке 19 (M6g).
- Призраки — строка отчёта, не удаляются (уборка — стопка 20; при нехватке места до тех пор работает прежний `purge_ghost_hosts`).
- **Кэши процесса** (ревью №30): команда идёт по 136 схемам в одном процессе; любой кэш модульного уровня, ключ которого не содержит схему (кэш строк объекта на время запроса §2.1, множество «уже предупреждали о незнакомой `v`» §1.3.1, `siteconfig`-кэши), между схемами сбрасывается или ключуется `(schema_name, …)`. Замок — две схемы с одинаковыми слагами категорий и одинаковыми ключами групп: копия одной не попадает в другую.
- Старые ключи не удаляются. В конце схемы — флаг `Tenant.m6_migrated_at` (§1.6) **только если** `errors=0`, `unknown_version=0` и `page_axes_residue.tenant_residue(tenant)` пусто; иначе флага нет, отчёт называет причину, следующий деплой повторяет схему (объекты с полем — no-op).
- Отчёт на схему одной строкой: `<schema>: product copied=3 inherit=120 ghost=1 kept=0 unknown_version=0 errors=0 · category … · group … · residue=0 · flag=set`; **без текстов бизнеса** (ни заголовков блоков, ни имён объектов — только счётчики и pk/hex; ревью №30); итог; код выхода ≠ 0, если упала хоть одна схема (остальные доигрывают, ошибка — `logger.exception` с именем схемы, вопрос 8).
- Идемпотентность: второй прогон — схема с флагом пропускается целиком (`skipped=flag`); без флага — `copied=0`, поле не трогается.

1. стопка 18 одним деплоем (рекомендация; вопрос §15 №4): `migrate_schemas` (поля, public `tenants/0044` — первой, `migrate_schemas --shared` в `deploy.sh` идёт до `--tenant`) → новый код (читает поле, затем старые ключи; пишет только поле) → шаг `migrate_object_structures`. Окно между миграциями и шагом безопасно: правка в черновике делает `materialize` из старых ключей, `reset` снимает старые ключи своего объекта, команда объект с полем пропускает. Деплой — вне пиковых часов, после замера на стенде (§1.5).
2. стопка 19 — тем же порядком для Combo/BlogPost/ContentPage/Teacher.
3. стопка 20 (M7) — снятие старых ключей, `page_override`, потолков и запасного чтения.

### 5.3. Откат кода после переноса
Данные в старых ключах целы — старый код покажет структуру на момент переноса (кроме объектов, сброшенных после деплоя: их старые ключи `reset` снял — старый код покажет общую, это и есть результат сброса). Потеряются правки, сделанные после деплоя (они только в поле). Перед откатом — `migrate_object_structures --undo` (ревью №14):
- первым шагом снимает `Tenant.m6_migrated_at` (`clear_migrated`) — старые ключи снова читаются запасным путём;
- снимает только копии `origin="migrate"`, у которых `sig` совпадает с пересчитанным по **всей** копии, включая `i18n` (новый перевод, добавленный после переноса, — тоже правка: такая копия остаётся, в отчёт);
- пишет через `reset(kind, obj, system=True)` в тех же коротких транзакциях Tenant → объект, но **без** снятия старых ключей (флаг `keep_old_keys=True` только у `--undo`) и с журналом (`apps/audit/services.py:23` `audit_event`, строка на объект: схема, вид, pk, «undo»);
- правленные копии — список в отчёте владельцу (pk/hex, без текстов).
Откат миграций — только с согласия владельца.
