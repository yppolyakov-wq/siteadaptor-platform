## 4. Хранение и формат

### 4.1. Поле `structure` — три состояния

Абстрактный миксин `OwnStructureMixin` в `apps/core/models.py` (поле + охрана `save`, §5.3):

```python
structure = models.JSONField(default=structure_born, db_default={}, blank=True)
```

| Значение | Состояние | Что читается |
|---|---|---|
| `{}` | **не тронуто** (`legacy`) | старое хранилище, как сегодня, байт-в-байт: `page_override`, хост `<kind>:<hex>` / `catalog:<slug>` / `promo_group:<md5>`, их переводы |
| `{"v": 1}` (+ необязательные `src`, `lh`) | **наследует** (`inherit`) | только общая структура типа; старое хранилище этого объекта **не читается** |
| `{"v": 1, "rows": […], …}` | **своя** (`own`) | только копия |

- «Своя» ⇔ есть ключ `rows`. «Наследует» ⇔ `v` есть, `rows` нет. Сброс пишет ровно `{"v": 1}`.
- `default=structure_born` (Python): объект, **созданный новым кодом, рождается `{"v": 1}`** — новая категория
  со старым слагом не подхватит мёртвый хост `catalog:<slug>`, а `_pin_own_categories` не напишет ей старое
  хранилище (A-12). `db_default={}` — для строк, которые вставляет старый web в окне деплоя, и для всех
  существующих строк (`ADD COLUMN … jsonb NOT NULL DEFAULT '{}'` на Postgres 16 — правка каталога без
  переписи таблицы; подтверждено ревью 2 database).
- **Флага на схему нет.** `Tenant.m6_migrated_at`, миграция `tenants/0044`, функции `mark_migrated /
  clear_migrated` сняты: «перенесено» — свойство объекта. Перенос не зависит от остатка FB-31.7, сброс не
  «оживает» по построению (Р1-1, Р1-2, П-3).
- **Шов для тестов** (§3 №14): `structure_born()` возвращает копию модульной константы
  `apps.core.models.STRUCTURE_BORN = {"v": 1}`. Корневой `conftest.py` получает autouse-фикстуру, которая для
  тест-модулей из списка `+apps/core/tests/m6_legacy_modules.txt` подменяет константу на `{}` — тесты старого
  хранилища и эталоны «до» (`golden_fb31p5`, `golden_fb3016`, `golden_fb31p3`) идут старым путём без правки
  ≈ 70 файлов. Список строится grep-ом в срезе M6a1 (команда — §12.5), **может только сокращаться** (замок
  `test_m6_legacy_module_list_only_shrinks`), снимается в стопке 20. Новые тесты M6 идут с боевым значением.
  Прод-код константу не меняет (AST-замок «один писатель» видит присваивание `STRUCTURE_BORN`).

### 4.2. Формат копии, версия 1

```
{"v": 1,
 "rows":     [ {"key": "<раздел>"},                                  # якорь раздела
               {"id": "<id>", "key": "<вид блока>", "enabled": …, "data": {…}, "width": …},   # блок
               {"key": "<ось>", "style": …, "grid": …, "focus": …} ],  # строка оси / вида (категория, группа, акция)
 "sections": {"hidden": ["<раздел>", …], "order": ["<раздел>", …], "layout": "standard|tabs|breit"},
 "settings": {"<код настройки>": <значение>, …},
 "i18n":     {"<язык>": {"<id блока>": {"data": {"<поле>": "<текст>"}}}},
 "src":      "migrate" | "seed" | "clone",      # необязательный маркер происхождения
 "lh":       "<sha1 старых данных на момент переноса>"}              # только вместе с src = "migrate"
```

- **`rows`** — в формате строк общего хоста типа (`site_schema.load_items`, `apps/core/site_schema.py:3349`;
  `detail_parts.edit_rows`, `apps/core/detail_parts.py:407`): блоки с `id`, якоря разделов, строки осей без
  `id` (`siteconfig.page_builtin_keys`, `apps/tenants/siteconfig.py:1766`). У акции — строки `promo_detail`
  (ось `offer`, общие блоки) плюс свои блоки; у категории — строки хоста `catalog`; у группы — строки по
  цепочке `promo_group:<md5>` → `promo_group` → `promos` (`siteconfig.page_rows`, `siteconfig.py:1922`).
- **`sections`** — три ключа **всегда все три**: `hidden` — полный список скрытых разделов (включая разделы,
  которые у типа скрываются флагами `detail_parts.VISIBILITY_KEYS`, `detail_parts.py:87-106` —
  `promo_show_*`, `combo_show_*`, `blog_show_more`; в копии флагов нет, только имена разделов); `order` —
  полный порядок разделов модуля; `layout` — у видов из `LAYOUT_KINDS`, у прочих `"standard"`.
- **`settings`** — **каждый** код из `object_structure.setting_codes(kind)` (реестр: `page_settings.cabinet_settings(<тип>)`
  минус `DESIGN_SETTINGS` плюс коды строк `site_schema.SETTING_ROWS`, `site_schema.py:4169`) со значением,
  действовавшим на момент копии, **в том числе со значением по умолчанию** — иначе поздняя общая правка
  протекла бы в «отвязанную» страницу (A-8, решение 24). Виды разделов («Ähnliche Produkte» — Raster / Slider /
  число колонок) — это настройка `product_related` → ключ `detail_related_layout`.
- **`i18n`** — по `id` блока, не по позиции (A-9, Р1-8): перестановка и удаление блоков переводы не сдвигают,
  `siteconfig.realign_block_overlays` для копии не нужен. Строки осей без `id` переводимых полей не несут
  (предпосылка — проверить в срезе M6a2 по `block_i18n.TRANSLATABLE`; если несут — ключ перевода `@<key>`).
- **`src`** — маркер «записано не пользователем и после этого не правлено»: `"migrate"` (перенос — и у
  «наследует от переноса» тоже: `{"v": 1, "src": "migrate"}`), `"seed"` (сидер), `"clone"` не хранится —
  **клон и вставка `src` срезают**; любая пользовательская запись `src` и `lh` снимает (D-5, D-6, A-10).
- **`lh`** — отпечаток старых данных объекта на момент переноса: по нему `--residue` видит правки старого web,
  сделанные после переноса (откат кода, D-7).
- **`id` блоков копии — те же, что у общей** (Р1-7): метка «nur hier» = «`id` нет среди блоков общей сейчас»,
  строка потерь «geänderte Blöcke» = «`id` есть в общей, а `data` или перевод отличаются». Коллизия внутри
  одной копии (свой блок и общий с одним `id` — сидеры дают `pb-kit-N` в каждом хосте,
  `demo_kits.py:25680-25687`, Л9): у **своего** блока при копии новый `id`, его перевод едет с ним парой.
- **Не входят в структуру**: «Kartenform» (`card_style`, решение 7), свои вопросы FAQ объекта (`faq`,
  `faq_i18n`, решение 18), SEO страницы, места баннеров (решения 8, 13), общие настройки «Design», шапка и
  подвал, вид группы в списке акций `promo_groups[key]` (он и сегодня свой у каждой группы; предпосылка —
  проверить в срезе M6c2, что страница группы читает из него только то, что вошло в `settings`).
- **Версия.** Незнакомая `v` читается как «наследует» с `logger.warning` раз на объект на процесс (ключ
  множества — `(schema_name, kind, pk)`); писатель её не перезаписывает (`SchemaError("version")`); перенос
  пропускает и пишет в отчёт (Р1-10).

### 5.2. Порядок записи (`write`)

1. **Права — первым шагом и безусловно** (S-1, Р1-23): `user is None` → отказ `SchemaError("rights")` (сегодня
   образец обратный: `if user is not None and not allowed`, `aufbau_draft.py:1653`). Проверяются **оба** права:
   `website.edit` и право формы объекта из `KINDS`; вид без маршрута права → отказ; неизвестный вид —
   `SchemaError("kind")`, не `KeyError`.
2. `validate` (§5.4) и потолки (§4.4) — до блокировок.
3. Блокировки в неизменном порядке **строка `Tenant` → строка объекта** (как сегодня:
   `aufbau_draft.py:1422`, `_lock_object :1631`): `Tenant.objects.select_for_update().get(pk=…)` — она же
   сериализует копию с правкой общей структуры; затем `Model.objects.select_for_update().filter(pk=…).first()`
   (у мягко удаляемых — живые). Замок порядка — AST по `object_structure.py` и ядру переноса
   (`test_m6_lock_order_tenant_then_object`, D-15).
4. **Сверки под блокировкой, до первой записи** (вопрос 9): состояние и отпечаток сохранённой структуры
   (`base` — sha1 сохранённого значения поля на момент открытия черновика) — иначе `DraftConflict`; при первой
   копии (A2) — отпечаток общей `shared_base` (строки + настройки + переводы общего хоста на момент копии):
   общую правили до «Speichern» → `DraftConflict` существующим сообщением (Р1-9). `force` конфликт отпечатка
   снимает, **права и `validate` — нет** (S-2).
5. Объект исчез (строки нет) → `SchemaError("gone")`, черновик снят, частичной записи нет (Л25).
6. Группа акций: строка `PromoGroupPage` — `get_or_create(key=…, defaults={"host": …})` **только здесь**, под
   блокировкой `Tenant`, во вложенной точке сохранения (`IntegrityError` → повторное `get`); витрина и чтение
   строку не создают (D-15, S-7).
7. Запись — `Model.objects.filter(pk=…).update(structure=…, updated_at=now())`: `post_save` не шлётся (нет
   пересинхронизации портала на каждое «Speichern» — портал структуру не читает, Л14); `updated_at` — как
   сегодня у записи разделов (`aufbau_draft.py:1626-1627`). Пользовательская запись снимает `src` и `lh`.
8. `transaction.on_commit` → `bump_storefront_cache` (§8.4).

`write_system` — те же шаги 2–8 без шага 1; `updated_at` не трогает (вид страницы не изменился); при
`caller="migrate"` блокировка `Tenant` — через `config_migration.lock` с `lock_timeout` (§8.1).

### 5.3. Охрана полного `save()` — у всех двенадцати моделей

По образцу `Tenant.save` (`apps/tenants/models.py:446-457`):

```python
def save(self, *args, **kwargs):
    if not self._state.adding and self.pk is not None and kwargs.get("update_fields") is None:
        deferred = self.get_deferred_fields()
        kwargs["update_fields"] = [f.name for f in self._meta.concrete_fields
                                   if not f.primary_key and f.name != "structure" and f.attname not in deferred]
    ...
```

- `save(update_fields=[…, "structure", …])` извне писателя — `structure` из списка выбрасывается с
  `logger.warning` (в тестах — ошибка).
- **Отложенные поля** исключаются из списка (иначе `save()` экземпляра из `.only()/.defer()` потянул бы запрос
  на каждое поле и записал бы устаревшее) — A-18, D-14.
- **Исчезнувшая строка**: `save(update_fields=…)` жёстко удалённой строки даёт `DatabaseError("did not affect
  any rows")`, а прежний полный `save()` вставил бы строку заново. Миксин ловит эту ошибку **только когда
  список полей подставил он сам**, пишет `logger.warning` и повторяет прежнее поведение
  (`super().save(force_insert=True)`). Замок `test_m6_save_of_deleted_row_is_handled`.
- **Клон `pk = None`** без `_state.adding = True`: условие `self.pk is not None` оставляет вставку вставкой.
  Замок `test_m6_clone_without_adding_flag_still_inserts`.
- Собственные `save()` моделей (`apps/catalog/models.py:362` — слаг товара, `apps/promotions/models.py:624`)
  проверяют `update_fields` **до** вызова `super()` — миксин стоит первым в MRO и сужает список уже после них;
  `SoftDeleteMixin.delete / restore` (`apps/core/models.py:133-142`) идут с явным `update_fields` — не задеты.
- Приёмники `post_save` портала фильтруют «`update_fields` не `None` и не пересекается»

### 5.4. Проверка копии (`validate`) — в писателе, для любого входа

Копия приходит из черновика сессии, то есть от клиента.

- **Белый список верхних ключей**: `v`, `rows`, `sections`, `settings`, `i18n`; `v`, `src`, `lh` ставит
  сервер, пришедшие отбрасываются. Лишний ключ — `SchemaError("keys")`.
- **`rows`** — через `siteconfig.normalize_page_blocks({<общий хост>: rows})` (`siteconfig.py:2044`): правила
  блоков зависят от ключа хоста (`banned_blocks :2029`, `page_builtin_keys :1766`, якоря, оси), поэтому
  нормализация идёт **под ключом общего хоста типа**, а не виртуального (A-6). Если нормализация что-то
  выбросила или сократила — **отказ** (`SchemaError("rows")`), не тихая запись урезанного (A-1, A-7). `id`
  уникальны; число блоков ≤ `MAX_BLOCKS`.
- **`sections`** — три ключа; разделы — из `detail_sections` модуля; `layout` — из допустимых вида; порядок
  якорей там, где `detail_parts.fixed_order(<общий хост>)`, совпадает с реестром (`SchemaError("fixed_order")`);
  обязательные разделы не скрыты (§4.3).
- **`settings`** — ключи ровно `setting_codes(kind)`; каждое значение — `page_settings.validate(tenant, code,
  value, …)` (`apps/core/page_settings.py:940`), как сегодня у настроек черновика (`aufbau_draft.py:1543-1547`).
- **`i18n`** — языки только из языков сайта (`apps/core/i18n_input.py:17`), `id` — только из `rows`, поля —
  только переводимые строковые поля вида блока, потолки длины — те же, что у писателя окна
  (`apps/core/block_i18n.py:398-429`). `normalize` оверлеи не чистит (`siteconfig.py:4250-4278`) — поэтому
  проверка здесь. Нарушение — `SchemaError("i18n")`, не отбрасывание (S-6).
- **Санитайзер rich-text не нужен**: тексты блоков плоские, HTML в них не хранится (проверено ревью 2
  security); требование Р1-27 «через `richtext.py`» снято.
- Замок `test_m6_write_validates_overlay_settings_top_keys`, `test_m6_write_refuses_truncation`.

## 6. Чтение — одна явная точка

### 6.1. `object_structure.page(config, kind, obj, *, draft=None)` → «эффективная страница объекта»

Возвращает неизменяемый объект `OwnPage`: `state` (`legacy / inherit / own`), `ref`, `shared_host`, `rows`
(нормализованные строки страницы), `hidden`, `order`, `layout`, `settings`, `own_ids` (блоки «nur hier»),
`overlay(locale)` (позиционный оверлей переводов для `siteconfig.localize`, собранный из `i18n` по `id`).

- **Состояние — с уже загруженного экземпляра** (`obj.structure`): детальная вьюха объект и так загрузила —
  запроса по pk нет, бюджет запросов детали **«+0»** (D-11). Страница группы акций — «+1» по уникальному
  `host` (`PromoGroupPage`), витрина строку не создаёт.
- `legacy` → собирается **прежними функциями** (`effective_hidden / effective_full_order / effective_layout`,
  `own_blocks`, `detail_parts.flow`) — байт-в-байт сегодняшний вид; сторожа — `golden_fb31p5` (94 файла),
  `golden_fb3016` (79), `golden_fb31p3` (49) без пересъёмки (A-17).
- `inherit` → строки, разделы и настройки общей; старый хост, `page_override` и черновик `_object_override`
  этого объекта **не читаются**.
- `own` → только копия: строки нормализуются под ключом общего хоста (§5.4), обязательные разделы добавляются
  из реестра (§4.3), недостающие коды настроек — из общей.
- **Битая копия** (не словарь, незнакомая `v`, `validate` отказал) → страница рисуется как наследующая, 200,
  `logger.warning` с `schema_name` и pk раз на объект на процесс; **перевод остальных страниц не гаснет** —
  оверлей копии никогда не вливается в общий `i18n` конфига (A-17, вопрос 38).
- **Черновик в превью** (`?preview=1&aufbau=<код>`): `draft` применяется, только если код черновика — это
  **объект, загруженный вьюхой** (`ref_for_code(code) == ref(kind, obj)`), и пользователь вправе видеть
  превью (`page_settings._may_preview`, `page_settings.py:1034`). Черновик объекта A на адресе объекта B не
  применяется (S-3). `page_settings.preview_raw` (`:1048-1097`) для кодов объекта, категории, группы
  **черновик в конфиг не накладывает** — возвращает сохранённый конфиг; копию из черновика берёт только
  `page()`.
- Памятка — на экземпляре на время запроса (`obj._own_page`, ключ — `id(config)` и наличие черновика): копия
  разбирается один раз на рендер. Кэша модульного уровня нет (команда переноса идёт по ≈ 136 схемам в одном
  процессе — Р1-30).
- **Функции старого хранилища сами возвращают «пусто» для объекта с `v`**: `object_structure._raw(obj)`
  (`object_structure.py:40`) → `{}`, `own_blocks` (`:291`) → `[]`, `blocks_first` (`:360`) → `False`,
  `deviations` (`:157`) → 0. Обход, который забыли перевести на `page()`, покажет общую страницу, а не
  мёртвый хост (A-4). Замок `test_m6_marked_object_ignores_legacy_everywhere`.
- **Вьюха передаёт страницу шаблону явно** — переменной контекста `own_page` (после всех проверок 404).
  Привязки к запросу нет: страница 404 и её общий кэш (`apps/core/not_found_views.py:118`,
  `apps/core/pagecache.py:115-148`) копию увидеть не могут по построению (S-5). Замок
  `test_m6_404_never_sees_own_page`.

## 7. Копия, A2, сброс, черновик

### 7.1. Копия-кандидат (`candidate`)

«То, что страница показывает сейчас», в формате v1 — одна функция для A2, переноса, сидера и клона.

- Объект `inherit` или `{}` без старых данных: строки общего хоста, общие разделы, **каждая** настройка из
  `setting_codes(kind)` (включая значения по умолчанию), переводы общего хоста, переложенные с позиции на
  `id`.
- Объект `{}` со старыми данными: слияние по сегодняшнему правилу показа — у раздела сначала общие блоки,
  потом свои (`detail_parts.flow`, `detail_parts.py:325-351`); `sections` = общие ± `page_override`;
  `blocks_first` акции — местом своих блоков; переводы — общего хоста и поверх них старого своего хоста.
- Категория: четыре сочетания переключателей (Л4) сводятся к одному: блоки — свои, если
  `siteconfig.has_own_schema` (`siteconfig.py:1960`), иначе общие; оси — свои, если `catalog_parts.has_parts`,
  иначе общие. У копий, рождённых прежним `adopt` (`site_schema.py:993-996` выдаёт новые `id` и не копирует
  переводы), блоки сверяются с общими через `siteconfig._match_items` (`siteconfig.py:4472`) — совпавшие
  получают `id` общего (Р1-7).
- Группа: строки по цепочке `promo_group:<md5>` → `promo_group` → `promos`.
- Кандидат длиннее `MAX_BLOCKS` или не прошёл `validate` — копия не создаётся, отказ с существующим
  сообщением потолка страницы; при переносе — «ПРОПУЩЕНО» с причиной.

### 7.2. Вариант A2 (решение 9)

- Состояние A: экран показывает строки кандидата; ничего не записано, черновика нет. ⚙ строки открывает окно
  блока **этой** страницы; общую со страницы объекта окно не правит никогда.

  правка перевода) создаёт черновик новой формы с копией-кандидатом, отпечатками `base` и `shared_base`,

- «Verwerfen» — черновика нет, страница снова A. Сайт до «Speichern» не меняется.
- Категория сегодня работает через `adopt / reset` (`site_schema.category_items`, `site_schema.py:971-1000`) —

### 7.3. Сброс «Zur gemeinsamen Struktur zurück» и список потерь

- Операция черновика `reset`: копия черновика снимается, флаг «сброс»; до «Speichern» ничего не меняется.
  «Speichern» → `write(ref, None, …)` → поле ровно `{"v": 1}`.
- **Сброс не оживает** по построению: старое хранилище читается только при `{}`. Замок
  `test_m6_reset_never_resurrects_legacy` — пять путей: повтор переноса, `materialize_page_axes`,
  `_pin_own_categories`, «Version wiederherstellen», Save Студии.
- **Сброс не стирает чужую свежую копию**: «Speichern» сброса сверяет `base` под блокировкой, как любая
  запись; флаги черновика `own` / `reset` — не основание записи, основание — код страницы, разобранный
  сервером (S-12, S-3). Замок `test_m6_stale_reset_does_not_wipe_newer_copy`.
- **Сброс не трогает**: места баннеров (решение 13), «Kartenform», свои вопросы FAQ объекта (решение 18), SEO
  страницы, вид группы в списке акций.
- **Группа акций**: строка `PromoGroupPage` не удаляется — сброс пишет `{"v": 1}` в ту же строку (A-13).
  Замок `test_m6_group_reset_keeps_row`.
- **`losses(config, ref, obj, copy)`** — список для окна и страницы подтверждения, по порядку:
  1. блоки «nur hier» (`id` нет в общей сейчас) — поимённо (заголовок блока, иначе название вида);
  2. **правленые блоки, скопированные из общей** (`id` есть в общей, `data` или перевод отличаются) —
     «%(n)s geänderte Blöcke: …» (решение 18, Y-3);
  3. отличия разделов и настроек от общей сейчас: «„Bewertungen“ ausgeblendet», «„Ähnliche Produkte“ als
     Slider»;
  4. блок «Banner» с `from_page` — отдельная строка (решение 13).
  Пустой список — фраза «Dabei geht nichts verloren.» вместо заголовка и списка; имён больше
  `OWN_NAMES_MAX` — «und %(n)s weitere»; блок без заголовка — название вида (Y-8). Замки
  `test_m6_losses_cover_edited_copied_blocks`, `test_m6_losses_empty_long_unnamed`.

- **Новый ключ сессии** `aufbau_own` для черновиков страниц объекта, категории, группы (прежний —

## 8. Перенос, деплой, совместимость, кэш, права

### 8.1. Команда `migrate_object_structures`

Файлы: `+apps/core/management/commands/migrate_object_structures.py` (аргументы, вывод),
`+apps/core/structure_migration.py` (ядро; пишет только через `object_structure.write_system`).

По каждой схеме, по каждому виду реестра стопки 18:

1. **Кандидаты — без блокировок**: объекты с `structure == {}`. Со старыми данными — `page_override != {}`
   или свой хост в `page_blocks`; категории — хост `catalog:<slug>` с блоками или осями; группы — хост
   `promo_group:<md5>` или запись `promo_groups[key]` у живых и встроенных `sys:*` групп. Объект `{}` без
   старых данных получает `{"v": 1, "src": "migrate"}` массово, по одному `update` на вид с условием
   `structure={}` (без `candidate`, без рендера).
2. **Корзина.** Товары и акции — через `all_objects` (мягко удалённый объект восстановится со своей
   структурой). **Категории — только живые**: слаг мягко удалённой категории освобождается
   (`apps/catalog/forms.py:165-178`, уникальность слага — среди живых, `apps/catalog/models.py:76-80`),
   `restore()` в коде никто не зовёт, а хост `catalog:<slug>` принадлежит живой категории с этим слагом;
   мягко удалённые категории — в отчёт, не переносятся (D-9; отменяет Р1-22 в части категорий). Замок
   `test_m6_migrate_category_slug_reuse_goes_to_alive`.
3. `candidate()` → равен общей (отличий нет) — `{"v": 1, "src": "migrate", "lh": …}`; иначе копия с
   `"src": "migrate"` и `lh`. **Пишет только при действующем отличии** (решение 2).
4. **Сверка «до = после»** до записи: «подпись вида» (видимые разделы по порядку, последовательность блоков с
   данными, шаблон, значения настроек, тексты на каждом языке сайта) по старому пути и по `page()` обязана
   совпасть — у каждого кандидата. `--verify-render N` (по умолчанию 3 на вид на сайт; `all` — все) — сверка
   HTML тем же помощником, что у `materialize_page_axes` (`apps/core/page_axes_migration.py:454` нормализует
   `data-pb-host`), **новым запросом на каждый рендер** (без памяток прошлого рендера). Не совпало — объект
   **не трогается** (`{}`), строка «ПРОПУЩЕНО» с причиной; при первой правке в «Seitenaufbau» — предупреждение
   (§7.2).
5. **Запись — короткая транзакция на объект** (D-2, A-15): `config_migration.lock(Tenant, pk)`
   (`apps/core/config_migration.py:47-52`, `lock_timeout` 2 с — занятый сайт даёт «ПРОПУЩЕНО, занято», не
   висит) → сверка `config_migration.config_hash` с хэшем конфига, по которому строился кандидат (не совпал —
   кандидат строится заново, один повтор) → блокировка объекта → повторная проверка `structure == {}` →
   `update`. `candidate` и рендер — **вне** блокировки. `try` + точка сохранения на объект и на схему: сбой
   одного не отравляет транзакцию следующего (S-9).
6. `QuerySet.update` не шлёт `post_save` — шторма пересинхронизации портала нет (приёмники
   `apps/aggregator/tasks.py:834-900` срабатывают на каждое сохранение акции, номера, события; Л14) — и не
   меняет `updated_at` (вид не изменился). Порталу и sitemap `updated_at` от переноса не нужен: портал
   структуру не читает (grep `apps/aggregator` пуст), в `sitemap_xml` витрины
   (`apps/promotions/public_views.py:3658`) `updated_at` / `lastmod` объектов не встречается (grep по телу
   функции, 2026-11-27; предпосылка — перепроверить в срезе M6b3).
7. **Кэш витрины** — один сброс на схему в конце, если записана хотя бы одна копия
   (`config_migration.bump`, `config_migration.py:55`).
8. **Отчёт на схему** — счётчики: своя / наследует / пропущено (по причинам) / хост без живого объекта / хост
   сверх потолка (есть в сыром конфиге, выброшен `normalize`) / хост группы без известного ключа / мягко
   удалённые категории / серии событий с одинаковыми отличиями / незнакомая версия. **Без текстов бизнеса**:
   ни имён объектов, ни заголовков блоков, ни ключей групп (вместо ключа — md5); только схема, вид, pk
   (S-9, Р1-30). Код выхода ≠ 0, если упала хоть одна схема; остальные доигрывают; ошибка —
   `logger.exception` с именем схемы.

Аргументы: `--dry-run` (тот же отчёт, без записи); `--schema <имя>` (имя сверяется с реестром
`Tenant.objects.filter(schema_name=…)`; **`--schema public` и неизвестное имя — отказ**, код ≠ 0);
`--residue` (только остаток: объекты `{}` со старыми данными; объекты с `v`, у которых старые данные
изменились после переноса — сравнение с `lh`, след правок старого web после отката; мёртвые хосты);
`--undo` (§8.3); `--verify-render N|all`.

Идемпотентность: повтор берёт только `{}`; перенесённое, сброшенное и правленное не трогает; пропущенные
пробует снова.

Изоляция схем: один процесс идёт по ≈ 136 схемам — ни одного кэша модульного уровня без `schema_name` в
ключе (множество «уже предупреждали о версии» — с ним). Тесты проекта подхватывают TENANT-приложения как
SHARED (`CLAUDE.md` §5), поэтому изоляцию pytest не докажет — **обязательный прогон на стенде ≥ 2 схем** с
одинаковыми слагами категорий и ключами групп (D-19).

Замки — §15, срез M6b3.

### 8.3. Совместимость, откат, выкат

**Окна деплоя** (Л21):

- [7] → конец [8]: новый web, перенос идёт. Объект `{}` читается старым путём; первая правка такого объекта в

  старой формы у страниц объектов снимаются с сообщением о конфликте (§7.4).
- FB-31.7 не закрыт: шаг `materialize_page_axes` остаётся на каждом деплое, но видит только объекты `{}`; его
  `--undo` возвращает ключи конфига — на объекты с `v` это не влияет. Наследник акции по-прежнему копирует
  `page_style` через `_RECUR_CLONE_FIELDS` — не трогаем (Л20).

**Откат кода стопки 18.** Старые данные не удаляются и не меняются до стопки 20 → старый web читает их как
до деплоя. Правки, сделанные в структурах после выката, старый код не видит; после повторного выката они на
месте. Чистый откат: новым кодом **до** отката — `migrate_object_structures --undo`:
- возвращает в `{}` только объекты с `"src": "migrate"` — и «своя от переноса», и «наследует от переноса»
  (D-5); сброшенные владельцем (`{"v": 1}` без `src`), правленные и клоны остаются с `v`;
- пишет через `write_system(caller="undo")` теми же короткими транзакциями; строка журнала на объект
  (`apps/audit/services.py:23`: схема, вид, pk, «undo»);
- число оставшихся — в отчёте. Замок `test_m6_migrate_undo_restores_inherit_marked`.

Старый web после отката пишет `page_override` и хосты объектам с `v` — эти правки после повторного выката не
читаются. `--residue` показывает их (сравнение с `lh`) с предупреждением (D-7). Замок
`test_m6_residue_reports_legacy_edits_on_marked`.

Виртуальные имена хостов (`product:<hex>`, `catalog:<slug>`, `promo_group:<md5>`) остаются кодом страницы,
параметром `?seite=`, `von`, адресом ⚙, ключом черновика (Л23); `siteconfig.is_page_block_host` не сужается.

**Порядок выката стопки 18** (решение 12): замер миграций на стенде → `--dry-run` на копии прода, отчёт
владельцу (число «своих», пропусков, серий, остаток) → деплой вне пика одним заходом (миграции → код →
перенос) → отчёт шага → `--residue` → пересев демо (`seed_demo_tenants --group all --changed --jobs 3`). Ветка
стопки до конца второй сессии в `main` не вливается.

`test_m6_kind_without_edit_route_denies`.

**Просмотр.** Страница объекта по прямому коду (`?seite=<kind>@…`) раскрывает имя и тексты блоков — одного
`website.view` мало: без права просмотра объектов вида — **404** (S-8); то же для GET страницы подтверждения
сброса и для фрагментов окна. `site_schema._object_for` (`site_schema.py:651-663`) отдаёт и неактивные
объекты — с правом вида это допустимо, без — 404. Новый маршрут сброса (если отдельный) — строка в

**Разбор кода страницы** — только `object_structure.ref_for_code` (внутри — `site_schema.resolve / host_for`,
`site_schema.py:1079, 2656`): объект существует и жив, тип включён, префикс сравнивается точно. **Группа
акций — два источника**: живая группа (`site_schema._live_promo_groups`, `:838`) **или** строка

символов и `\x00` (`unicodedata.category(ch)[0] == "C"` → отказ), длина 1…64, непустой после `strip()`,
**без обрезки и смены регистра** («Sale», «Sale » и «sale» — разные группы, как сегодня:

`apps/promotions` — пусто). Страница остаётся у старого ключа (решение 15) и видна в отчёте `--residue` как

## 17. Риски

- **Шов рождения для тестов** (§4.1) — тестовая подмена константы прод-кода. Цена ошибки — тест старого
  хранилища идёт не тем путём. Смягчение: список только сокращается; новые тесты M6 идут с боевым значением;
  стопка 20 снимает шов. Альтернатива (править ≈ 70 тест-файлов в первом срезе) дороже и шире.
- **Настройки типа в шаблонах** (§6.3): полный перечень вхождений шести ключей в `templates/` на момент плана
  не построен (известен только `detail_related_layout`). Если шаблон читает ключ из `site` глубоко во
  включениях — правка шире прогноза M6b1; замок-перечень `test_m6_copy_setting_readers_listed` покажет это
  первым коммитом, до кода.
- **Редактор кабинета идёт через `normalize`** (§7.4): три правила закрывают CRITICAL, но это самое хрупкое
  место стопки; замок `test_m6_editor_survives_full_host_caps` и сценарий стенда `caps` обязательны.
- **M6a2 — широкий срез** (весь чистый слой в одном файле): деление по коммиту (§11.1); находки ревью в
  `object_structure.py` во время волны M6b* — только через `plan_check.py --add` в M6c2.
- **M6c2 — самый тяжёлый срез** (черновик + права + настройки + категория): если исполнитель не
  укладывается — выделить «настройки на странице объекта» отдельным коммитом той же ветки.
- **`ACCESS EXCLUSIVE` на ≈ 136 схемах × 12 таблиц** ждёт долгие транзакции: `lock_timeout` 3 с даёт честный
  отказ шага, повтор деплоя идемпотентен; замер на стенде и деплой вне пика обязательны.
- **`materialize_page_axes` остаётся исключением** «пишет старое хранилище для `{}`» до закрытия FB-31.7
  (прогон на сервере — за владельцем): для объектов с `v` не действует; остаток виден в `--residue`.
- **Откат кода после выката**: правки старого web объектам с `v` не читаются после повторного выката — только
  отчёт `--residue`; автоматического слияния нет.
- **Сотрудник с одним `website.edit`** теряет правку блоков страниц объектов (решение 11) — предупредить
  владельца при выкате.
- **Вид группы `promo_groups[key]`** остаётся вне копии (§4.2) — если страница группы читает из него то, что
  по решению 24 должно быть в копии, состав `settings` группы расширяется в M6c2 (предпосылка).
- **Открытые черновики** страниц объектов на момент деплоя дадут по одному `DraftConflict` (сообщение
  честное); выкат вне пика делает случай редким.

## 18. Где третья редакция отступает от вводных координатора (и почему)

1. **П. 3 «чтение — явная точка, без подмены конфига» — выполнено для витрины; редактор кабинета оставлен на
   рабочем словаре конфига** (§7.4). Операции окна (`store_items`, `block_i18n`, «Wie», «Karte», «Texte»,
   `_check_normalized`) написаны над `config["page_blocks"][host]`; переписать их на «строки копии» — это весь
   `aufbau_draft` и окно блока. Рабочий словарь никогда не рисуется на витрине и никогда не записывается
   (`commit` страницы объекта `site_config` не сохраняет); CRITICAL A-1 закрыт правилами «один хост
   структуры в словаре», «потолок хостов для таких кодов снят», «меньше строк после операции — отказ».
2. **П. 3 «настройки типа» — явная функция `setting()` плюс правило для шаблонов** (§6.3): шаблоны берут
   настройки из контекста `site`; на страницах объектов шесть ключей передаются вьюхой явно. Перечень
   вхождений строится в срезе (риск §17).
3. **П. 6 «новый код не пишет старое хранилище для `{}`» — одно названное исключение**:
   `materialize_page_axes` (FB-31.7 сверяет сайт целиком, перевод на писателя по объектам ломает его откат —
   довод редакции 1, Р1-2). `_pin_own_categories`, пресеты, fetch-ветка `add_block`, «Version
   wiederherstellen» — по вводной.
4. **П. 1 «объекты рождаются `{"v": 1}`» — принято, но потребовало шва для тестов** (§4.1) и записи сидера
   через писателя (§7.6): иначе ≈ 70 тест-модулей и киты с категориями ломаются в первом же срезе.
5. **П. 7 «проверки ключа из редакции 1» — сохранены, `follow_group_rename` снята**: автоматический переезд
   страницы на новый ключ противоречит решению 15 «страница остаётся» и требовал блокировок из формы акции;
   смена группы — строка отчёта `--residue` и отложенное `M6-group-move`.
6. **Корзина** (ревью 2 против редакции 1): категории — только живые; товары и акции — с корзиной (слаг не
   участвует, ключ — pk).
7. **`lh`** — добавлен к маркеру `src` (не было во вводной): без него `--residue` не может показать правки
   старого web после отката (D-7).

## 24. Открытые вопросы владельцу (только новые; ответ не блокирует M6a1–M6b2)

1. **Раздел, появившийся в общей структуре после того, как у страницы уже есть своя.** Обязательные по
   закону и закреплённые разделы копия получает всегда (это не вопрос). Прочие новые разделы — два варианта:
   (а) появляются на «своей» странице сразу видимыми, в конце (как сегодня у страниц с отличиями); (б)
   появляются **скрытыми** в списке «Ausgeblendet» — владелец включает сам. **Рекомендация — (б)**: плашка
   обещает «Änderungen an der gemeinsamen Struktur … gelten hier nicht», новый раздел без спроса это
   обещание нарушал бы.
2. **Текст предупреждения для страницы, которую перенос пропустил** (вид «до» и «после» не совпал, объект
   оставлен как был; при первой правке копия делается на месте). Предложение: «Diese Seite wurde nicht
   automatisch übernommen. Bitte prüfen Sie die Vorschau, bevor Sie speichern.» **Рекомендация — принять**;
   показывается только у таких страниц, до «Speichern».
3. **Два коротких текста в окне сброса, которых нет на артбордах**: «Dabei geht nichts verloren.» (когда
   терять нечего — вместо пустого списка) и «und %(n)s weitere» (хвост длинного списка имён; тот же хвост —
   в списке «… mit eigener Struktur»). **Рекомендация — принять.**
4. **Смена группы у акций.** Страница группы остаётся у старого названия (решение 15); если владелец
   «переименовал» группу, поменяв её у всех акций, новая группа начнёт с общей структуры, а прежняя страница
   останется без акций. **Рекомендация — оставить так в стопках 18–19** (в отчёте переноса такие страницы
   видны), перенос страницы на новое название — отдельной задачей `M6-group-move`, когда появится действие
   «переименовать группу».
