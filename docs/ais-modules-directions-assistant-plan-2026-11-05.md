# AIS-M + AIS-A — порядок в модулях (направления) и ИИ-помощник на всех стадиях (2026-11-05)

Запрос владельца: «навести порядок в модулях — там каша; привязать к архетипам, лишнее скрыть;
сделать направлениями — что для кого нужно, а что базово — вообще скрыть. ИИ-помощник нужен на
всех стадиях создания: показывать, что заполнить, чего не хватает, как персональная техподдержка,
но в рамках проекта; где можно обойтись без ИИ — без него. Проверить через ECC.»

Опирается на уже принятые решения: KA-3 (пакеты Aktionen/Eintrag/Website/Laden, честный доступ),
KA-4 (подпункт виден, только если нужен направлению), T-8.32 (направления Waren/Termine/Zimmer/
Tickets/Anfragen, реестр «Обязательно/Желательно», жёсткий гейт продажи) и мастер v4
(`ais-wizard-v4-structure-2026-11-05.md`). Кода нет.

## Часть 1. Модули → направления (AIS-M)

### 1.1. Каша сегодня (факты из `apps/core/modules.py`)

Экран «Funktionen» (`/dashboard/modules/`) — 22 модуля плоским списком тумблеров в трёх секциях
(«Empfohlen» / «Weitere Funktionen für andere Typen» / «Premium» — пустая):

1. **Смешаны три разных сущности:** способы продажи (orders, booking, stays, events, jobs),
   инструменты для всех (crm, reviews, inbox, promotions) и дополнения (loyalty, gift, blog,
   finance, analytics, publishing, telegram, customer_account) — одинаковые тумблеры рядом.
2. **Пять core-модулей показаны неснимаемыми строками** в «Empfohlen» (dashboard, board, catalog,
   settings, billing) — выключить нельзя, но место занимают (уточнено ревью ECC: это не тумблеры).
3. **Технические имена:** «Reservierungen nach Zeit (Booking)», «Übernachtung (nach Datum)»,
   «Veröffentlichung (Kanäle)».
4. **Пресеты по типам кривые** (стартовый набор `default_disabled_for`):

| Тип | Сегодня включено | Проблема |
|---|---|---|
| hotel | crm reviews stays gift inbox customer_account | **нет акций**, хотя Lücken-Deal и акции на номер есть |
| tour_operator | crm reviews **booking** gift events inbox … | лишний booking, нет акций |
| handwerker / werkstatt | … jobs … | нет акций |
| other | promotions crm reviews gift inbox | ни одного способа продажи |
| все 16 | — | finance, analytics, publishing, telegram, blog **выключены у всех**, хотя помечены «Für alle» |

5. **`catalog` — core у всех**, поэтому Lager/Einkauf/Kombi/Import видны отелю и ремеслу (KA-4 P1).
6. **«Weitere Funktionen für andere Geschäftstypen»** показывает парикмахеру «Übernachtung» —
   это вопрос «какие ещё направления у вас есть», а не список чужих модулей.

### 1.2. Целевая модель — три слоя

**Слой 1. Базовое — всегда есть, на экране НЕ показывается.**
Übersicht, Verkäufe (доска), Einstellungen, Abo, Nachrichten (inbox), Kunden (crm),
Bewertungen (reviews), Aktionen (promotions), Website/Studio. Тумблеров нет; доступ режет только
пакет (KA-3) и права сотрудника (E6.7).

**Слой 2. Направления — «Wie verkaufen Sie?».** Карточки с объяснением и примером:

| Направление | Модули | Режимы | По умолчанию у типов |
|---|---|---|---|
| **Waren** (Sortiment, Abholen/Liefern) | catalog-UI + orders | zeigen / verkaufen | bakery, butcher, grocery, retail, clothing, online_shop, cafe |
| **Termine** (Leistungen, Tisch) | booking | zeigen / buchen | friseur, werkstatt, restaurant, cafe |
| **Zimmer** | stays | zeigen / buchen | hotel |
| **Tickets** (Veranstaltungen, Touren) | events | zeigen / verkaufen | events, tour_operator |
| **Anfragen** (Angebote, Aufträge) | jobs | — | handwerker, werkstatt, catering, tour_operator |
| **Speisekarte** (контент без продажи) | catalog-UI | zeigen | restaurant, catering |

- Направлений может быть несколько (кафе: Waren + Termine; werkstatt: Termine + Anfragen).
- «zeigen» = пакет Website (каталог/услуги/номера как контент, отклик «Anfrage»), «verkaufen» =
  пакет Laden + гейт готовности (T-8.32 §4, KA-3 В-6). Переход = включение продажи, данные те же.
- Экран складских/закупочных разделов показывается ТОЛЬКО при Waren (KA-4 P1 закрывается здесь).
- «Weitere Richtung hinzufügen» вместо списка чужих модулей.

**Слой 3. Дополнения — по направлениям, остальные скрыты совсем.**

| Дополнение | Модуль | Видно при направлении | По умолчанию |
|---|---|---|---|
| Treue & Stempelkarte | loyalty | Waren, Termine | вкл. у пекарни/кафе/салона |
| Geschenkgutscheine | gift | любом продающем | вкл. |
| Kundenkonto | customer_account | Waren, Termine, Zimmer, Tickets (режим verkaufen) | вкл. |
| Telegram-Bot | telegram | любом | выкл. |
| Kanäle (Google/Facebook/…) | publishing | любом | выкл. |
| Blog / Neuigkeiten | blog | любом | выкл. (KA-4 В-3) |
| Finanzen | finance | любом продающем | выкл. (Profi, T-8.32) |
| Auswertung | analytics | любом | выкл. |
| Lager & Einkauf | (области catalog) | Waren | выкл., включается вместе с остатками |

Дополнение, у которого нет ни одного подходящего направления, на экране не показывается вовсе.

### 1.3. Как это ложится на код (без миграций)

- **НОВЫЙ `apps/core/directions.py`** — реестр `Direction(key, label, blurb, icon, modules,
  default_for, addons)`; «направление активно» = его модули активны (вывод из
  `disabled_modules`, отдельного хранения нет). Включить/выключить = записать набор модулей
  одной функцией (под блокировкой строки тенанта).
- **`ModuleSpec` += `layer`** (`base` / `direction` / `addon`) и `addon_for` (направления).
  `recommended_for`/`suited_for` остаются для пресета, но экран читает слой.
- **Базовые модули остаются выключаемыми в БД**, экран их просто не показывает. Тенантам, которые
  их когда-то выключили, — разовый отчёт (`modules_report`, как `package_report`) до решения
  владельца, включать ли обратно (вопрос М-1).
- **Пресет по типу** — из таблицы §1.2 (исправляет hotel/tour_operator/handwerker/other).
  Только для новых бизнесов; живым — ничего не меняем молча.
- **Экран «Funktionen»** → «Richtungen & Funktionen»: блок направлений карточками + дополнения
  активных направлений. Мастер v4 (шаг 1) и «Verkauf öffnen» используют тот же реестр.
- `nav_registry` получает гейт `directions` (KA-4 §2 п.2): подпункт виден, если нужен направлению.

### 1.4. Замки

- Каждый не-core модуль принадлежит ровно одному слою; каждое дополнение имеет ≥1 направление.
- Пресет каждого из 16 типов содержит ≥1 направление; `other` — после выбора на шаге 1 мастера.
- Подпункт складских/закупочных разделов не виден без Waren (у всех 16 типов).
- Экран не показывает базовые модули и дополнения без активного направления.

## Часть 2. ИИ-помощник на всех стадиях (AIS-A)

### 2.1. Принцип: правила — основа, ИИ — только где правил мало

«Что заполнить и чего не хватает» — это **детерминированная** задача, ИИ для неё не нужен и
опасен (может сказать неправду о состоянии магазина). ИИ нужен для двух вещей: понять свободный
вопрос владельца и сформулировать ответ по-человечески.

| Что делает помощник | Чем | ИИ? |
|---|---|---|
| «Чего не хватает» на каждом экране и в целом | реестр готовности (W4-0) по направлениям | нет |
| «Почему не работает» (нет слотов, корзина закрыта, не видно в каталоге города) | реестр диагнозов: симптом → проверки → причина → ссылка | нет |
| «Где это настраивается» | поиск по `nav_registry` (Ctrl+K уже есть) | нет |
| «Что сделать дальше» | карточки «Nächster Schritt» (AIS-6) | нет |
| «Создай мне 5 услуг / акцию на выходные» | `setup_plan` → префилл форм (есть) | да, с правилами-запасом |
| Свободный вопрос «как сделать доставку только по Solingen?» | ИИ выбирает статью справки + диагноз + ссылки | **да** |
| Тексты, фото меню, перевод | задачи AIS-4/5/7 | да |

### 2.2. Как выглядит

- Кнопка **«✨ Assistent»** в шапке кабинета, в мастере, в Mini App. Боковая шторка (контракт
  `drawer.md`).
- Вверху шторки — всегда без ИИ: «Auf dieser Seite fehlt: …» (из реестра готовности по текущему
  экрану) и «Gerade wichtig: …» (1–3 карточки).
- Ниже — поле вопроса. Ответ ИИ: короткий текст + до 3 кнопок. Кнопки — ТОЛЬКО адреса из
  `nav_registry`/реестра готовности (белый список), никаких сгенерированных ссылок.
- Действия: помощник **ничего не меняет сам**. Максимум — открывает форму с префиллом
  (как `setup_plan`), сохраняет владелец.
- **Вне рамок проекта** (налоги, юр. консультация, общий чат) — вежливый отказ + где спросить
  (Steuerberater, IHK). Юр. тексты — только наши генераторы и ссылка «проверить у юриста».
- **«An den Support senden»** — эскалация в существующие тикеты «Hilfe» (`apps/support`) с
  вопросом, ответом помощника и снимком состояния (без данных клиентов).

### 2.3. Источник знаний (RAG без векторной БД)

- **Статьи справки** — короткие how-to на экран/задачу (`docs/help/*.md` или реестр в коде,
  de + переводы), связаны с ключами `nav_registry`. Пишем их сами: 40–60 статей по глоссарию
  и экранам. Отбор: по ключу текущего экрана + поиск по словам (Postgres FTS, как портал) —
  в промпт идут 3–5 статей, не вся база.
- **Снимок состояния тенанта** — результат реестра готовности и диагнозов (факты «да/нет»,
  числа позиций), тип, направления, пакет. **Без** персональных данных клиентов, без заказов.
- Всё внешнее — в рамке недоверенных данных (контракт AI-0 §10).

### 2.4. Защиты

- Ответ проходит пост-проверку: ссылки только из белого списка; никаких цен, сроков, обещаний
  о тарифе; утверждения о состоянии магазина — только из снимка (как гард `check_reply`).
- Метка «KI-Assistent» (AI Act ст. 50 с 02.08.2026), `AI_LABEL` на ответах.
- Лимиты: правила — без лимита; ИИ-вопросы — квота тарифа (`AIUsage`), тест — малая квота.
- Права: помощник видит только экраны, открытые пользователю (`view_perms`/`can_open`);
  сотруднику не советует экраны владельца.
- Журнал вопросов без персональных данных (как журнал поиска T-8.21) → какие статьи писать.

### 2.5. Модель и провайдер

Claude (решение владельца). Разработка/стенд — прямой API; прод — Claude через AWS Bedrock EU
(рекомендация принята, `AI_REQUIRE_EU`). Новая задача реестра `apps/ai`: `assistant_answer`.

## Часть 5. Ревью ECC (2026-11-05) — что меняется в плане

Прогоны: `architect` (архитектура против кода), `security-reviewer` (дизайн), `planner` в режиме
product-lens (путь пяти персон: Bäckerei, Friseur, Pension, Handwerker, Café). Факты архитектора
перепроверены по коду. Пункты ниже **имеют приоритет над частями 1–3** при расхождении.

### 5.1. Архитектура (обязательные правки)

1. **Гейт направлений уже существует** — `nav_registry.direction_active` (`apps/core/nav_registry.py:1153`,
   `NavEntry.direction`, значения `waren`/`gastro`: тип ∪ модуль orders ∪ «есть товары/категории»).
   В M-0 `directions.is_active()` — ЕДИНСТВЕННЫЙ предикат, `nav_registry` делегирует ему; замок «других
   вычислений направления в коде нет». Правило «есть товары» сохраняется явно.
2. **«Активно = модули активны» не работает:** `catalog` core (`modules.py:544` — True до всех проверок),
   `booking` обслуживает и мастеров, и столы, `jobs` входит в лёгкий пакет ради заявок по акции
   (`packages.py:46`). → у направления предикат `active_when` (модули + данные), режим zeigen/verkaufen
   хранится явно в `site_config["directions"]` (presence-minimal, ключ — в `normalize`, иначе Save его
   уронит — грабля W0/W6). Пакет остаётся потолком всего тенанта; режим — по направлению.
3. **«Выключил владелец» ≠ «выключено пресетом»** (`default_disabled_for` пишет в `disabled_modules` всё,
   чего нет в `recommended_for`). У hotel/tour_operator/handwerker/werkstatt акции выключены пресетом.
   → `modules_report` по классам: совпадает с пресетом → включить автоматически; отличается → владелец.
   Базовые модули НЕ делать `core=True`: core обходит потолок пакета, лёгкие пакеты получили бы crm/reviews.
4. **Готовность — уже четвёртый механизм** (`SETUP_STEPS.check`, `lite_home.next_step`,
   `impressum_missing`, `settings_hints`). → `apps/core/readiness.py` единственный слой, остальное —
   потребители. Пункт «Recht» мастера (`onboarding.py:71`, `LegalDoc.exists()`) → `impressum_missing`
   (это и есть § 5 DDG).
5. **Жёсткий гейт продажи закроет кассу живым магазинам.** Гейт — в W4-0, но за флагом; сначала
   `readiness_report` (как `package_report`), затем исключение для живых или уведомление владельцу.
6. **Цена реестра:** ленивые предикаты, мемоизация на объекте тенанта в пределах запроса (как
   `_nav_has_products`), ≤ ~3 запросов; в хроме кабинета НЕ вызывать — шторка помощника грузится
   отдельным запросом; гейт чекаута проверяет только обязательное своего направления; без межзапросного кэша.
7. **Помощник:** ссылки — через существующий `setup_assistant.reachable()` (`:435`) + `packages.view_allowed`
   + `view_perms`; новые вьюхи — в `_AKTIONEN_VIEWS` и `TG_LITE_VIEWS` (иначе 403 в лёгком пакете/Mini App);
   «на этом экране не хватает» — по `nav_key` через `ANCHOR_BY_NAV`; **диагнозы зовут настоящие гейты**
   (`closures`, `packages`, слоты, `visibility.listable`), а не повторяют их; снимок для эскалации —
   в `SupportMessage` только `body` (`apps/support/models.py:60`) → текстом в теле или JSON-поле (миграция).
8. **Мастер v4 за флагом:** свой набор шагов, `HANDLERS` ↔ `STEP_KEYS` (замок `setup_steps.py:9`),
   маппинг состояния v2→v4 без понижения `completed`; тенанты быстрого старта (мастер пройден) v4 снова
   не видят.
9. **Google:** текстовый поиск + адрес/телефон/часы — дороже Basic-SKU GK-11 → Autocomplete с
   session-токеном + Details с минимальным FieldMask; смету цены записать до кода.
10. **Поправки фактов:** записей в `SETUP_STEPS` 14 (видимых до 13); `_gate_category` всегда True (catalog
    core); смена пресетов затрагивает `provision_quick` и демо-киты → `SEEDER_VERSION` + замки китов.

### 5.2. Безопасность (требования к инкрементам)

- **CRITICAL — Google в регистрации:** поиск только после подтверждения почты или владельцу; лимит
  IP//64 + сессия + суточный потолок расходов платформы (`ratelimit.hit`, SEC); `maxResultCount` ≤ 5,
  жёсткий FieldMask, длина запроса, кэш ≤ 30 дней; храним только `place_id` и подтверждённые поля;
  ключ ограничен в Google Cloud и не уходит в браузер.
- **CRITICAL — prompt injection:** `assistant_answer` отдаёт по схеме только идентификаторы статей и
  ссылок; URL подставляет сервер из реестра; любая строка, похожая на URL/e-mail, в тексте → отказ;
  пост-проверка как `check_reply`; извлечение меню/сайта — только поля по схеме, цена принимается,
  если число есть в исходнике; вывод модели — только autoescape, никогда `|safe`. Проверить, что рамка
  недоверенных данных (AI-0 §10) реально ставится в `generate`.
- **CRITICAL — кросс-тенант:** снимок — белый список ключей (да/нет, числа, тип, направления, пакет),
  без имён клиентов, заказов, сообщений; кэш ответов (если будет) с ключом схемы; эскалация — схема с
  сервера, текст через `scrub`; замок «второй тенант ничего не видит из снимка первого».
- **HIGH:** права (подсказки и ответы только по экранам, открытым пользователю; сотруднику — «Fragen
  Sie den Inhaber» на владельческое; эндпоинт — `login_required` + право в `view_perms` + лимит);
  PDF — тип по сигнатуре, ≤ 10 МБ, ≤ 10 страниц, разбор только в Celery с таймаутом, сырой PDF провайдеру
  не шлём; фото — всегда `images.reencode` (EXIF/GPS), исходник удаляется ≤ 24 ч, отдача через
  `media_views`; импорт сайта в мастере — только через `safe_fetch` и подтверждение владения (Г1);
  стоимость — квота на тенанта и пользователя + потолок платформы, вопрос ≤ 500 символов, тяжёлое в
  Celery с `idempotent_task`; DSGVO — Impressum-реквизиты владельца в ИИ не отправляем, dev (прямой API) —
  только демо-данные, прод — `AI_REQUIRE_EU` без тихого фолбэка, AVV с AWS, `pii_scrub` у новых задач явно.
- **MEDIUM:** «Sie chatten mit einer KI» при входе в чат + бейдж «KI-erkannt, bitte prüfen» у позиций;
  журнал вопросов — агрегат (день × тема × исход), сырой текст ≤ 30 дней после `scrub`; эскалация только
  кнопкой с показом того, что уйдёт; «налоги/право» отсекаются правилами ДО модели; замки CI на всё это.

### 5.3. Продукт (путь персон) — правки классификации и мастера

| Было в плане | Стало |
|---|---|
| Aktionen — базовые и видны всем | базовые в данных; пункт меню виден типам из пресета, остальным — после первой акции или через карточку (у отеля подпись «Lücken-Deal & Frühbucher») |
| Speisekarte — режим Waren (М-2) | **отдельное направление «Speisekarte» (только zeigen, без склада/доставки/Grundpreis)** — иначе кафе и ресторан увидят склад |
| Café = Waren по умолчанию | Café = Speisekarte + Tisch; «Torten vorbestellen?» (Waren verkaufen) — карточкой |
| Restaurant Termine | направление называется **«Tisch reservieren»** (столы/комбинации/Tischplan — не услуги) |
| Kundenkonto вкл. у Zimmer | у hotel выкл., вкл. у Waren/Termine |
| werkstatt без Waren | werkstatt сохраняет склад деталей (`nav_registry.py:1149`) — записать замком |
| tour_operator: Tickets + Anfragen | + дополнение «Unterkunft im Paket» (stays) для многодневных туров, не направление |
| Analytics — тумблер | карточка «Zahlen ansehen» после первых 10 продаж |
| Замок «≥ 1 направление у всех 16» | исключение `other`: направление выбирается в шаге 1 |

Мастер v4 (дополнения к `ais-wizard-v4-structure-2026-11-05.md`):
- **Вопрос «Wie verkaufen Sie?»** в шаге 1 — для `other` и смешанных типов (кафе, werkstatt,
  tour_operator); остальным дефолт по типу с «ändern».
- **Friseur:** авто-ресурс «Ich» со всеми услугами — иначе навыки мастеров (fail-closed, E4.2a) молча
  закрывают онлайн-запись; длительность — обязательное поле шага 2; «ab»-цена.
- **Pension:** фото номера — обязательно для режима «buchen»; источник шага 1 «Booking.com / iCal»;
  Kurtaxe — пресет «wird nicht erhoben» с «ändern».
- **Handwerker:** Impressum-вариант для регулируемой профессии (Kammer, Berufsbezeichnung,
  Handwerksrolle — § 5 DDG); зона выезда (PLZ) — в шаге 2; пример «виды работ без цен».
- **Lebensmittel:** аллергены/Zusatzstoffe названных позиций — в шаге 2 (LMIV действует и для витрины
  «zeigen»), не только в «Verkauf öffnen».
