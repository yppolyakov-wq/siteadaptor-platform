# RESEARCH: bitrix

## SUMMARY
Битрикс24 — портал «всё в одном» (CRM, задачи, сайты, магазин, коммуникации) с одним плоским левым меню на ~30 пунктов; управляемость достигается не архитектурой, а компенсаторными механизмами: персональная настройка меню (скрытие/порядок/избранное), выбор «главного инструмента», админский пресет меню для всех, полное отключение инструментов и единый раздел «Настройки» (11 групп) с поиском, который перекидывает прямо в нужную настройку. 1С-Битрикс «Управление сайтом» — двухрежимная система («Сайт» = правка поверх публички, «Администрирование» = дерево разделов Рабочий стол/Контент/Магазин/Маркетинг/Сервисы/Настройки) с поиском по админ-меню и избранным по звёздочке. Главная причина репутации «каши» — не количество функций само по себе, а конкретные механизмы: дубли входов в одну сущность (товары через «Контент»-инфоблоки и через «Магазин»; коммуникации в Ленте/чате/комментариях), настройки одной фичи, размазанные по 3–4 слоям (модуль/компонент/инфоблок/шаблон; портальные настройки vs шестерёнки внутри разделов), скрытые режимы, меняющие модель данных (простая/классическая CRM), жаргонная терминология (лид/смарт-процесс/инфоблок/торговые предложения/эрмитаж) и отсутствие единого стиля между модулями. Вывод для нашего кабинета: «всё показать и дать спрятать» — проигрышная стратегия; выигрышная — «показывать мало по архетипу и дать включить», один вход на сущность, настройка живёт там, где её эффект, поиск по настройкам как страховка.

## PATTERNS
- Единый раздел «Настройки» с поиском, который не просто ищет, а ПЕРЕКИДЫВАЕТ в нужную настройку — главная страховка от «размазанных» настроек; у нас аналог — поиск по кабинету, ведущий прямо на экран/аккордеон (Битрикс пришёл к этому только после лет критики)
- Понятие «главный инструмент»: пользователь (или архетип) выбирает, что открывается при входе и что стоит первым — прямой аналог нашего primary-модуля архетипа; у Битрикс24 это ручной выбор, у нас может быть автоматическим по типу бизнеса
- Админский пресет меню: задать состав/порядок меню ВСЕМ сотрудникам или только новым + возможность полностью отключить инструмент (не «скрыть», а выключить, чтобы не всплывал нигде) — ровно наша механика модулей/simple_hidden, подтверждает выбранное направление
- Меню фильтруется правами роли: сотрудник видит только доступное — меньше шума без отдельной настройки
- Счётчики «требует внимания» на пунктах меню (красные/зелёные цифры) — навигация по задачам дня, а не по структуре; клик сразу открывает нужное (наш бейдж inbox — то же самое, можно расширить)
- Избранное по «★» на ЛЮБОЙ странице админки (включая сохранённые фильтры) — дешёвый механизм персональных ярлыков при глубокой структуре
- Два режима редактирования сайта: правка «поверх публички» (эрмитаж) для контентщика + полная админка для настройщика — сама идея верная (наш канва-редактор это и есть); ошибка Битрикса не в идее, а в том, что возможности режимов пересекаются частично и непредсказуемо
- Пресеты фильтров в списках + сохранение своих наборов с управлением видимостью (только мне / всем) — хорошо для наших списков заказов/броней
- Режим CRM как пресет сложности: «простая CRM» (без лидов, всё — сделки) по умолчанию, «классическая» — по осознанному выбору; правильно, что дефолт = простой, и что переключение конвертирует данные автоматически, а не ломает их
- Мастера первичной настройки (визард при создании магазина/портала) с демо-данными — снижают порог входа; наш мастер-слайды AB6 идут дальше
- Рабочий стол = дашборд с перетаскиваемыми виджетами по ролям (заказы для магазина) — «что происходит» вместо «где что лежит», аналог нашего ST-4a
- Плавающие панели действий/заголовков в длинных списках, «Сохранить и добавить ещё» — микропаттерны продуктивности для форм кабинета

## ANTIPATTERNS
- Плоское меню на ~30 пунктов без группировки: все модули равноправны и видны сразу, релевантность решается ВЫЧИТАНИЕМ (пользователь должен сам скрывать лишнее). Итог по отзывам: «новичок тонет в кнопках», обучение 2–4 недели, «не разобраться без встроенного бота и вебинаров». Урок: правильный дефолт — показывать мало (по архетипу) и давать ВКЛЮЧИТЬ, а не показывать всё и давать скрыть
- Дубли входов в одну сущность: товары редактируются и через «Контент → Инфоблоки» и через «Магазин → Каталог»; коммуникация размазана по Ленте + Мессенджеру + комментариям задач + чатам CRM; «Маркетинг», «Центр продаж» и CRM-маркетинг пересекаются; «Сайты» и «Интернет-магазин» — два раздела одного конструктора. Пользователь не понимает, какой вход «настоящий», и находит разные подмножества функций в каждом
- Настройки одной фичи размазаны по слоям: в УС поведение страницы = настройки МОДУЛЯ (в «Настройках») + настройки КОМПОНЕНТА (доступны только из публички!) + настройки ИНФОБЛОКА (в «Контенте») + шаблон сайта. В Битрикс24 — портальные «Настройки» отдельно, настройки CRM за шестерёнкой внутри CRM, права в трёх местах. Чтобы поменять одно поведение, нужно знать, в каком из 3–4 мест оно живёт
- «Иллюзия функциональности» через количество опций (формулировка с Хабра): десятки параметров у каждого модуля создают ощущение мощи, но реальные сценарии всё равно требуют доработки; длинные простыни настроек ≠ настраиваемость. Урок: меньше опций, каждая должна менять что-то видимое
- Режим меняет модель данных незаметно: «классическая/простая CRM» переключается шестерёнкой глубоко внутри и меняет саму сущность (есть лиды или нет) — сотрудники видят разные картины мира. Режимы сложности должны менять ВИДИМОСТЬ, а не семантику данных (наш инвариант W0: скрытие только CSS/UI)
- Жаргонная терминология как барьер: «лид», «смарт-процесс», «дело/активити», «инфоблок», «торговые предложения» (=варианты товара), «highload-блок», «эрмитаж», «композитный сайт», «открытые линии» — внутренние термины платформы вместо языка задач пользователя. Требуется словарь терминов, чтобы читать интерфейс. Урок: язык задач (наш NAV_TASK_LABELS) важнее «правильных» терминов
- Нет единого стиля между модулями: разделы разных поколений выглядят и ведут себя по-разному (старая табличная админка рядом с новыми экранами), одна и та же операция в разных модулях делается по-разному — каждый модуль приходится изучать заново
- Два частично пересекающихся режима редактирования: часть настроек доступна ТОЛЬКО из публички (настройки компонента), часть — только из админки; «админка программиста и админка менеджера — это должны быть две разные админки, а сделан неудобный гибрид» (Хабр). Границу между режимами пользователь выучить не может
- Навигационные страховки вместо лечения структуры: поиск по админ-меню, избранное, большое выпадающее «Меню», горячие клавиши — всё это компенсирует, а не исправляет запутанное дерево. Компенсаторы полезны, но если без них нельзя работать — структура провалена
- Глобальный поиск ищет данные, но исторически не настройки (единый поиск по настройкам появился только в новом разделе «Настройки» и только для админа) — годы «где это включается?» как главный вопрос форумов
- Функция как ещё один пункт меню: каждая новая возможность (КЭДО, Подпись, Онлайн-запись, BI Конструктор…) добавляет корневой пункт вместо встраивания в существующий сценарий — меню растёт линейно с развитием продукта. Урок: новые фичи класть внутрь существующих хабов/сценариев (как наши HUB_TABS), корневой уровень — заморозить
- Скрытие ≠ отключение без объяснения разницы: пункт можно «скрыть в меню» (функция жива и доступна по ссылкам/поиску) или «отключить инструмент» (умирает везде) — два похожих действия с разными последствиями в разных местах настройки
- Перенос сложности на «настройщика»: система предполагает, что меню/права/воронки под сотрудников настроит интегратор; из коробки дефолт неюзабелен для конкретного бизнеса. Наш принцип противоположный: дефолт по архетипу должен быть рабочим без настройки
