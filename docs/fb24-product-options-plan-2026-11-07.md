# FB-24 — вкладка «Optionen»: стандартные и свои типы опций товара

Фидбэк владельца 2026-11-07 + решение того же дня: **стандартные** типы опций (их значения
сопоставлены с фильтрами портала и Google) **и свои** типы владельца; базовый набор стандартных
пополняем по ходу. Разбор батча — `fb-feedback-batch-2026-11-07.md`. **Статус: решения владельца
2026-11-07 — вариант A (типы общие на магазин), стартовый набор §2.1 подходит; в работе FB-24a.**

## 1. Что есть сегодня (разведка, файл:строка)

- **Вариант** `catalog.ProductVariant` (`apps/catalog/models.py:597`): ДВЕ жёсткие оси
  `size` (:611) и `color` (:612) + `label` (:606) — ключ учёта: на нём держатся склад
  (`inventory`, матрица «размер × цвет» `inventory/matrix.py`), снимок заказа
  (`OrderItem.variant_label`), PDF/письма, CSV-импорт (`imports/processors/product.py`),
  уникальность `(product, label)` (:641). Переводы — оверлеи `size_i18n`/`color_i18n` (I18N-10).
- **Фильтры витрины** `catalog/facets.py`: `?groesse=` по оси `size` (с легаси-фолбэком на
  `label`, :22–35) и `?farbe=` по `color` со свотчами (`option_styles.COLOR_HEX`).
- **Портал**: `AggregatorListing.variant_terms` (T-8.26 п.5c) — размеры UPPER + цвета вариантов;
  `?groesse=` портала.
- **Google**: фид Merchant/size/color (WR-1, `catalog/google.py`, `catalog/feed.py`).
- **Вид выбора** `catalog/option_styles.py` (O-волна): список/кнопки/кружки/фото/две оси.
- **Генератор вариантов** (WR-5) — перебирает оси размер × цвет.
- **Модификаторы** (`ModifierGroup/Option`) — платные добавки, НЕ варианты: не трогаем.

Вывод: «третьей оси» нет вовсе — материал/объём/вкус/длина у одежды и товаров приходится
писать в `label` («100 ml · Lavendel»), и такой вариант не фильтруется и не уходит в Google.

## 2. Решение (на согласование)

### 2.1 Данные
- Новая модель **`catalog.OptionType`** (TENANT): `code` (slug), `name` + `name_i18n`,
  `standard` (код из реестра или пусто = свой), `sort_order`, `display` (вид выбора из
  `option_styles`). Значения — **`catalog.OptionValue`**: `type` FK, `value` + `value_i18n`,
  `hex` (для цвета), `sort_order`.
- У варианта — M2M/таблица связи **`VariantOption(variant, type, value)`** (уникально
  `variant+type`). `size`/`color` **остаются** полями и становятся двумя *стандартными* типами:
  при сохранении варианта зеркалим их в `VariantOption` и обратно (приём M4-A «рядом, а не
  вместо»), поэтому склад/заказы/фид/импорт/матрица не переписываются.
- **`label` остаётся ключом учёта**; для новых вариантов собирается из значений осей
  («M · Blau · Baumwolle»), владелец может переписать.
- Реестр **стандартных типов** `apps/catalog/option_types.py`: `size`, `color`, `material`,
  `volume` (ml/l), `weight`, `flavor` (Geschmack), `length`, `pack` (Stückzahl) — у каждого код
  Google (`size`, `color`, `material`, `pattern`… — только те, что Google принимает) и ключ
  фильтра портала. Свой тип портала/Google не получает (честно подписано в форме).

### 2.2 Где управляются типы — **решение владельца ❓ (рекомендую «на магазин»)**
- **A (рекомендую): типы общие на магазин** — экран «Sortiment › Optionen»: список типов,
  значения, порядок, вид выбора. В форме товара на вкладке «Varianten» владелец отмечает,
  какие типы у товара, и генератор строит сетку по ним. Плюс: один фильтр «Material» на весь
  каталог, одинаковые значения (нет «Baumwolle» и «baumwolle»).
- B: типы у каждого товара свои — гибче, но фильтр витрины по своим типам невозможен
  (значения не сопоставимы между товарами), и владелец заводит одно и то же много раз.

### 2.3 Витрина и каналы
- Пикер варианта: N осей (обобщение «двух осей» O-волны) — каждая ось своим видом.
- Фасеты каталога: стандартные типы + свои типы магазина (вариант A) — `?opt_<code>=…`;
  `?groesse=`/`?farbe=` остаются (ссылки и меню живых сайтов целы).
- Портал: `variant_terms` += значения стандартных типов (материал/объём/вкус) — поиск
  «Baumwolle» находит товар; свой тип в портал не уходит.
- Google: стандартные типы со своим атрибутом фида; прочее — в `title`/описании НЕ дописываем.

## 4. Риски
- Склад/матрица/заказы держатся за `label` и `size/color` — поэтому они остаются, а новая
  связь строится РЯДОМ (замки: снимок заказа и леджер байт-в-байт до и после).
- Уникальность `(product, label)`: генератор обязан выдавать различимые label.
- CSV-импорт: колонки `size`/`color` работают как прежде; колонки `opt_<code>` — по спросу.

## 5. Вопросы владельцу
1. Типы опций общие на магазин (A, рекомендую) или свои у каждого товара (B)?
2. Стартовый набор стандартных типов — §2.1 подходит? (Größe, Farbe, Material, Volumen,
   Gewicht, Geschmack, Länge, Stückzahl.)
3. Нужен ли свой тип в фильтре портала, если владелец сам сопоставит его со стандартным
   («Stoff» = Material)? Рекомендую: да, через выбор «entspricht» в форме типа.

## 7. Решения владельца (2026-11-07) и уточнение реализации
- Типы опций — **общие на магазин** (вариант A); стартовый набор стандартных типов §2.1 — подходит.
- Уточнение 24a: оси `size`/`color` **не зеркалим** в новую таблицу — стандартные типы «Größe»/
  «Farbe» читаются прямо из полей варианта (на них держатся склад, матрица, фид, импорт, фасеты);
  в `VariantOption` живут только остальные типы. Двойной записи и бэкфилла нет; единое чтение —
  `option_types.variant_axes(variant)`.
- Какие оси у товара — `Product.option_axes` (список кодов типов, presence-minimal: пусто =
  прежние «размер/цвет»).
