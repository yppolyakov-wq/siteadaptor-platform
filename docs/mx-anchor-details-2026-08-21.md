# MX v4 — Якоря в деталях: продажа, опции, архетипы, кабинет, склад и ERP

**Дата:** 2026-08-21 · **Статус:** детализация стратегии v3 (кода нет, на обсуждение)
**Цепочка:** `mx-multi-sale-analysis` (дефекты) → `mx-sellable-model` (перепись) →
`mx-anchor-strategy` (4 якоря + способы продажи) → **этот документ** (как каждый якорь
работает; отсюда выводятся ассортимент, склад и ERP).

Запрос владельца: расписать по каждому якорю — что и как продаётся, куда попадают
доп-услуги, какие архетипы объединяет, как каждый архетип обрабатывает сущность.
В разделе продаж: отдельный пункт для доп-продаж (видны и в основной сделке) и
отдельные пункты на каждое направление (за направление может отвечать сотрудник).

---

## §0. Словарь (фиксируем термины)

- **Якорь** — за чем клиент пришёл: Вещь · Работа · Проживание · Впечатление.
- **Карточка** — витринная единица якоря (контент, фото, цена, категория, SEO).
- **Способ продажи** — свойство карточки: sofort · slot · zeitraum · platz · anfrage.
- **Опция (доп-услуга)** — добавляется к сделке, меняет цену; четыре вида по природе
  снабжения (§5 — ключ к складу и ERP).
- **Ресурс** — исполнение за кулисами (мастер, стол, комната, мотоцикл, гид);
  клиент его не покупает.
- **Сделка** — экземпляр продажи (заказ, запись, бронь, билет, заявка/смета).
- **Доп-продажа** — проданная опция как строка учёта (сводный экран §6.2).

## §1. Якорь «ВЕЩЬ» (Sache) — единственный якорь со складом

### 1.1 Что и как продаётся
Карточка товара → вариант (оси размер/цвет, свой SKU/EAN/цена/остаток) → модификаторы
(надбавки) → корзина → заказ (`sofort`), либо запрос (`anfrage`: торт на заказ,
Partyservice). Сегодня: `Product`/`ProductVariant`/`ModifierGroup` → `Order`; категории
со страницами и шаблонами (KAT), наборы-упаковки (`Combo`), прайс-виды, PDF-Speisekarte.

**Цифровые Вещи** (по стратегии v3): подарочный сертификат (номинал), абонемент
(N кредитов на Работу, связь `PassPlan.service` есть). Без склада, доставка — письмо
с кодом. Сегодня — теневые чекауты мимо Sortiment и выручки; сводим в этот якорь.

### 1.2 Вариации
- **Вариант** = складская единица (своя цена, свой остаток, своя себестоимость) —
  ось ассортимента;
- **Модификатор** = опция строки (соус, упаковка) — цену меняет, складом сегодня
  не управляет;
- **Упаковка** (`Combo`) = комплект с ценой комплекта. ⚠️ Дефект D6: продажа набора
  не списывает состав — решение владельцем отложено.

### 1.3 Куда попадают доп-услуги
В строку заказа снимком модификатора; после MX-0 снимок несёт id → строки попадают
в сводные «Доп-продажи» (§6.2). Доп-услуги уровня СДЕЛКИ (срочная доставка, подарочная
упаковка на весь заказ) сегодня некуда класть — у заказа опций нет, только доставка;
закрывается MX-2 (опции на сделку-заказ).

### 1.4 Архетипы и их обработка
| Архетип | Роль Вещи | Особая обработка |
|---|---|---|
| Пекарня | primary | предзаказ к слоту выдачи (Auftragsbuch), партии/MHD, `anfrage` на торты |
| Мясник | primary | партии/MHD, Partyservice через `anfrage` |
| Продукты/Aktionsmarkt | primary | акции-слой, лояльность |
| Ритейл | primary | Click&Reserve (Anprobe с дедлайном), доставка |
| Одежда | primary | оси размер×цвет, матрица склада, Lookbook, Warteliste |
| Online-Shop | primary | только доставка + трек-номер |
| Кафе/Ресторан | вторичный | Speisekarte, заказ со стола (QR, table_number), KDS |
| Кейтеринг | витрина | browse-only: состав собирается в заявку, не в корзину |
| Werkstatt | вторичный | Teile: списание при commit заявки |
| Friseur | вторичный | косметика с полки |
| Отель | вторичный | мини-бар/мерч (демо прячет пустой каталог) |

### 1.5 Склад и ERP
Единственный якорь с полным контуром: леджер → партии FEFO → локации → инвентаризация →
себестоимость/маржа (T5) → Bestellvorschlag → закупка `Bestellung` → приёмка.
Дыры: приёмка не пишет расход (`SOURCE_PURCHASE` мёртв), продажа набора не списывает
состав. Всё остальное в платформе касается склада ТОЛЬКО через этот якорь.

## §2. Якорь «РАБОТА» (Leistung) — время исполнителя

### 2.1 Что и как продаётся
Карточка услуги → способ `slot` (клиент выбирает время из свободного; двухшаговый
buy-box, мультивыбор времён HF-6c) → запись `Booking`; либо способ `anfrage` (смета:
`Job` → строки → Angebot → заказ). Прецедент карточного способа — `Service.primary_action`.
Цена — за бронь; множитель `?dauer=` — длительность, не люди.

### 2.2 Вариации
Сегодня вариаций НЕТ — «стрижка короткие/длинные волосы» плодит отдельные Service.
Станет опциями-radio (MX-2). Вторая ось — исполнитель: выбирается (`?resource=`),
но связи Service↔Resource нет (пул = все активные ресурсы) — «красит только Мария»
невыразимо. Третья ось — режим цены (за бронь / за человека) — нужен для
индивидуальной/групповой экскурсии (Tripster), сегодня только «за бронь».

### 2.3 Куда попадают доп-услуги
`Extra` scope=booking — снимок в брони. ⚠️ Найдено разведкой: в КАБИНЕТНОЙ карточке
записи допы не видны и в сумме не показаны (выводится цена услуги, а не итог) —
владелец видит заниженную цену. Фиксить независимо от всего.

### 2.4 Архетипы и их обработка
| Архетип | Роль Работы | Особая обработка |
|---|---|---|
| Friseur | primary (`slot`) | мастер-ресурс, Tagesplan, абонементы, видео-консультация |
| Werkstatt | primary (`slot`+`anfrage`) | бокс/мастер + KVA-смета + Teile со склада |
| Handwerker | primary (`anfrage`) | смета JobLine, материалы со склада при commit, событийные поля AF-1 |
| Кейтеринг | primary (`anfrage`) | заявка с датой/гостями/типом события |
| Кафе/Ресторан | поддержка | **стол = поддерживающая бронь** (депозит-гарантия, не выручка) — якорь тут ужин-Вещь |
| Tour-Operator | будущее | индивидуальная экскурсия за группу (режим цены + гид-ресурс) |
| Отель | вторичный | SPA/массаж к проживанию |

### 2.5 Склад и ERP
Склада у Работы нет, но есть **расходники**: краска, запчасти, материалы. Сегодня
списывает только `anfrage`-ветка (jobs commit_stock). Слотовая ветка (`Booking`) склад
не трогает вовсе — «рецепт услуги» (услуга потребляет N единиц Вещи) — отложенный шов,
решение владельца. Себестоимость Работы = материалы + время; сегодня не считается нигде.

## §3. Якорь «ПРОЖИВАНИЕ» (Aufenthalt) — юнит × ночи

### 3.1 Что и как продаётся
Карточка категории номера → способ `zeitraum` (диапазон дат, календарь наличия, правила
min-stay/CTA/CTD) → бронь `StayBooking`. Цена: базовая × ночи по сезонам + тариф
(`RatePlan`: питание/отмена, предоплата 0/часть/100 %) + дети + Kurtaxe − авто-скидки
(LOS/Frühbucher/Lücken) − промо-слой. Богатое исполнение: шахматка, физические комнаты,
housekeeping, Meldeschein, Online-Checkin, Channel-фундамент.

### 3.2 Вариации
Категория = карточка; тариф = вариант ЦЕНЫ (не сущности); физический Room — исполнение.
Это самый зрелый якорь: у него уже есть всё, что стратегия хочет дать остальным.

### 3.3 Куда попадают доп-услуги
`Extra` scope=stays, разовые и per-night (завтрак, парковка, поздний выезд) — снимок
в брони. Два доказанных денежных дефекта пересчёта (MX-0). Прикреплённые сделки
(VS-3, велопрокат) — соседний механизм: **опция = строка внутри сделки, прикреплённая
сделка = отдельная сделка со своим статусом**; граница — «нужен ли допу свой статус».

### 3.4 Ключевой разворот якоря (главный пример стратегии)
**Одна и та же ночёвка:** у отеля — ЯКОРЬ (свой ресурс, свой календарь, своя выручка);
у тур-оператора — **ОПЦИЯ с закупкой** («одноместное размещение +250 €» → потребность
заказать номера у партнёра в Джиспе — SupplierBooking kind=hotel). Не тащить stays-движок
в туры, а дать опции вид «закупаемая» (§5). У ретрита — середина: проживание к билету
из СВОЕГО фонда (accommodation_units уже работает).

### 3.5 Архетипы: hotel (primary), events/retreat (койка к билету), tour_operator
(закупаемая опция), other/Ferienwohnung.

### 3.6 Склад и ERP
Свой фонд — не склад (ничего не расходуется, занимается время). Расходники завтрака —
через «рецепт» (как у Работы, отложено). Внешнее размещение — закупка SupplierBooking.

## §4. Якорь «ВПЕЧАТЛЕНИЕ» (Erlebnis) — места на дату продавца

### 4.1 Что и как продаётся
Карточка (сегодня `Tour`; для одиночных событий карточка = само событие) → даты
(`Event`-заезд: своя ёмкость, тиры, депозит, рассрочка) → способ `platz` → билет
`Ticket` (цена за место × количество); способ `anfrage` — приватная группа (уже
работает у moto через jobs). Богатое исполнение: анкеты, waiver, check-in, roster,
логистика, маршрут с видимостью, чат группы, досье.

### 4.2 Вариации
Тиры = категории места (одна ось, свободный текст — усилить); даты = группировка на
карточке (обобщить `Tour`, оживить мёртвый `series_id` для курсов/серий); формат
инд/группа = способ продажи, не отдельная сущность.

### 4.3 Куда попадают доп-услуги
`Extra` scope=events + встроенное проживание к билету. Будущее (ядро мото-кейса):
опции с ёмкостью и закупкой — «аренда Enfield 500 (+400 €)» ограничена парком в 8 машин
и порождает заказ мотопрокату. Сводный экран доп-продаж отвечает «сколько аренд продано
на заезд X» → кнопка «заказать у поставщика».

### 4.4 Архетипы и их обработка
| Архетип | Роль | Обработка |
|---|---|---|
| Events/Retreat | primary | анкеты, waiver, рассрочка, проживание к билету |
| Tour-Operator | primary | тур-карточка, маршрут, логистика, чат, приватный выезд |
| Ресторан | вторичный | винные ужины/дегустации (pranasy) |
| Кейтеринг | suited | мастер-классы |
| Friseur/прочие | эпизодически | воркшопы |

### 4.5 Склад и ERP
Самый закупко-ёмкий якорь: SupplierBooking (форма готова) + ExpenseEntry + маржа заезда
(MT-5, v1 есть). Не хватает: связи «проданные опции → qty закупки» и расходов вне туров.

## §5. Четыре вида опций — ключ к складу и ERP

Вид опции определяет, что происходит за кулисами. Это ядро ответа «от этого зависит
ассортимент, склад и ERP»:

| Вид | Пример | Склад | ERP |
|---|---|---|---|
| **Надбавка** | сервисный сбор, украшение торта | — | только цена |
| **Расходуемая** | завтрак, бутылка вина к брони, краска | списывает Вещь со склада при исполнении (рецепт) | себестоимость из cost_price Вещи |
| **Ёмкостная** | мотоцикл из парка 8 шт, кресло визажиста | резервирует единицу ПУЛА на срок сделки | пул = ресурс, не склад |
| **Закупаемая** | номер у отеля-партнёра, пермит, трансфер | — | порождает потребность → SupplierBooking → расход → маржа опции |

Одна опция может быть ёмкостной И закупаемой (свой парк 5 байков + докупка у проката).
Минимум для старта (MX-2): вид «надбавка» + поле поставщика; «расходуемая» и «ёмкостная»
— вторым шагом, «рецепт» — за отдельным решением.

## §6. Кабинет «Verkäufe» — по требованиям владельца

### 6.1 Направление = отдельный пункт (за него отвечает сотрудник)
Уже так с SM-2a: вкладка на каждый активный модуль, внутри Kalender/Board/Liste.
Закрепляем принципом: **вкладка = направление = зона ответственности**. Роли admin/staff
сегодня идентичны (решение владельца «оставить как есть») — когда понадобится «сотрудник
видит только своё направление», ось уже готова: гейт вкладки по роли, не новая структура.

### 6.2 НОВОЕ: пункт «Zusatzverkäufe» (доп-продажи)
Сводный список ПРОДАННЫХ опций по всем направлениям: строка = опция × сделка
(что, к какой сделке, статус сделки, день исполнения). Фильтры: тип опции, день,
направление. Примеры вопросов, на которые отвечает: «сколько завтраков завтра»,
«сколько аренд байка на заезд 12.09», «какие доп-работы в цеху на неделе».
- Та же опция остаётся видимой в карточке своей сделки (сегодня у записи — не видна,
  фикс в §2.3).
- Требует MX-0 (id опции в снимке) — без id список не собрать.
- Из строки доп-продажи закупаемого вида — переход к созданию SupplierBooking.
Размещение: вкладка в ряду направлений Verkäufe (гейт: есть проданные опции), плюс
подпункт сайдбара. ⚠️ Якоря сайдбара под мораторием X7.1 — вкладка мораторий не трогает.

### 6.3 Поддерживающие брони
Стол ресторана — вкладка направления «Termin» как сейчас, но: депозит ≠ выручка,
в журнал не пишется (и сегодня не пишется — корректно), на карточке пометка роли.

## §7. Матрица: тип бизнеса × якоря (ассортимент типа)

P = primary, ● = вторичный, a = режим anfrage, (о) = как опция

| Тип | Вещь | Работа | Прожив. | Впечатл. | Замечание |
|---|---|---|---|---|---|
| Пекарня | **P** | a (торты) | — | — | слоты выдачи |
| Мясник | **P** | a (Party) | — | — | партии/MHD |
| Продукты | **P** | — | — | — | акции-слой |
| Ритейл | **P** | — | — | — | Anprobe-резерв |
| Одежда | **P** | — | — | — | оси, матрица |
| Online-Shop | **P** | — | — | — | доставка |
| Кафе | **P** | ● стол | — | — | QR-стол |
| Ресторан | **P** | ● стол | — | ● ужины | KDS |
| Кейтеринг | ● витрина | **P a** | — | ● мастер-классы | наборы |
| Отель | ● мини-бар | ● SPA | **P** | — | шахматка |
| Friseur | ● полка | **P** | — | ● воркшопы | мастер-ресурс |
| Werkstatt | ● Teile | **P** (slot+a) | — | — | склад запчастей |
| Handwerker | — | **P a** | — | — | смета+материалы |
| Events | ● мерч | ● | ● койки | **P** | ретрит-пакет |
| Tour-Operator | — | ● инд.экск. | (о) закупка | **P** | опции+логистика |
| Other | по выбору | | | | |

Следствия:
- **Ассортимент** типа = его строка матрицы: Sortiment показывает разделы включённых
  якорей (+ упаковки + цифровые Вещи). Пресеты модулей уже близки — расхождения
  пресет↔демо у 9 типов чинить по матрице.
- **Склад** нужен только типам с P/● в колонке «Вещь» + werkstatt/handwerker
  (материалы). Ни один якорь, кроме Вещи, склад сам не заводит.
- **ERP** = три контура закупки: складская `Bestellung` (Вещь, по Meldebestand) ·
  сервисная `SupplierBooking` (закупаемые опции + Впечатление + внешнее размещение) ·
  материалы Работы (складская, через commit/рецепт). Все три пишут в ЕДИНЫЙ журнал
  расходов (MX-1) → маржа по сделке / направлению / периоду.

## §8. Открытые развилки (сужены по этому обсуждению)

1. **Старт MX-0** (id опции + 2 денежных фикса + допы в карточке записи §2.3) — да?
2. **Виды опций (§5):** согласен ли владелец с четырьмя видами; в v1 берём
   «надбавка+поставщик», ёмкостную и расходуемую — вторым шагом?
3. **Рецепт услуги** (Работа списывает материалы со склада при исполнении, как jobs) —
   делаем в этой программе или откладываем?
4. **«Zusatzverkäufe»** — вкладка в Verkäufe (без снятия моратория) устраивает?
5. Прежние: гид/мастер с занятостью? сертификат/абонемент в каталог? связь
   Service↔Resource («красит только Мария»)?
