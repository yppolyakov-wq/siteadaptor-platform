# T-10 «Быстрый деплой» — план на обсуждение (2026-10-20)

Запрос владельца: «обновление занимает уже часы — как оптимизировать обновление/деплой?».
Ниже — разбор по коду (`scripts/deploy.sh`, `Dockerfile`, `docker-compose.prod.yml`,
`seed_demo_tenants`), а не догадки. Кода ещё нет — сначала решения владельца (§4).

## 1. Куда уходит время (по коду)

| # | Шаг | Что происходит сейчас | Оценка |
|---|-----|-----------------------|--------|
| A | Сборка образа | В Dockerfile `COPY . .` стоит ДО `uv pip install`. Любая правка кода сбрасывает слой зависимостей → **все пакеты ставятся заново на каждом деплое**, да ещё с `--no-cache`. `uv:latest` из ghcr сверяется по сети при каждой сборке. | 3–10 мин |
| B | Три одинаковых сборки | `web`, `worker`, `beat` — у каждого `build: .`; compose собирает и тегирует образ трижды (кэш помогает, но не до нуля). | +1–2 мин |
| C | Миграции схем бизнесов | `migrate_schemas` идёт по **130 схемам по одной** (79 из них — демо волны DCC). Для каждой — граф из ~350 миграций, даже если применять нечего. | 2–15 мин, растёт с каждым демо |
| D | collectstatic дважды | Шаг 7 `run --rm collectstatic` пишет во временный контейнер и **ничего не даёт** (рабочий web делает collectstatic сам при старте — см. compose). 40 МБ статики, ~900 демо-фото хешируются заново. | 1–2 мин впустую |
| E | **Пересев демо** | `seed_demo_tenants --recreate`: каждый кит удаляет схему и создаёт её заново, а создание схемы = **прогон всех ~350 миграций с нуля (~1 мин и растёт)**. Плюс наполнение. ~100 китов → **1,5–3 часа**. | **часы** |

Главная гипотеза: «часы» — это шаг E (пересев демо после деплоя), а не сам `deploy.sh`.
Шаги A–D дают ещё 10–30 минут на каждом деплое. Подтвердить замером — §3 D-0.

## 2. Что предлагаю (по убыванию выигрыша)

**D-1 Создание схемы клонированием, а не миграциями** (самый крупный выигрыш).
django-tenants это умеет штатно: `TENANT_BASE_SCHEMA` — шаблонная схема, которая
мигрируется вместе со всеми, а новая схема **копируется** из неё (`clone_mode="NODATA"` —
только структура). Создание схемы: ~60 с → ~2–5 с. Выигрывают сразу три места:
пересев демо (часы → минуты), **регистрация настоящего бизнеса** (сейчас минута ожидания на
экране «создаётся») и тесты. Риски: шаблон обязан быть на последней миграции (деплой
мигрирует его первым); данные из data-миграций (если какие-то пишут строки) клон без данных
не перенесёт — проверю каждую data-миграцию TENANT-приложений до включения.

**D-2 Пересев только изменённых демо и не во время деплоя.**
- Хеш спеки кита хранится у демо-тенанта; `seed_demo_tenants --changed` пересоздаёт только
  киты, чья спека поменялась (обычно 1–3, а не 100).
- Пересев идёт фоновой задачей ПОСЛЕ деплоя (сайт уже работает), а не руками в консоли.

**D-3 Сборка образа за секунды при правке кода.**
- Dockerfile: сначала `pyproject.toml` + `uv.lock` → установка строго по локу (`uv sync --frozen`,
  как уже делает CI), потом `COPY . .`. Зависимости пересобираются, только когда меняется лок.
- Кэш uv через `--mount=type=cache` (встроенный BuildKit это умеет без загрузки сборщика —
  урок T-9 учтён), версия uv закреплена вместо `latest`.
- Один образ на web/worker/beat (`image: siteadaptor-app`, сборка один раз).
- Ожидание: 3–10 мин → 20–60 с при обычной правке кода.

**D-4 Параллельные миграции и пропуск, если нечего применять.**
- `migrate_schemas --executor=multiprocessing` (штатно в django-tenants, 4 процесса).
- Если `migration_state` говорит «всё применено» — шаг миграций схем бизнесов пропускается.
- Ожидание: минуты → десятки секунд.

**D-5 Мелочи.** Убрать бесполезный шаг 7 (collectstatic во временном контейнере); печатать
длительность каждого шага; `--recreate` демо — только явной командой.

**D-6 (по желанию, позже) Сборка в GitHub Actions.** CI уже собирает и проверяет код;
образ можно собирать там же и класть в GitHub Container Registry, а сервер будет только
скачивать готовый образ. Сборка на сервере исчезает совсем. Нужен токен на чтение пакетов
на сервере — это решение владельца.

## 3. Порядок и проверка

1. **D-0 замер** (без риска): тайминги шагов в `deploy.sh` + одна строка от владельца — сколько
   длится сам деплой и сколько пересев демо.
2. **D-5 + D-3** (сборка) — безопасно, без изменения данных; проверка: деплой без правок
   зависимостей ≤ 1 мин на сборку.
3. **D-4** (миграции) — проверка на копии: `migrate_schemas` с параллельным исполнителем на
   130 схемах, сверка `migration_state`.
4. **D-1** (клонирование) — сначала разведка data-миграций, замки «клон = миграции» (сравнение
   структуры схемы, созданной клоном и миграциями), затем включение.
5. **D-2** (пересев изменённых) — поверх D-1.

Каждый шаг: план → тесты → ревью (django + database, D-1 ещё security) → зелёный CI → в `main`.

## 4. Вопросы владельцу

1. Что именно длится часы: сам `./scripts/deploy.sh single` или пересев демо
   (`seed_demo_tenants … --recreate`)? Если можно — время каждого.
2. Порядок D-0 → D-5/D-3 → D-4 → D-1 → D-2 — согласны? (Рекомендую: да.)
3. Клонирование схем (D-1) включаем и для регистрации настоящих бизнесов, не только для демо?
   (Рекомендую: да — минута ожидания при регистрации уходит.)
4. D-6 (сборка в GitHub и готовый образ на сервер) — делать сейчас или позже? (Рекомендую:
   позже, после D-1–D-5; выигрыш тогда уже небольшой.)
5. Все ~100 демо нужны на сервере постоянно? Если часть (например, 79 демо Золингена) нужна
   только для показа портала — можно держать их и не пересевать при каждом обновлении.

## 5. Решения владельца и исполнение (2026-10-20)

Ответы: (1) `deploy.sh single` долгий, но **часы — пересев демо**; (2) порядок принят;
(3) клонирование — и для регистрации настоящих бизнесов; (4) D-6 — позже;
(5) демо засеваются один раз и обновляются только при необходимости.

**Сделано D-0/D-3/D-4/D-5** — тайминги шагов; Dockerfile: зависимости строго по `uv.lock`
отдельным слоем до `COPY . .`, uv закреплён; один образ на web/worker/beat; шаг миграций
пропускается при `migration_state --check`, иначе 3 процесса с повтором по одной схеме;
лишний collectstatic снят; тег образа по коммиту для отката.

**D-1 — схема копией шаблона.** Встроенный `TENANT_BASE_SCHEMA` НЕ используем: после копии
он запускает `migrate_schemas --fake`, и отставший шаблон тихо помечает недостающие
миграции применёнными. Свой путь (`apps/tenants/schema_template.py`):
- `TENANT_TEMPLATE_SCHEMA` (по умолчанию `_template`, пусто = выключено);
- копия режимом `DATA` (вместе со служебными `django_migrations`/contenttypes/permissions),
  только если шаблон свежий и чистый (в таблицах бизнеса ни строки);
- копия под `pg_try_advisory_xact_lock`: шаблон мигрирует — новая схема идёт миграциями,
  без ожидания;
- после копии: имена ограничений возвращаются по шаблону (функция копирования
  переименовывала UNIQUE `…_uniq` → `…_key` — поймано замком), структура копии сверяется с
  шаблоном в той же транзакции; расхождение или ошибка = откат, путь миграциями;
- миграция, появившаяся между проверкой и копией, применяется ПО-НАСТОЯЩЕМУ;
- `manage.py ensure_template_schema` (шаг деплоя 6a) строит/освежает шаблон; грязный —
  отказ, `--force` пересоздаёт; `migration_state` включает шаблон в сверку.
Замер: копия ~2,5 с против ~100 с миграциями.

**D-2 — пересев только изменённых.** Отпечаток кита (`apps/tenants/demo_fingerprint.py`):
sha256 спеки `DemoKit` + переводов строк этого кита + `SEEDER_VERSION`; хранится в
`site_config["demo_kit"]` (без миграции). `seed_demo_tenants --changed` создаёт
недостающие и пересоздаёт изменённые, остальные пропускает; `--stamp` — разово записать
отпечатки уже засеянным демо. Правило: меняя код сидера (не спеку), поднять `SEEDER_VERSION`.

**Ops владельцу (после деплоя, один раз):**
1. `./scripts/deploy.sh single` — шаг 6a сам построит шаблон (~1–2 мин один раз).
2. `docker compose -f docker-compose.prod.yml exec web python manage.py seed_demo_tenants --group all --stamp`
3. Дальше после обновлений: `… seed_demo_tenants --group all --changed --jobs 3` — пересевает
   только изменённые киты.
