# KA-11 — сводка аудита кабинета и путь к реальному тестированию (2026-10-23)

Итог программы KA (`ka-cabinet-audit-program-2026-10-22.md`): 14 отчётов KA-0…KA-10,
11 хотфиксов KA-H1…H11, решения ИИ AI-1/AI-2. Здесь — выводы, а не перечень:
что нашли, что исправили, какой корень, что блокирует пилот, какие вопросы владельцу.

## 1. Что показал аудит — коротко

Платформа **широкая и в основном работает**: 16 архетипов, ~1400 экранов кабинета
открываются (стенд KA-0), ядро продаж/броней/акций проходит. Но у каждого направления
есть **«последняя миля»** — места, где деньги, данные или обещание клиенту расходятся
с тем, что реально произойдёт. Таких мест найдено много, и они однотипны.

**Исправлено сразу (деньги / данные / закон) — 11 хотфиксов:**

| | Что было | Что стало |
|---|---|---|
| H1 | Сохранение статусов без входа, изменения по GET | Вход + POST, замок на все вьюхи кабинета |
| H2 | IBAN для Vorkasse мог сменить любой сотрудник | Только владелец, проверка IBAN, письмо при смене |
| H4 | Отмена с разных экранов по-разному возвращала деньги | Один путь возврата Stripe со всех поверхностей |
| H5 | Счёт из сметы со скидкой — 404, гости брони терялись, нет Zusatzstoffe в PDF | Исправлено |
| H6 | Отель: депозит считался полной оплатой, питание по 7 %, овербукинг iCal молчал | Депозит/остаток, питание 19 %, предупреждение |
| H7 | Абонемент давал двойную выручку, ставка НДС неверная, TÜV-напоминание по отменённым | Исправлено |
| H8 | Отмена события не возвращала деньги участникам, выручка не сторнировалась | Фоновая отмена с возвратами и письмами |
| H9 | Сертификат гасился целиком, чужой купон раскрывался | Списание остатка, купон не раскрывается |
| H10 | Принятую смету можно было менять, счёт без Leistungsdatum, Mahnung на оплаченное | Смета заперта, §14 UStG, Mahnung на остаток |
| H11 | Обезличивание стирало клиентов с живыми сделками; любой сотрудник выгружал ПДн | Живые сделки защищены; выгрузки — владельцу, с журналом |

## 2. Корни — почему проблем много и они похожи

Полторы сотни находок сводятся к **пяти корням**. Чинить их по одной — бесконечно;
чинить корни — конечно.

1. **Деньги без единого контракта.** Оплата, депозит, остаток, возврат, выручка в
   журнале, счёт — каждый вид сделки делает по-своему. Отсюда H4/H6/H7/H8/H10 и ещё
   открытые E8 (возврат только депозита), E9 (банк в обход FSM), E11 (выручка без
   оплаты), H6 (аванс без документа), Z9 (сертификат режет базу НДС).
   → **Решение:** один «денежный контракт» сделки (оплачено / к оплате / возвращено /
   проведено в журнал) и **сквозной тест-инвариант**: для любой сделки после любого
   перехода «журнал = оплачено − возвращено», «счёт = сделка», «Offene Posten =
   к оплате». Это ловит целый класс сразу и на будущее.

2. **Брошенные оплаты держат ресурс бессрочно.** Z7 (номер), E10 (места события),
   неоплаченные корзины. → Единый срок удержания для всех видов (`expire_payment_holds`
   уже есть для счёта фирме — распространить).

3. **Ручной ввод в кабинете беднее витрины.** Ручная бронь, запись, билет, заявка
   не знают полей, которые знает витрина (H5, H7 исправили часть). → Одна форма
   сделки на обе стороны, а не две.

4. **Меню и доступ не учитывают пакет и направление.** Лёгкий бизнес «Nur Aktionen»
   по ссылкам доходит до 70 экранов полного кабинета; ERP-экраны есть только в Ctrl+K;
   демо богаче, чем реальный новый бизнес. → Уже спроектировано: пакеты T-8.32
   (KA-3) + структура KA-4. Это и есть «комплексное решение» для кабинета.

5. **Нет общей дизайн-системы.** 1129 жёстких `indigo`, 55 видов кнопок, контраст
   серого 2.5:1, поля без подписей, мелкие цели на телефоне (KA-6/KA-8, WCAG). →
   Токены + 6–8 компонентов, затем замена по экранам.

## 3. Что блокирует РЕАЛЬНОЕ тестирование

Моё мнение: **открытое тестирование всеми направлениями сразу — рано. Контролируемый
пилот с 3–5 реальными бизнесами в одном-двух направлениях — можно, после короткого
списка ниже.**

**Блокеры пилота (обязательно до первого реального клиента):**

| # | Что | Почему блокер | Где |
|---|---|---|---|
| P1 | Stripe live + Connect, Resend, бэкапы, Sentry | Без этого нет денег, писем и восстановления | Stage 0, владелец |
| P2 | Юр. вычитка: Impressum (правовая форма, L6), Datenschutz, Widerruf, AVV | Абмаскир-риск с первого дня публичной витрины | KA-1/KA-9, юрист |
| P3 | Время забора обещано, но не выбирается (W-1) | Click&Collect не выполняет обещание | KA-5a |
| P4 | Списки молча обрезаются на 200/50 | Владелец «теряет» заказы и клиентов, 201-му не выставить счёт | KA-7, KA-5a |
| P5 | Телефон: iOS зумит поля, «12,50» не принимается, сканер ваучеров на iOS | Основная работа владельца — с телефона | KA-6 |
| P6 | Брошенные оплаты держат номер/места | Потерянные продажи | KA-5d Z7, KA-5e E10 |
| P7 | Лёгкий кабинет открывает полный по адресам | Путаница, лишние действия | KA-0, решается T-8.32 |

**Не блокер, если сузить пилот:** касса/TSE (не продаём Mini App как кассу в пилоте),
план зала, мастера по колонкам, генератор вариантов, E-Rechnung 2027.

## 4. Рекомендуемый порядок

1. **Пилот-скоуп.** Направления первой волны: **Aktionen (лёгкий)** + **Waren /
   Click&Collect**. Они самые проверенные (T-8, SF, AMP) и ближе всего к «пятиминутному
   старту». Отель/события/ремесло — вторая волна.
2. **Волна «пилот-блокеры»** P3–P7 (≈1–2 недели работы).
3. **Пакеты T-8.32** — гейт доступа по направлению (решает P7 и половину KA-4).
4. **Денежный контракт + тест-инвариант** (корень №1) — до второй волны направлений.
5. Параллельно — Stage 0 и юрист (владелец).
6. Дизайн-система и доступность — после пилота, по фидбэку.

## 5. Каких тестов не хватает

Что есть: ~4900 серверных тестов, замки классов, стенды Playwright по фичам. Чего нет:

1. **«Золотые пути» на стенде** — сквозной браузерный сценарий на каждое направление
   пилота: регистрация → первая акция/товар → заказ клиента → оплата (Stripe test) →
   выдача/погашение → журнал/счёт. Сейчас фичи проверялись по отдельности.
2. **Денежный инвариант** (см. корень №1) — один параметризованный тест на все виды.
3. **Реальные устройства:** iPhone Safari, Android Chrome, Telegram Mini App на обоих.
4. **Роли:** сценарий «сотрудник» на каждом экране (что видит, что может).
5. **Нагрузка:** прогнать k6 (`scripts/load/`) на стенде, близком к проду.
6. **Восстановление:** учебный restore из бэкапа на чистый сервер.
7. **Почта:** реальные письма в Gmail/Outlook/GMX (спам, вёрстка, ссылки).
8. **Пилотный протокол:** что меряем (время до первой акции, ошибки, обращения).

## 6. Вопросы владельцу (сведены из всех отчётов)

1. **Пилот:** согласны с первой волной «Aktionen + Click&Collect» и 3–5 бизнесами Solingen?
2. **Выручка заявок/мастерской** (KA-5c В-1): писать в журнал при выставлении счёта? (рекоменд.)
3. **Отмена брони из кабинета** (KA-5d В-1): спрашивать «вернуть деньги / не возвращать»? (рекоменд.)
4. **Витрина до подтверждения почты** (KA-5f В-1): скрывать? (рекоменд. — скрывать)
5. **Каталог города** отмечен заранее (L8): оставить или снять галочку по умолчанию?
6. **Widerruf при онлайн-принятии сметы** (KA-5f В-3) — к юристу.
7. **DATEV/выручка для бухгалтера-сотрудника:** открыть роли admin или оставить только владельцу?
8. **GoBD 10 лет vs DSGVO Art. 17** для клиентов только с заказами/счетами — к юристу.
9. **Касса/TSE** — исключаем Mini App-кассу из пилота?
10. **Тёмная тема** кабинета (KA-8 VI-9) — нужна?
11. **ИИ:** после теста на прямом ключе — переход на ключ ЕС до пилота?
