«проверяй остальные архетипы на похожие проблемы». Ниже — факты по коду, а не по

## 1. Что выяснила разведка

| Наблюдение | Факт по коду |
|---|---|
| Деталь заказа read-only | `templates/orders/order_detail.html` умеет только смену статуса и «оплачено». Ни состав, ни количество, ни доставка, ни скидка, ни клиент не правятся |
| Налоги | у `OrderItem` НЕТ ставки НДС; у `Product` тоже. Ставки живут только в `finance.RevenueEntry.VAT_RATES` и на счёте → «разный налог на товар» требует миграции |
| Второй номер заказа | поля нет (`Order.reference_code` один, `unique`) |
| Плательщик/счёт | поля «плательщик» нет; есть `payment_state`, `payment_method` (E-7), `stripe_payment_intent`, счёт — через `finance` |
| Скидка | `Order.discount_cents` + `voucher_code` ЕСТЬ, но задаются только промокодом на витрине — в кабинете не правятся |
| Доставка | `fulfillment`, `shipping_address`, `shipping_cents`, `tracking_code` есть; правится только трек-номер (W10-5) |
| «Хлебные крошки» под заголовком | ряд ссылок в теле Belegungsplan (`stays/_belegungsplan_body.html`) — 6 ссылок, дублирующих сайдбар, плюс второй `<h1>`. **Тот же класс у booking** (`_tagesplan_body.html`: свой `<h1>Kalender</h1>` + 5 ссылок) |
| Свёрнутое меню | `body.sb-min #sidebar { display: none }` — сайдбар исчезает целиком, иконок не остаётся |
| Русские подписи вкладок | в РЕПО корректны: Заказы · Записи · Ночлеги · Билеты · Заявки. На скрине владельца «6 ночевок / Даты / Заказы / Заказы» → сервер крутит СТАРУЮ сборку переводов; лечится деплоем |
| Календарь у заказов | `KIND_VIEWS["order"]` включает `kalender` (Auftragsbuch по `pickup_slot`) — у магазина слоты выдачи не используются, вид пустой |

## 3. Группа B — редактирование сделки (без миграций)

| п. | Что делаем |
|---|---|
| 2/3 | правка состава заказа: количество, удаление позиции, свободная позиция; пересчёт итога |
| 5 | правка клиента с карточки заказа — тем же приёмом, что уже сделан у заявки (QF-4), и на всех архетипах |
| 6 | правка доставки: адрес, стоимость, способ (самовывоз/доставка), трек-номер |
| 7 | скидка на заказ: сумма или процент, с причиной; ложится в существующий `discount_cents` |

**Опасное место.** Изменение количества у ПОДТВЕРЖДЁННОГО заказа обязано двигать
склад и выручку тем же движком, что создание и отмена (`orders.services`,
FSM-хуки, `inventory.record_movement`) — иначе счётчик разойдётся с леджером
(класс T1). Поэтому правка состава идёт через сервис, а не через прямое
изменение полей, и покрывается замками «склад сошёлся после правки».

## 6. Решения владельца (2026-08-20)

1. **Налог:** ставка на ТОВАРЕ + СНИМОК в позиции заказа; итог разбивается по
   ставкам. Две аддитивные миграции.
2. **Правка заказа:** править ВСЕГДА (любой незакрытый), склад и выручка
   пересчитываются тем же движком, что создание/отмена; замок «счётчик сошёлся
   с леджером».
3. **Второй номер:** внешний номер (касса/маркетплейс/бумажный журнал), свободное
   поле, ищется поиском.
4. **Клиенты:** вкладка в «Продажах» у ВСЕХ архетипов без включения CRM; CRM
   остаётся модулем для тегов/заметок/сегментов.

   *Исполнено 2026-08-20.* Вкладка «Kunden» стоит СПРАВА от ряда направлений и в
   него не входит — иначе одинокое направление снова получило бы ряд вкладок
   (VS-2a). Тело вкладки — тот же партиал и тот же контекст, что у экрана CRM
   (`crm/_customer_list_body.html` + `crm.views.customer_list_context`), так что
   расхождению данных взяться неоткуда. Без модуля список ЧИТАЕТСЯ, но ссылок в
   `/crm/` нет (гейт путей дал бы 404 — класс дефекта из сверки 2026-08-19), а
   вместо кнопок стоит честная строка «карточка/теги/история — в модуле».

   **SH-14 (доставка).** Отдельного экрана доставки не заводим: «Lieferungen» —
   подпункт сайдбара, ведущий на список заказов с фильтром `?versand=1`
   (`fulfillment=delivery`; `is_delivery` — свойство, не поле). Фильтр включён в
   `_VIEW_FILTERS`, поэтому адрес с ним ИСПОЛНЯЕТСЯ: доска его не понимает →
   вид падает на «Liste» (правило ревью 2026-08-19). В тулбаре — снимаемый чип.
   Дедуп подпунктов сайдбара стал по паре (url_name, query) — иначе второй пункт
   на ту же страницу продаж молча исчезал бы; палитра Ctrl+K дедупит по-прежнему
   по url_name (она адресует экраны без query).

### Исходные варианты (для истории)

1. **Налог (п.4).** Ставка на товар и снимок в позиции (рекомендую) · одна ставка
   на весь заказ · пока только показ уже имеющейся ставки бизнеса.
2. **Правка подтверждённого заказа (п.2/3).** Править всегда с пересчётом склада
   (рекомендую, но это движение остатков задним числом) · править только до
   подтверждения, дальше «сторно + новый».
3. **Второй номер заказа (п.8).** Что это: внешний номер (маркетплейс/касса) ·
   номер счёта · свой формат нумерации? От ответа зависит поле и валидация.
4. **Клиенты (п.15).** Списка клиентов нет там, где модуль CRM выключен (у 9 из
   15 типов). Варианты: вкладка «Kunden» внутри Продаж для всех · включить CRM
   всем по умолчанию · оставить как есть (модуль включается на «Funktionen»).

**Ключевые решения реализации.**

* Цены в проекте БРУТТО (PAngV) — значит НДС не доначисляется, а выделяется:
  `netto = brutto / (1 + r)`. Скидка уменьшает базу пропорционально долям ставок,
  доставка облагается по максимальной ставке заказа (правило Nebenleistung).
* Движения склада при правке пишутся БЕЗ `source_ref`: `record_movement`
  идемпотентен по (source, ref, kind), и второе такое же изменение количества
  молча потерялось бы.
* Терминальный заказ не правится: его остаток уже вернул FSM, повторное движение
  задвоило бы склад. Замок `test_closed_order_is_not_editable`.
* Пикер позиций вынесен в `apps/catalog/picker.py` — у сметы и у заказа один
  список «что можно добавить» (у заявки он уже был, QF-1).
