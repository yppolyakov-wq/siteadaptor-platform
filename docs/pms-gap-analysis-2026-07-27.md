# PMS-анализ: спека TravelLine (WebPMS + Price Optimizer + CRM) ↔ наш код

**Дата:** 2026-07-27 · **Метод:** 5 адверсариальных разведчиков по коду (фронт-деск/
шахматка · гости/расчёты/документы · отчётность · ценообразование · CRM/рассылки),
каждый факт с файлом:строкой. Блок Booking Engine (§3) разобран ранее тем же днём —
его приоритет №1 (G12 Verkaufsregeln) уже реализован и в main.

## 0. Резюме

Мы сильны там, где спека про **онлайн-продажу** (booking engine ~80 % закрыт,
включая G12) и **право DACH** (Meldeschein/GoBD/DATEV/UWG/PAngV — у TravelLine
этого среза в таком виде нет). Мы слабы там, где спека про **работу стойки**
(front-desk операции, платежи на месте, хаускипинг) и **автоматику маркетинга**.

**Три системных корня большинства пробелов:**
1. Нет сущности «физический номер» (StayUnit = категория с quantity) → нет
   статусов номера, хаускипинга, переселения «в номер», построчной шахматки.
2. Нет «карточки проживания» (folio) с журналом начислений/платежей → нет
   пост-начислений, доплат, раздельной/корпоративной оплаты, сверки при выезде.
3. Нет сущности «компания» → нет корпоративного контура.

Вводить ли №1 (физические номера) — **ключевая архитектурная развилка владельца**;
всё остальное реализуемо на текущей модели.

## 1. WebPMS (§5) — статус по разделам

- **5.2 Шахматка** ⚠️ — tape chart есть (плашки, drag, клип, счётчики свободного,
  клик→walk-in), но по категориям, не по номерам; нет маркеров заезд/выезд, долгов
  и пиктограмм на плашках; горизонт фикс. 30 дней. Кастом-статусы теряют цвет/drag
  (литералы в шаблоне).
- **5.3 Создание брони** ⚠️ — **самый дешёвый большой разрыв:** движок `book_stay`
  принимает тариф/питание/extras/adults+children/rooms/промокод — витрина всё
  передаёт, кабинетная форма НЕ передаёт ничего из этого (плюс поле note в форме
  отсутствует, хотя вьюха его читает).
- **5.4 Редактирование** ⚠️ — перенос дат (кнопки+drag) и смена категории drag'ом
  есть; смена тарифа/состава гостей/услуг, платежи, split/merge, правка
  комментария — нет.
- **5.5 Профили гостей** ⚠️ — контакты/теги/заметки/история/LTV есть; паспортные
  данные живут в разовом Meldeschein (1:1 к брони, purge через год), не в профиле;
  дедуп только по email; ФИО одной строкой; ДР/адрес/компания — нет.
- **5.6 Заселение** ⚠️ — G6 Online-Checkin/BMG-контур аккуратный (подпись, purge,
  DSGVO), но самого check-in у стойки нет: ни статуса «проживает» (кроме
  кастом-статусов), ни оплаты, ни печати. ✔️ Фикс сегодня: ссылка на чекин теперь
  в письмах confirmed/reminder (раньше — только страница подтверждения).
- **5.7 Выселение** ⚠️ — `fulfilled` + счёт (GoBD) + выручка; сверки/доплат/
  уборки нет.
- **5.8 Статусы номера / 5.9 Хаускипинг** ❌ — 0 % кода (следствие корня №1).
- **5.10 Блокировки** ✅ почти целиком — с шахматки и со страницы номеров, в
  iCal-экспорт и G8-фид; причина — свободный текст (справочника нет); ARI-push в
  OTA нет по дизайну. ✔️ Фикс сегодня: блокировки теперь вычитаются из знаменателя
  отчёта загрузки.
- **5.11 Начисления** ⚠️ — extras только при брони; пост-начислений/штрафов/
  плательщика/своих ставок НДС на позицию нет (следствие корня №2).
- **5.12 Оплаты** ⚠️ — Stripe-предоплата per-тариф + полный возврат есть;
  журнала платежей, наличных/карты/перевода на стойке, доплат, частичных — нет.
  `payment_method` (E7) есть у Order, на StayBooking не портирован.
- **5.13 Компании** ❌ (корень №3).
- **5.14 Документы** ⚠️ — счёт+PDF+DATEV+GoBD на уровне; печатных регкарт, актов,
  списков заездов — нет.
- **5.15 Отчётность** ⚠️ — G9 Belegung/ADR/RevPAR/Umsatz (✔️ сегодня исправлены
  3 искажения формулы: rooms, блокировки, кастом-статусы); нет разрезов
  (источники/тарифы/категории/отмены/LOS/глубина), нет списков «заезды/выезды/
  in-house», нет CSV-экспорта stays, нет stays-виджета на хоуме.
- **5.16 Облако** ✅ — SaaS-природа, мобильный кабинет, удалённо; PWA/офлайн и
  ролевой гейтинг сотрудников — нет.

## 2. Price Optimizer (§6) — статус

- Движок цен полностью **статический**: база → weekend (Fr/Sa хардкод) → сезоны
  (per-unit) → RatePlan ±%/надбавка → G4 авто-скидки (только вниз) → ваучер →
  Kurtaxe. Ничего от **загрузки/темпа** (6.1-6.4) — нет; рекомендаций/автопилота —
  нет; календаря событий — нет (только ручной SeasonRate per-unit); аналитика цен —
  только помесячный G9.
- **Шов для occupancy-based v1 готов:** третий экземпляр JSON-паттерна правил
  (`occupancy_rules` по образцу G4/G12: «загрузка ночи ≥ X % → +Y %»), одна точка
  врезки `pricing.nightly_price_cents`, occupancy дёшево из availability
  (вынести `occupied_by_night`). Обязательно синхронно обновить G8-фид (rate
  parity) и учесть exclude_pk при reprice переноса.
- **Конкуренты (6.6):** данные УЖЕ есть в агрегаторе (цены всех отелей платформы
  по городам + живой кросс-тенантный расчёт по датам с кешем 5 мин) — фича
  «позиция цены в городе» = чтение существующих таблиц. Продуктово/юридически
  (rate parity, картельные риски «подтянись к соседу») — решение владельца.

## 3. CRM (§8.2-8.4) — статус

- **8.2 База** ⚠️ — Customer + 360°-карточка + LTV есть; дыры целостности: дедуп
  только по email, `created_source` не информативен для отеля, LTV отеля
  структурно пуст пока владелец вручную не ставит `fulfilled` (нет авто-beat),
  purge-обезличивание не покрывает stays-гостей.
- **8.3 Сегменты** ⚠️ — движок один (тег ∧ неактивность ∧ top-LTV); нет: новые/
  постоянные-по-числу/дети/категория/отменившие/период/корп. Теги — только руками.
- **8.4 Рассылки** ⚠️ — купон-кампании по сегментам + авто-win-back + DOI/UWG-гейт
  по построению + one-click отписка — сильная база. Дыры: **в воронке брони нет
  чекбокса согласия** (база opt-in не наполняется — бутылочное горлышко), два пути
  ставят согласие без `marketing_opt_in_at` (нет доказательства по UWG §7), ДР-поля
  нет, Telegram в кампаниях не используется (только транзакционные), латентный
  TypeError в win-back при top_ltv из шелла.

**Исправлены сегодня (в батче af6241f):** формула G9 (rooms/блокировки/
кастом-статусы через `counted_statuses_for`), недостижимость Online-Checkin
(ссылка в письмах), мёртвое свойство `GuestRegistration.kurtaxe_eur`.

**Найдены, НЕ исправлены (очередь багфиксов):**

2. Кастом-статусы на шахматке: серые и без drag (литералы в calendar.html).
3. Win-back TypeError при `top_ltv` (слайс → exclude), достижим из шелла.
4. `purge_due_customers` не видит stays-гостей (retention-пробел).
5. Кабинетная форма walk-in: поле note читается вьюхой, но отсутствует в форме;
   guests без adults/children завышает Kurtaxe при детях.

## 5. Предлагаемая очередь (волны, по соотношению эффект/цена)

- **PMS-A «Стойка» (дёшево, сразу видно):** A1 ручная бронь = паритет с витриной
  (тариф/питание/extras/дети/комментарий/источник); A2 списки «Заезды/Выезды
  сегодня» + in-house + stays-виджет хоума (данные и индексы готовы); A3 платежи
  на стойке: `payment_method` на StayBooking (порт E7) + «отметить оплаченным» +
  остаток к доплате; A4 кастом-статусы на шахматке по роли (цвет/drag).
- **PMS-B «Гость/маркетинг»:** B1 чекбокс согласия в воронке брони + фикс
  `opt_in_at` (юр. риск — первым); B2 авто-`fulfilled` beat (оживляет LTV и
  win-back для отеля); B3 авто-теги beat'ом (stammkunde/familie/storniert/
  zimmer:*) → сегменты бесплатно; B4 `Customer.birthday` + ДР-кампания (префилл
  из чекина); B5 Telegram-канал в кампаниях.
- **PMS-C «Отчёты v2»:** разрезы источники/тарифы/категории/отмены + LOS/глубина
  + CSV-экспорт + произвольный период (паттерны annotate/CSV в коде готовы).
- **PMS-D «Цены v2»:** occupancy-надбавки (правила по паттерну G4/G12, ручной
  режим = рекомендация в кабинете, автопилон позже) + tenant-wide событийные
  сезоны; позиция цены среди отелей города — за отдельным решением владельца.
- **PMS-E «Хаускипинг-lite» (без физических номеров):** чек-лист уборок из
  выездов дня (выезд → задача на юнит → галочка «убрано»), готовность видна на
  шахматке. Полные статусы номера — только после развилки №1.
- **Развилки владельца:** (1) вводить ли физические номера (Zimmer 101, 102…)
  под StayUnit — открывает 5.8/5.9/переселение, но это самая большая перестройка;
  (2) корпоративный контур (компании) — большой, спрос неочевиден для микро-
  отелей; (3) показывать ли цены конкурентов.
