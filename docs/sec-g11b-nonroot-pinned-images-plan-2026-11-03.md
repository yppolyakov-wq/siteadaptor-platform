# SEC-G11b — приложение не под root + закреплённые версии образов (2026-11-03)

Хвост аудита безопасности (`security-audit-report-2026-11-01.md` §6, «осталось за рамками
волн»): контейнеры web/worker/beat работают под root, образы БД/Redis/Caddy/Python —
плавающие теги (`postgres:16-alpine`, `redis:7-alpine`, `caddy:2`, `python:3.12-slim`).

## 1. Почему важно
- **root в контейнере:** RCE в Django/Celery (уязвимость зависимости, загрузка файла) =
  root внутри контейнера: запись в код приложения, лёгкий побег через ошибки ядра/рантайма.
- **плавающие теги:** каждый `deploy.sh` может молча притащить новую минорную версию
  Postgres/Redis/Caddy — непроверенную и невоспроизводимую при откате.

## 2. Решение
1. **Dockerfile:** системный пользователь `app` (uid/gid 10001), владелец только
   `/app/media` и `/app/staticfiles` (туда пишут загрузки и `collectstatic` при старте web);
   код и site-packages остаются root-owned → процесс приложения их не перезапишет.
   `USER app` в конце. Базовый образ — `python:3.12.16-slim`.
2. **Том `media` уже существует и принадлежит root** → под `app` загрузка фото упала бы.
   Ручного шага нет: `deploy.sh` перед перезапуском сервисов один раз выравнивает
   владельца **только у несовпадающих файлов** (`find … ! -uid 10001 -exec chown`,
   от root через `run --rm --user 0`). На повторных деплоях находит 0 файлов — секунды.
3. **Теги:** `postgres:16.15-alpine`, `redis:7.4.12-alpine`, `caddy:2.11.7` (сборка
   caddy в `caddy/Dockerfile`). Мажор не меняется (данные Postgres 16 и Redis 7 совместимы
   с минорными версиями внутри мажора); обновление — осознанной правкой тега в коммите.
4. Caddy (порты 80/443), Postgres и Redis не трогаем: официальные образы сами
   понижают права (postgres/redis), Caddy слушает привилегированные порты.

## 3. Что пишет приложение во время работы (проверено grep'ом)
| Путь | Кто | Под `app` |
|---|---|---|
| `/app/staticfiles` | `collectstatic` при старте web | ✅ владелец app |
| `/app/media` (том) | загрузки, импорт, документы | ✅ после выравнивания в deploy.sh |
| `/tmp` | временные файлы экспорта/PDF | ✅ общий |
| `.pyc` | — | `PYTHONDONTWRITEBYTECODE=1`, не пишутся |
| celery beat | `DatabaseScheduler` — файла расписания нет | ✅ |
| `.mo` переводов | компилируются при СБОРКЕ (root) | ✅ |

## 4. Риски
- Локально образ не собрать (в среде сессии нет Docker-демона) → проверка: замки на
  текст Dockerfile/compose/deploy.sh + `docker compose config` невозможен; первый
  реальный прогон — деплой владельца. Откат: `git revert` коммита и повторный деплой
  (владелец тома после выравнивания — 10001; root-процесс старого образа всё равно может
  писать туда, откат безопасен).
- Файлы, созданные в томе позже из-под root (ручной `docker compose exec` от root) —
  следующий деплой выровняет их сам.

## 5. ECC-прогоны
| Когда | Что | Зачем |
|---|---|---|
| до кода | скиллы `docker-patterns`, `deployment-patterns` | non-root, закрепление тегов, порядок шагов деплоя |
| после кода | `security-reviewer` | Dockerfile/compose/deploy.sh: права, что ещё пишет под root, побочные эффекты chown на томе |
| после кода | `silent-failure-hunter` (deploy.sh) | шаг выравнивания не должен молча пропускаться и не должен ронять деплой при пустом томе |
| перед мержем | CI на git | финальный гейт (замки текста) |
| ops | владелец: обычный `./scripts/deploy.sh single` | первый прогон выравнивает том; проверить загрузку фото в кабинете |
