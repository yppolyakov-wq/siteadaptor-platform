### C. M5a-2 — кэш 404 и `noindex` при `?q=`
Сейчас: `pagecache._cacheable:86` кэширует только 200, `_unpack:126-139` собирает 200; 404 рендерит хром на
каждый битый адрес (`not_found_views.py:62-70,101`). В теле 404 от запроса зависят: переключатель языка
(`_header_icons.html:30`, `next=` с путём), баннер демо (`_demo_banner.html:12,15`), обложка раздела при
`Http404` из вьюхи раздела (`context.py:406-425`, дефект §5.6). Robots на листингах ставит только
`_base.html:25` (у демо); `canonical_link` query уже отрезает.

(а) Кэш — одна функция в `pagecache`, второго кэша нет:
- `NOT_FOUND_CACHE_TTL = 60`; рабочий TTL — `min(PUBLIC_PAGE_CACHE_TTL, …)` (0 выключает);
- ключ `sf404:{host}:{schema}:{lang}:v{версия}` — без пути (хост через `_cache_host`);
- мимо кэша: не GET/HEAD, любой query, **любая** cookie, непустая сессия; запись — при прежних проверках
  `_cacheable` со `status=404`; хит — код 404, `X-Robots-Tag`, `Vary: Cookie`; Cache-Control не ставим;
- вызов — в `storefront_404` строго после `_wants_blocks` (простая 404 для `/media/`, `/static/`, портала,
  закрытой витрины в кэш не попадает); legacy-301/410 работают — кэш внутри обработчика;
- тело без пути: `_page` кладёт `archetype_cover: {}` (заодно закрывает дефект §5.6) и
  `storefront_return_path: "/"`; два шаблона читают его с запасным прежним значением — остальные страницы
  выводят те же байты;
- сбой Redis — страница отдаётся, WARNING с порогом по времени в процессе.

(б) `noindex`: в `context.py` рядом с `_SEARCH_ROUTES` — `SEARCH_NOINDEX_ROUTES` (производный набор +
`storefront-aktionen`, `storefront-category`), ключ контекста `storefront_search_noindex` (маршрут из набора и
непустой после `strip` `q`); `_base.html:25` — один мета-тег `noindex,follow` (демо или поиск). `?page=` и
фасеты не трогаем.

Коммиты: замки (`apps/core/tests/test_fb33_m5a2_cache_search.py`) → `pagecache` → 404 через кэш + шаблоны →
`noindex` → заметки для доков (сводит координатор).
