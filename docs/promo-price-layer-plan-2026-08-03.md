# План: «Акция = ценовой слой над базовой сущностью» (2026-08-03)

Решение владельца: переводим ВСЕ акции на новые рельсы; услуги — с привязкой к
периоду/мастеру/слотам; наборы — расширяем Combo. Требование: акция зависит от
РЕАЛЬНОГО наличия (товар/номер/услуга в период), попадает в СТАНДАРТНЫЙ
заказ/бронь, закрывается там наличием, клиент ведётся как обычно (CRM).
Разведка движка — отчёт агента 2026-08-03 (факты сверены с кодом).

## 1. Что вскрыла разведка (главное)
- `Promotion.product` FK **уже существует** (с 0001), но используется только для
  фолбэка цены/фото/PAngV — ни в чекауте, ни в наличии не участвует.
- **Два независимых счётчика**: `Promotion.available_quantity` (conditional
  UPDATE, F(), замок 100 потоков) и `Product.stock_quantity` (`_reserve_stock`).
  Одну коробку можно продать дважды: через корзину и через резерв акции.
- **Рельсы уже готовы принять промо-цену**:
  `create_order(custom_lines=(title, price, qty, product, variant))` — замороженная
  цена + ШТАТНОЕ списание склада; `book(price_cents=…)` — цена услуги снаружи;
  `book_stay` уже снимкует авто-скидку (`auto_discount_cents/label`) — паттерн
  Lücken-Deal = готовый прецедент «ценовой слой над реальным наличием».
- У stays слой УЖЕ работает по-владельчески (G4+Lücken); дельта волны — orders,
  booking и сама детальная акция.
- Потребители Promotion/Reservation: агрегатор (snapshot цен), publishing,
  finance (`source="reservation"`), доска (kind reservation), ЛК, CRM, демо,
  45 тест-модулей. `status_effects` зеркалит возврат остатка для кастом-статусов.

## 2. Целевая модель
**Акция = кампания скидки над целью.** Цель: product | variant? | combo |
service | stay_unit | (пусто = свободная акция). Одна аддитивная миграция
`promotions/0025`: FK `service`→booking.Service, `stay_unit`→stays.StayUnit,
`combo`→catalog.Combo (nullable, SET_NULL; `product` остаётся как есть — нулевая
миграция для всех текущих акций). Условия для услуг — JSON `target_rules`
(паттерн `auto_discount_rules` + `clean_*_rules`): дни недели/часы (период,
«счастливые часы»), `resource_id` (мастер), конкретные даты.

**Два счётчика с РАЗНЫМИ ролями:** `available_quantity` становится «лимитом
кампании» (сколько единиц отдаём по акционной цене; conditional UPDATE и ветка
None остаются как есть), физическое наличие закрывает ШТАТНЫЙ движок цели
(`_reserve_stock` / anti-double-book / `range_available`).

**Чекаут = стандартные сделки.** Деталь акции диспатчится buybox'ом по
purchase_mode ЦЕЛИ (SellableEntity уже отдаёт select_url/submit_url):
- товар/вариант → `create_order(custom_lines=…)` (склад штатно);
- combo → тот же путь (позиция combo уже продаётся через create_order);
- услуга → селектор слотов услуги (фильтр по `target_rules`: период/мастер) →
  `book(service, price_cents=промо)`;
- номер → выбор дат → `book_stay` с промо-кандидатом в `pricing.auto_discount`
  (метка «Aktion: <title>», механика Lücken-Deal);
- свободная акция (без цели) → `create_order(custom_lines=(title, price, qty,
  None, None))` — стандартный заказ с замороженной строкой, канбан/CRM/письма
  штатные. **Kind reservation больше не порождается**; /r/<code>/ и открытые
  резервы доживают (история цела), вкладка «Reservierungen» исчезает сама по
  мере опустошения (exists-гейт Verkäufe).

**Витрина базовой сущности показывает акцию** (обратная сторона зависимости):
карточка/деталь товара/услуги/номера с активной акцией рендерит промо-цену и
бейдж (сегодня товарная деталь про акцию не знает вовсе).

## 3. Инкременты
- **P1 модель** (⚠️ `promotions/0025`): 3 FK + `target_rules` + валидатор +
  пикер цели в форме акции (реюз FB-8 sellable_manage-пикера) + `target`-резолвер
  на контракт SellableEntity.
- **P2 чекаут-товар/сombo/свободная**: ветка cart в детали акции →
  `create_order(custom_lines)`; списание лимита кампании В ТОЙ ЖЕ транзакции
  (conditional UPDATE; откат при OutOfStock штатным исключением); PAngV/письма
  заказа. Замок: промо-продажа списывает ОБА счётчика; корзина без акции цела.
- **P3 чекаут-услуга**: `target_rules` (период/мастер/слоты) + фильтр селектора
  слотов + `book(price_cents=промо)`; замки: слот вне правила не продаётся по
  промо-цене; anti-double-book цел.
- **P4 чекаут-номер**: промо-кандидат в `auto_discount` (не суммируем — макс,
  как сейчас) + лимит кампании; Belegungsplan/письма штатные.
- **P5 перевод витрины акций**: /p/<uuid>/ buybox по цели; /aktionen/ карточки
  целы (цены уже property); Reservation-флоу закрыт для новых; конфирмация
  редиректит в стандартные подтверждения сделок.
- **P6 промо-цена на витрине цели** + демо-киты (bakery «Brötchen −50%» станет
  настоящим товарным чекаутом; отель — акция на номер) + build-log/CLAUDE.md.
- **P7 хвосты потребителей**: аналитика (конверсия по сделкам вместо
  Reservation), finance source, агрегатор/publishing (snapshot цел — читает
  property), status_effects-зеркало, ЛК/CRM (360° показывает сделки штатно).

Каждый инкремент — паритет-замки ДО правок чекаутов (create_order/book/
book_stay — байт-в-байт без акции), адверсариальное ревью анти-оверселла.

## 4. Риски
1. Ядро anti-oversell: двойное списание (лимит кампании + склад) обязано жить в
   ОДНОЙ транзакции с корректным откатом обоих.
2. `status_effects.restore_stock_for("reservation")` — зеркало возврата: пока
   живы легаси-резервы, не трогаем; после опустошения — деприкация.
3. Возврат лимита кампании при отмене СТАНДАРТНОЙ сделки: нужен маркер «эта
   сделка из акции» (snapshot в `OrderItem.modifiers` / `Booking.note`? — решить
   в P2: предлагаю поле `promotion` FK на OrderItem/Booking/StayBooking НЕ
   заводить, а вернуть лимит по метке в metadata + FSM-hook; проверить в ревью).
4. 45 тест-модулей promotions: прогонять целиком на каждом инкременте.
