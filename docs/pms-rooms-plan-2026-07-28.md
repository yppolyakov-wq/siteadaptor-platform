# PMS-R — Физические номера («Zimmer 101») поверх категорий

**Дата:** 2026-07-28 · **Статус:** одобрено владельцем («вводить физические
номера — да»). Открывает: статусы номера (спека 5.8), хаускипинг (5.9),
переселение «в номер» (5.4/5.6), построчную шахматку (5.2), «брони без
назначенного номера» (5.15).

## 1. Архитектурный принцип — Вариант A (домашний паттерн склада E1/E2)

**Движки брони НЕ переписываем.** `StayUnit.quantity` остаётся единственным
источником ёмкости для anti-oversell/availability/цен — как счётчик остатка на
складе. Физические комнаты — **разбивка поверх** (как партии Lot/локации):

- Новая TENANT-модель `stays.Room`: `unit FK` (категория), `number`
  (CharField 40, «101»), `sort_order`, `is_active`, `notes`; unique
  `(unit, number)`. Миграция аддитивная.
- Пока у юнита 0 комнат — ничего не меняется нигде (ленивая активация, как
  мультисклад E2: UI появляется при заведённых комнатах).
- Синхронизация ёмкости: при create/delete/деактивации Room с непустым набором —
  `unit.quantity = live count активных` (targeted-write). У юнита с комнатами
  поле quantity в форме становится read-only («считается по номерам»).

## 2. Назначение номера брони

- `StayBooking.room FK null` (аддитивная миграция). NULL = «не назначен» —
  легитимное состояние (OTA/онлайн-брони приходят без номера).
- Назначение: (а) в карточке брони (селект свободных на диапазон комнат
  категории); (б) drag на шахматке v2 (дорожка = комната). Конфликт-чек:
  пересечение дат по той же Room среди активных броней → отказ с причиной
  (это UI-валидация поверх; глобальный anti-oversell по quantity остаётся
  жёсткой гарантией).
- `move_stay` при смене категории сбрасывает room (комната принадлежит
  категории).
- Список «Ohne Zimmer» (нужно назначить) — на шахматке, счётчиком+фильтром.

## 3. Шахматка v2

- Юнит с комнатами → по строке НА КОМНАТУ (заголовок «101 · Doppelzimmer»);
  назначенные брони — на строке комнаты, неназначенные — на общей строке
  категории «— ohne Zimmer» сверху. Юнит без комнат — как сейчас (лейны).
- Drop на строку комнаты = назначение + перенос дат (существующий move-fetch +
  `room` в POST).

## 4. Статусы номера + хаускипинг-lite (следующий инкремент после R1-R2)

- `Room.housekeeping` ∈ clean/dirty/inspected + `out_of_order bool` (блокировка
  через существующий UnitBlock с привязкой `room FK null` — аддитивно).
- Автопереход: выезд (fulfilled) → room.dirty. Список уборки «сегодня»
  (выезды дня + dirty) + чек «убрано» → clean; бейдж на шахматке.

## 5. Инкременты

- **R1** модель Room + CRUD на `stays:units` (секция «Zimmer» у юнита) +
  quantity-синк + замки (ленивая активация: без комнат всё байт-в-байт).
- **R2** `StayBooking.room` + назначение в карточке брони + «Ohne Zimmer».
- **R3** шахматка v2 (строки-комнаты + drop-назначение).
- **R4** хаускипинг-lite (§4) + статусы номера.
- Демо: hotel-кит заводит комнаты 101–104 (после R1).

Миграции: R1 `stays/0025` (Room), R2 `stays/0026` (booking.room, block.room) —
аддитивные, деплой владельцем.
