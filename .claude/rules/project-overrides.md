# Проектные правила поверх ECC

Правила `.claude/rules/ecc/` — общие советы. Где они расходятся с этим проектом,
действуют `CLAUDE.md` и пункты ниже:

- **Форматирование/линт:** только `ruff check` + `ruff format` (black/isort НЕ используем).
- **Коммиты:** стиль истории репозитория (`<ID задачи>: …` на русском), не conventional commits.
- **GitHub:** `gh` CLI в облачных сессиях недоступен — только MCP-инструменты `mcp__github__*`;
  PR не создавать без явной просьбы владельца.
- **Тесты:** pytest на Postgres (`--reuse-db` локально), CI на git — финальный гейт.
  Порог покрытия 80 % и обязательные E2E — не требование проекта; JS-фичи гейтим Playwright-стендом.
- **Размеры файлов/функций, иммутабельность, Repository-паттерн, API-конверты:** не переписываем
  существующий код ради этих правил — пишем как окружающий код (Django-идиомы).
- **FastAPI-правила** (`ecc/python/fastapi.md`) к проекту не относятся (Django).
- **Модели/эффорт** (`ecc/common/performance.md`): не менять настройки модели без просьбы владельца.
- **Имена агентов ECC:** без префикса `ecc:` (`planner`, `code-reviewer`, …) — они лежат в
  `.claude/agents/` копией, плагина нет.
- **Когда звать агентов ECC:** по просьбе владельца или для нетривиальной работы (план, ревью
  ветки перед мержем, разбор миграций). Пометки «MUST BE USED / PROACTIVELY» в их описаниях
  не означают «на каждую правку» — рабочий цикл задаёт `CLAUDE.md` §5.
- **Зависимости:** только `uv` и `uv.lock` (`uv add`/`uv lock` осознанно, в коммите) —
  не `pip install`, не `requirements.txt`, не Poetry.
- **Миграции (django-tenants):** `migrate_schemas`/`./scripts/deploy.sh`; без согласия владельца
  НЕ делать `migrate <app> zero`, `--fake`, `makemigrations --merge`, удаление миграций.
- **Процессы:** не убивать чужие процессы (`kill -9`) и не чистить кэши/окружение «на всякий случай».
